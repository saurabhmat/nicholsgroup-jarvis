## The route's order of checks (each refusal a fixed code, nothing proposed before the last)
1. same site (as `sameSite()` in `lib/teams-api.ts` does it): for a POST the `Origin` header must equal the request's own origin exactly (a missing or different `Origin` is 403 `forbidden`); `Sec-Fetch-Site`, when the browser sends it, must be `same-origin`, but a request WITHOUT `Sec-Fetch-Site` is accepted and relies on the exact `Origin` match alone (SameSite cookies and the AAL2 session still apply)
2. lane id shape (404 `not_found`)
3. session, lane membership, role with `own_mail`, AAL2 (401 `no_session` / 403 `mfa_required` / 404)
4. step-up within the LANE's Teams window (`teamsStepUpWindow`, never from the request) with the Teams bound (403 `step_up_required`)
5. `messages` module visible (404)
6. body read, at most 100,000 bytes, exactly `{conn, chat, text, textSha256, clientRequestId}` (400 `bad_request`)
7. `conn` is a lower-case uuid (400) and one of the caller's OWN Teams rows in this lane (read under RLS, `mine`); another person's, another lane's, disconnected, pending and unknown ids are the SAME 404; the caller's own expired one is 409 `reconnect`
8. 1 request per second per connection (429 `rate_limited`, `retry-after`)
9. chat key decodes (400)
10. approvals entry: write role (403), the connection is the caller's usable Teams connection (404), gates in this order: `lane_off`, `reconnect`, `policy_off`, `drafts_off`, `not_live` (409 `gate_<name>`), text by the Zod schema (400 `invalid_message`), hash (400 `text_mismatch`)
11. propose + approve the computed hash + claim + ONE POST + read-back, inline. Answer `{ok, state}` with `sent` / `checking` / `not_sent` (+ fixed `code`, `message`) / `unknown`; an unclassified failure after step 10 started is 502 `unknown_outcome`.
`cache-control: no-store` on every answer. The database re-checks owner, role, AAL2, the step-up age (`act.approve`), every gate and the single claim.

## What is stored, where, and for how long
- Server: the proposal row holds `payload.text` only while the action is proposed / approved / executing (T-286: emptied by the database in the same statement as every terminal state). Ids, type and hash go to status history and the audit; the text never does. Nothing else stores it: not logs, errors, Inngest events, the approvals history, `result`, claims.
- The one POST body holds the text (to Microsoft).
- Browser: the textarea state; a copy in sessionStorage under `nichols:teams-draft:<lane>:<user>:<conn>:<chat>` for 2 hours (written 500 ms after the last keystroke; removed on Sent, Sent-checking and Outcome-unknown; removed at sign-out by `clearAllDrafts`; per tab, never sent to the server except in the send request). The sent bubble is memory only.
- Logs: the route logs the error CLASS only (`[api/teams-messages] unavailable / send ended unknown`).

## Review fixes (second commit series, "T-288 review")
### A. The request id, and what a replay of the same id and the same text returns
The id belongs to the exact text of one intended message. It is made at the first press for a text and kept (in memory and, while a request may be open, in the tab's session storage with the text's hash and start time) until the server has confirmed a terminal outcome: `sent`, `checking`, or a definite `not_sent` from an action that was proposed. A refusal that the route made before proposing (429, a gate, a stale code, 503 `unavailable`) keeps the id; an unknown outcome keeps it; a changed text makes a new id; a refusal that rejected its proposal on the spot (`fresh: true`) makes a new id.
What `POST .../messages/send` answers for a replay (`act_propose` returns the existing action for the same connection + id + hash, in any state, with the text purged or not; the hash is over the text, so the text itself is not needed after a purge):
| State of the action | What the replay does | Answer |
|---|---|---|
| proposed (never approved) | approves the same hash, sends ONCE | the send's own outcome (`sent` with the message id) |
| approved, not claimed (a killed request) | resumes: claim, one POST | the send's own outcome |
| executing, nothing recorded yet | no POST, no claim | `unknown` (Outcome unknown; Check again asks again) |
| executing, message accepted, not read back | no POST | `checking` (Sent, checking) |
| approved, claimed by another request still running | no POST | `unknown` (never "Sent, checking") |
| verified | no POST | `sent` (no message id: the browser matches by text, one to one) |
| verified, text purged | no POST, the text is not needed | `sent` |
| failed with a definite code | no POST | `not_sent` with the fixed sentence; the next press makes a new id |
| failed with an unknown-outcome code | no POST | `unknown` |
| expired (lazy or swept), invalidated by a disconnect, rejected | no POST | `not_sent` (`expired`, `connection_disconnected`, `execution_refused`), new id next time |
| same id, different text | nothing | 409 `request_reused` (the browser never does this: a changed text is a new id) |
Tested in `teams.test.ts` ("a replay ... in every state") and, behind the real route, in `apps/web/tests/teams-send-combined.test.ts`.
On return to a chat with a marker without an answer the composer shows "This message may have been sent. Check the chat in Teams before sending again." with **Check again** (the same id and text; the server's answer is shown) and **Discard** (removes the marker; the text stays on the page to copy). A late answer while the person was away updates the stored marker (`sent`, `checking`, `not_sent`, which also puts the text back into an empty box), and a composer that is open hears it.
