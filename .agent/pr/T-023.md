# T-023: App shell and lane switcher

## Summary
Authenticated layout under `/[laneId]/...`.
- **Desktop:** navy side menu.
- **iPhone:** navy header band and bottom tabs.
- **Company switcher:** limited to lanes that are enabled, served by this deployment and allowed for the user (aal2).
- **Routes:** a placeholder route for every module.
- **Lane in the URL:** verified on the server in the layout and in every page.

Scope per Saurabh (Nov 4, 2026): Projects is shown (between Assistant and Settings; under More on iPhone), and the shell has light and dark mode (follows the system, with a System/Light/Dark override). The signed-off design record is `docs/design/README.md`.

The first browser run also found three sign-in redirects that showed the right page at the wrong address. They are fixed here; T-018 to T-020 were only waiting on these browser tests.

## Changes
- **`packages/core`:**
  - `LaneRouter.listLanes(session)`: user client and RLS on `core.lanes`, intersected with ENABLED_LANES and the core data plane. A failed query throws instead of returning an empty list.
  - `Guards.listLanes()`, `laneSegment()`, `laneVerdict()` and the `LaneSummary` type.
  - No SQL.
- **`packages/ui`:**
  - `AppShell` and `LaneSwitcher`.
  - Nav as data in `lib/nav.ts` (T-024 edits this table).
  - `lib/theme.ts`: `data-theme` on `<html>`, a pre-paint script, the choice kept in localStorage only.
  - Tokens only. The light and dark values and the chart palette are in 4a17d71.
- **`apps/web` shell:**
  - `app/[laneId]/layout.tsx` and 9 pages.
  - `lib/lane-page.ts` (`loadLane`): unknown, disabled and non-member lanes all get the same 404. No session goes to sign-in; AAL1 goes to `/mfa`.
  - `/` goes to the first allowed lane, or shows "no company access".
  - `proxy.ts` answers a refused lane with a real 404 before streaming starts. The pages still do their own check.
  - Theme toggle.
- **Sign-in redirect fixes (found by the first browser run):**
  - The email code goes straight to `/mfa?next=…`. Every user has MFA (D-6).
  - The email-link handler returns a relative 303. `next dev` reports `localhost` for `127.0.0.1`, so the cookie did not follow the old redirect.
  - After the authenticator code, the user lands on their first lane (`lib/landing.ts`) instead of `/` redirecting mid-stream, which had kept `/` in the address bar.
- **Review fixes:**
  - The Approvals placeholder now reads "Approvals are not set up yet".
  - `/` shows the no-access notice for a `forbidden` user instead of redirecting to `/sign-in`, which could loop.
- **Test infra:**
  - The root ESLint-config test timeout is 30 s; it timed out at random under turbo's parallel load.
  - e2e waits allow for first-visit compiles in `next dev`.
  - Runbook: `docs/runbooks/e2e-browsers.md`.

## Review
- **Security review** (`.agent/notes/review-T-023-security.md`) and **code review** (`.agent/notes/review-T-023-code.md`) of b872029: no BLOCKER or HIGH. Two MEDIUM and LOW items were fixed (see Changes); the rest are logged in `docs/plan-review.md` §6 (T-023).

  - **Root files treated as lane ids.** The proxy treats files such as `/robots.txt` as lane ids, so they 404. It fails closed. Fix in T-025 at the latest.

## Risks
- The proxy lane check adds session reads and a `core.lanes` query to every page request, including prefetches. This uses Auth rate-limit budget; the reduction is logged.
- Root-level public files added later (T-025) need the proxy's lane check narrowed.
- The theme script is inline. A strict CSP later needs a nonce or hash for it.
