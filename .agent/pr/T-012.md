# T-012: Users, memberships, roles, allowed_lanes()

Approved by Saurabh, Oct 31, 2026 (combined branch `agent/pilot-build`; split into its own PR later).

## Changes
- Migration `20261031043014_users_memberships_allowed_lanes.sql`:
  - `core.users` (one row per auth user, display name) and `core.memberships` (user, lane, role ∈ owner / finance_operator / viewer / admin_technical, `views` for viewers only).
  - `core.view_names()`: every view name a policy may use (`lanes`, `lane_policies`, `memberships`, `action_index`, content views, operations views). `core.viewer_view_names()`: the content views a viewer may be granted (finance, briefing, projects, calendar, commitments).
  - `core.role_views(role)`: owner = all; finance_operator = lanes, action_index, finance; admin_technical = lanes, action_index, lane_policies, memberships, connections, health, jobs, config (no content); viewer = lanes, action_index + its named views.
  - `core.allowed_lanes(uid, view)` replaces T-010's placeholder: security definer, `search_path = ''`, fails closed. It answers only for the caller's own uid at aal2, or for any uid when the session's database role is service_role (`core.may_resolve`). Only enabled lanes, only currently known view names.
  - `core.has_lane_role(uid, lane, roles)`: the same rules, for actions a view does not imply (finance sign-off: owner, finance_operator; a viewer with the finance view cannot).
  - RLS: memberships readable as own rows plus lanes where the caller has the `memberships` view; users readable as self plus members of those lanes. No DML for anon/authenticated.
- Seed: `users-memberships` section (all five personas get a `core.users` row; the outsider has no membership; the viewer has the named view `finance`). `data.mjs` carries viewer views.
- Tests: `030_memberships.test.sql` (52), and `020_lanes.test.sql` now runs on real memberships, including an APK-only member who cannot read the PKG policy and the reverse.

## Review (security, Oct 31, 2026; no BLOCKER or HIGH)
- M1 (fixed): the service_role branch trusted the JWT `role` claim, which any SQL session can set. It now uses the session's database role (`current_setting('role')`, set by PostgREST from the verified JWT). Test: an authenticated session with a forged `service_role` claim gets nothing.
- M2 (fixed): finance_operator no longer gets the lane-wide `approvals` view (approvals spec §4: a proposer sees only its own proposals, through the act.* policy). Viewers can be granted only content views (`viewer_view_names()`), tested. `action_index` named for every member (approvals spec §4, `core.action_index`).
- L1 (fixed): `core.has_lane_role()` with tests (finance_operator and owner yes; viewer with finance, admin_technical, aal1, another uid no).
- L2 (fixed): `allowed_lanes` intersects with the current `view_names()`, so a removed name stops granting access; removal still needs a data migration (documented).
- L3 (fixed): the owner membership test asserts the full set (no filter); forged-claim case added; a test label corrected.
- L4 (recorded in T-013): `core.users` and `core.lanes` have no `lane_id` by design; the T-013 catalog test needs an explicit allowlist.

## Risks
- `may_resolve` relies on PostgREST's `set role` for service_role. A direct database connection used by jobs would connect as a role other than service_role and get nothing (fails closed); decide in T-016.
