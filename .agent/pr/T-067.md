# T-067: Microsoft: calendar delta sync

`docs/specs/microsoft.md` §9 (under decision D-59), §6.3, §17 (tests 18 and 19). TypeScript only: no SQL, no migration, no pgTAP change, no new dependency, no allow-list entry, no `eslint-disable`.

## Summary
`CalendarProvider<"microsoft">` now syncs a person's DEFAULT calendar with `GET /me/calendarView/delta?startDateTime=..&endDateTime=..` (the form Microsoft documents for v1.0), maps events to the strict `EventMeta`, reads an event's body live, and the facade's Microsoft calendar stream is real. A Microsoft `conn.sync` run without `streams` no longer fails after mail, and the scheduled calendar tick works for Microsoft connections. Google behaviour is unchanged.
- One calendar, one link, one window (D-59). No `GET /me/calendars`, no per-calendar request, no selection. `microsoft.calendar_ids` is ignored and logged once per run as a count (never the ids, never an error); `calendar.calendar_ids` and `calendar.include_read_only` are not applied to a Microsoft connection.
- The window goes on the INITIAL request only (`[today - min(180, retention), today + forward_days]`, UTC midnights, ISO 8601); later requests send the returned link's validated query unchanged. When the forward part of the window has run down below half of `forward_days`, a fresh full load with a new window starts (as T-064 does for Google); a load in progress is never reloaded, and a failed reload leaves the old cursor.
- `$select`, `$filter`, `$orderby`, `$search` and `$expand` are never sent (not supported on this delta), so Graph returns event bodies on every page. The mapper declares only the fields it uses, so `body`, `bodyPreview`, `onlineMeetingUrl` and everything else are dropped in memory (rule 6).
- Every request, link requests included, carries ONE `Prefer` header: `IdType="ImmutableId", outlook.timezone="UTC", odata.maxpagesize=N` (the Graph client's header rule already allows it: `Prefer` only, printable ASCII, up to 200 characters; no change was needed).
- Stored links: same rules as T-258. The request is always rebuilt on `/me/calendarView/delta`; only a validated query is reused. A link is valid only if the text before `?` is exactly `https://graph.microsoft.com/v1.0/me/calendarView/delta` and the query is exactly one `$skiptoken` or one `$deltatoken`, optionally with `startDateTime=<our window start>` and `endDateTime=<our window end>` byte for byte. Anything else in a stored cursor is `fullResyncRequired` with no request and no token read; a link Graph returns that fails the rule is not stored (`provider_error`, fixed message); a nextLink equal to the one just used is an error; a link over the bound is never cut (a resync).
- Mapping: `seriesMasterId` -> `recurring_event_id`, `originalStart` -> `original_start_at` (instances only); `isCancelled` -> a cancelled stub (the page writer merges the status only, as for Google); `onlineMeeting.joinUrl` (https only) -> `online_meeting_url`; `webLink` only on the allow-listed Outlook hosts (the T-258 `safeWebLink`); attendees capped at 500; subject, names, addresses and location cleaned and bounded as the mail mapper does (only a bad address is dropped, never the event). A `dateTime` without an offset is UTC; an event answered in a zone other than UTC is skipped and counted. A `seriesMaster` item (calendarView should not return one) is skipped and counted.
- All-day events: start and end are midnight in the event's own zone; the zone comes from `originalStartTimeZone` through a Windows-to-IANA table in `microsoft/cal-zones.ts` (marked as OUR assumption; 58 zones: every US zone including Alaska, Hawaii and Arizona, UTC/GMT, the main European, Indian, East Asian and Australian ones). An all-day event whose zone is missing from the table, is `tzone://Microsoft/Custom`, or whose instants are not that zone's local midnights is skipped and counted in a log line with no subject, id or zone name.
- `@removed` -> `removals`, whatever the reason (Microsoft also sends one for an event that fell out of the date range; the writer marks the row cancelled, which is right for an event that left the window).
- `readBody`: `GET /me/events/{id}?$select=body` with `Prefer: IdType="ImmutableId", outlook.body-content-type="text"`; the type is read from the answer, HTML converted by the shared converter, bounded, `UntrustedBody`, `live`, never persisted. Guard first, then the id schemas and the options, then the calendar id, then the request.

## Calendar id chosen for the default calendar
`microsoft:default` (`DEFAULT_CALENDAR_ID`, `microsoft/cal-cursor.ts`). It has a colon, which the characters of a Graph id (letters, digits, `_ - = + .`) never include, so it cannot equal a real Graph calendar id; it is stable across runs; `ProviderIdParamSchema` accepts it (`readBody` takes it as a path-free parameter); it fits the table's 512 characters. No existing reader or schema needs the real calendar id (the readers use `calendar_id` only inside a dedupe key and as a pass-through column), so the real id is never read.

## Bounds chosen
- Window: back `min(180, lane retention)` days (at least 1), ahead `forward_days` (lane setting, default 365), both as UTC midnights. Half-horizon: a reload when fewer than `floor(forward_days / 2)` days remain ahead (the T-064 rule), checked only on a finished load.
- Page size: 50 events by default (mail uses 100); events are heavier because the delta cannot `$select` and each carries its body. `CommsSyncOptions.pageSize` overrides it.
- Link: at most `MAX_LINK_CHARS` = 4,151 characters (the fixed head, `?`, and 4,096 characters of query, which is the Graph client's own limit for a raw query). With the window (120 characters) the largest allowed state encodes to about 5.8 KB, well under the cursor's 16,384. A longer link is never cut or stored. A cursor value longer than 16,384 is answered as a foreign cursor (a resync).
- Run budget: 150 seconds per run, the same value and reasons as the mail run (`MICROSOFT_CALENDAR_RUN_BUDGET_MS`; checked between pages; one failing page can still take about 210 seconds, logged for T-258).
- Attendees: 500 (Microsoft's documented maximum), and at most 100,000 serialized bytes (as the Google mapper); each entry is parsed on its own, at most 5,000 entries are looked at, and a cut list is counted as `attendees_truncated` in the skip log line. An IANA zone name that `Intl` knows is accepted for all-day events after the Windows table; the cursor's window must be canonical, at most 911 days long and end at most 731 days after now. Items per page: at most 2,000.
- Skips are counted by fixed reason (`invalid_item`, `series_master`, `not_utc`, `invalid_times`, `all_day_zone_unusable`, `invalid_all_day`, `invalid_event`, `invalid_removal`); nothing from an event is in the log.

## Risks
- **Default calendar only (D-59).** Shared and secondary calendars are not shown; a person who keeps meetings in a secondary calendar sees none of them until a later task.
- **All-day events in a zone that is not in the table are skipped** (and counted in `microsoft.calendar.events_skipped`); they do not appear in Home or the briefing. The table is our own assumption, not Microsoft's documentation.
- An event answered in a zone other than UTC is skipped (never guessed); if Microsoft names UTC in another spelling than `UTC`, every event would be skipped, visibly in the log counts (live check below).
- Timed events carry `timezone` only when `originalStartTimeZone` is in the table; otherwise null (Home displays instants).
- A removal for an event that left the window turns its row to cancelled. If the same event later comes back with an unchanged `lastModifiedDateTime`, the page writer keeps it cancelled (it needs a strictly newer version over a cancelled row). An edit that brings it back changes the version, so this only affects a window shift without an edit.
- `readBody` cannot prove the event is in the default calendar, and no caller exists yet: the facade has no calendar `readBody` and nothing in the app calls it. `GET /me/events/{id}` answers for the event id alone and the provider has no access to the index (no SQL, no store dependency). The request can only reach the mailbox owner's own events, under the connection's own token (`/me` only). Before the first caller is wired, that caller (or a facade method) must check that an index row exists for this lane, connection, `microsoft:default` and event id for that owner, and pass the owner as the mail `readBody` does.
- Home dedupes by `ical_uid` plus start time across connections in SQL (`core.home_calendar...`); Microsoft rows carry `iCalUId`, so the same meeting seen in a Google and a Microsoft calendar may collapse in some readers. D-58 says no de-duplication; the wiring task T-261 should check this.
- A first load of a large calendar takes many pages; the run budget stops a run after 150 seconds and the next continues from the stored link (`last_sync_at` advances only when a load completes).
- The fake is built from the documentation as read by the calling session; real behaviour is unverified (see Needs human).
