# T-005: Environment config

## Changes
- `packages/core/src/env/` (new), exported as `@nichols/core/env`, `/env/client`, `/env/server`, `/env/build`, `/env/startup`, `/env/secret-patterns`:
  - `secret-patterns.js`: plain ESM (no imports, no `server-only`, loads under Node 22) so T-003's ESLint rule can import it. Name patterns, the exact-name `PUBLIC_BY_DESIGN_NAMES` allowlist (Supabase publishable key, VAPID public key, Sentry DSN), value patterns (vendor prefixes, PEM keys, URLs with a password, JWTs with `role=service_role`), and `FREE_TEXT_VALUE_NAMES` (six Vercel git variables skipped by the value scan only).
  - `schema.ts`: pure Zod 4 schemas and parsers (no `process.env`). Blank counts as unset; errors carry variable names only (Zod messages, inputs and `cause` dropped). Cross-field rules: `APP_ENV` must agree with `VERCEL`/`VERCEL_ENV`; https required outside local for the app, Supabase, NL, Sentry and Intuit redirect URLs.
  - `client.ts`: `getClientEnv()`, literal `process.env.NEXT_PUBLIC_*` reads so Next inlines them; values allow-pattern checked (`sb_publishable_…`, VAPID format, http(s) URLs) and scanned for secrets.
  - `server.ts` (`server-only`): `getServerEnv()` (no secrets in it), `getSupabaseSecretKey()`, `getAnthropicEnv()` / `getInngestEnv()` returning `{ configured: true, … } | { configured: false, missing }`, `requireConnectorEnv(name)` (fails closed, names only). Production is always derived from the real `process.env`.
  - `redact.ts`: `toJSON` / `util.inspect` redaction on returned env objects (defence in depth only).
  - `build.ts`: `assertBuildEnv()`; also scans every `NEXT_PUBLIC_*` variable present, not only declared ones.
  - `startup.ts`: one startup warning (names only) for unconfigured AI/jobs outside production.
- Env strictness per Saurabh's decision (recorded in `docs/plan-review.md` §7 "Env strictness (T-005)"): app/Supabase core vars, `APP_ENV` and `ENABLED_LANES` are required everywhere; `ANTHROPIC_*` / `INNGEST_*` only when `APP_ENV=production` or `VERCEL_ENV=production`. Connector credentials are checked when the connector is used.
- `apps/web/app/env-check.ts` (imported by the root layout) fails `next build`; `apps/web/instrumentation.ts` validates at server start and emits the warning. The gate runs on `VERCEL=1|true`, `APP_ENV=staging|production` or `NICHOLS_VALIDATE_ENV=1`; CI typecheck/lint/test need no env.
- `apps/web/scripts/check-env-build.mjs` + `pnpm --filter @nichols/web check:env-build`: manual smoke test that a production build with no env fails and names the missing variables (refuses if `.env*` files exist in apps/web; restores `next-env.d.ts`; never prints values or build output).
- `packages/core`: deps `zod`, `server-only`; `allowJs`; vitest alias of `server-only` to a test stub (core tests only).
- `.gitignore`: `*.check-env-backup`. Verified existing ignores: `.env*` (with `.env.example` un-ignored), `.agent/logs/*`, `supabase/**/.temp/`.
- `docs/backlog.md`: T-005 and T-003 set to approved (Saurabh, Oct 24); T-005 acceptance line updated for the strictness decision; T-003 notes from this review; T-005 `status: done`.

## Risks
- Real-data isolation rests on Vercel environment scoping and on protecting the `staging` branch (H-023): any code that reaches `staging` runs with the staging database secret and the production Intuit keys.
- A missing core variable on a deployment fails the build and crashes the server at boot (intended).
- Vercel's "Automatically expose System Environment Variables" must stay on; validation also triggers on `APP_ENV=staging|production` as a backstop.
- `vercel dev` (`VERCEL_ENV=development`) must run with `APP_ENV=local`; `next dev` with `APP_ENV=staging` (a developer machine against staging) needs https URLs and is the only off-Vercel place production Intuit keys are accepted.
- `/PASS|PWD/` and `/(^|_)AUTH(_|$)/` may flag a harmless future `NEXT_PUBLIC_` name; the fix is a deliberate allowlist entry.

## Update Oct 28, 2026: Staging environment and real data
Follows the decision in `docs/plan-review.md` §7 "Staging environment and real data" (merged in from `docs/qbo-decisions`).
- `APP_ENV` gains `preview`. On Vercel, `APP_ENV` must match the deployment:
  - Production → `production`
  - custom environment Staging (`VERCEL_TARGET_ENV=staging`) → `staging`
  - PR Preview → `preview`
  `preview` is rejected anywhere else.
- PR Preview: the Supabase variables are optional (all three or none) through a separate preview schema chosen by `APP_ENV`. `getSupabaseSecretKey()` and the new `requireSupabasePublicEnv()` throw (names only) when there is no database, and startup logs "No database in this preview deployment". The client schema keeps the Supabase pair optional but all-or-none; the server schema and build gate require it everywhere except `preview`.
- Intuit guard: `INTUIT_ENVIRONMENT=production` is refused unless `APP_ENV` is `staging` or `production` (or `VERCEL_ENV=production`). It is checked in the server schema (build and boot) and in `requireConnectorEnv("intuit")`, which derives a new `realData` runtime flag from the real process env.
- The build gate also runs for `APP_ENV=preview`. The Intuit check in `assertBuildEnv` runs before the gate, so a local `next dev` / `next build` / `next start` with production Intuit keys fails at boot too.
- Review fixes (security + code review, Oct 28):
  - On Vercel, `VERCEL_ENV` must be present.
  - `vercel dev` is `local` only.
  - `staging` on Vercel needs `VERCEL_TARGET_ENV=staging`, including for the connector-time check (`isRealDataEnv`).
  - A PR Preview may not hold `SUPABASE_NL_*`.
  - Core suite: 163 tests.
- Review: security review found no BLOCKER or HIGH; code review found no HIGH. Fixed: code review MEDIUM ×2 (local build/boot Intuit guard; staging on `vercel dev`), security LOW ×4 (connector flag target check, `VERCEL_ENV` required on Vercel, NL data plane on Preview, doc drift), plus the H-023 Preview value (`APP_ENV=preview`) in the docs branch. Open, logged in Risks: the guard trusts the `INTUIT_ENVIRONMENT` label and Vercel's environment scoping. Production keys labelled `sandbox`, or staging Supabase values placed in Preview scope, are not detectable by code. Error lists arrive in rounds, because Zod skips the cross-field rules while required variables are missing; the parse still fails.
- Tests: 11 new tests in "real-data environments" cover target-environment matching, preview only on a Vercel Preview, Supabase all-or-none, the Intuit guard (build, boot, connector, caller env cannot switch it), fail-closed accessors and the startup warning. Existing preview fixtures were moved to the new model. Core suite: 157 tests.
