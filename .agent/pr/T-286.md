### T-287: Teams writer and reconciler (connector write side)
- `packages/connectors/src/teams/writer.ts`: `prepareTeamsWrite` (lane/connection brand, provider, action lane + connection + type, approver and action ids, payload hash in constant time, plain-text target and payload schemas, then the Teams guard with the send feature and the approver as the row's required owner; no token read) and `createTeamsMessageWriter` (`executeWrite`, `verifyWrite`, `findWrite`).
- ONE POST per approved action with `retry: false` through the existing write client (its 3 templates). The outcome table: 201 + id -> `accepted` (the executor records the claim and reads back); 400 / 403 / 404 / 413 -> fixed failure sentences (`TEAMS_SEND_FAILURES`; 403: "You are not a member of this chat or channel, or sending is not allowed"); 429 -> `throttled`, not retried; timeout / network / 5xx / an unreadable 201 -> NO retry, a date-range lookup (chat: `$orderby=lastModifiedDateTime desc&$filter=lastModifiedDateTime gt <claim - 2 min>&$top=50`; channel posts and replies: the newest 50 posts or replies) for the person's own message with the same normalised text: one match -> `already_applied`, two -> `ambiguous_match`, none -> `outcome_pending` (the action stays `executing` for the sweep).
- Read-back by id (chat: `GET /chats/{id}/messages/{id}`; channels: found in the newest posts/replies, because no single-message read route is allow-listed): sender = the connection's `entra_object_id`, same chat or channel and reply parent, created after the claim (2 minutes of skew), not deleted, a message (not a system event), and the body converted to plain text and normalised equals the approved text; `text` and `html` are both handled. Logs only `teams.send.read_back_form` with `form` = `text` | `html` | `other`.
- `packages/connectors/src/teams/writer-entry.ts` is the ONE production file that builds `createTeamsWriteClient` and the writer (`teamsMessageWriter`, `teamsMessageReconciler`); the shared guard, token manager and read client were moved to `teams/wiring.ts` (used by `teams/index.ts` and the writer entry only). `@nichols/connectors/write` exports the writer, the reconciler read side (`findWrite` + `verifyWrite`, no `executeWrite`), `loadTeamsWriteConnection`, the schemas and the fixed failure sentences.
- Approvals module (`packages/modules/approvals/src/server`): `teams.ts` (`proposeTeamsAction`, `approveAndExecuteTeams`, `executeApprovedTeams`, `buildTeamsSend`), `reconcile-teams.ts` (`createTeamsReconciler`: find + verify only, registered in `reconcileDeps` of `action.reconcile_stuck`), the Teams facts in `readFacts`, `capabilityOf` for the three types, new error codes `teams_not_enabled` and `request_reused`, `ApproveResult` member `outcome_pending`. `wire.ts` exports `approveAndExecuteTeamsAction` and `executeApprovedTeamsAction` (nothing calls them yet) and the generic `approveAndExecuteAction` REFUSES a Teams action (`invalid`).

## How the ONE-POST guarantee is enforced
1. `act.claim_execution` inserts the claim row (primary key `action_id`): at most one caller ever gets `executing`; every other gets `already_claimed` -> `already_in_progress` without touching Microsoft (pgTAP: second claim refused, exactly one claim row; Vitest: two concurrent `executeApprovedTeams` -> one writer call).
2. The writer checks `core.act_claim_open` (executing, open claim, same hash and approver) before the POST, and refuses an action id this process already posted (Vitest: two concurrent `executeWrite` -> one POST; a second after a failure -> no request).
3. The POST has `retry: false`, no transport retry. The only second attempt in the whole path is the write client's existing refresh after a 401, which Microsoft did not process (T-279).
4. After any unknown outcome nothing is posted again: lookup or `outcome_pending`; the sweep (`TeamsMessageReconciler`) is find + verify only and ends `failed` / `outcome_unknown` at give-up.

## Where the text lives and when it is emptied
Only in `act.proposed_actions.payload.text` while the action is `proposed`, `approved` or `executing` (the sweep needs it for the lookup), and in the one POST body. Not in status history (ids and statuses), claims (message id), audit (ids, type, hash, codes), logs, errors or `result`. Emptied by the guard trigger in the same statement as every terminal transition (verify, fail, reject, expire, invalidate, reconcile, disconnect). Canary tests: writer (logs, audits, api errors, thrown errors for every outcome), approvals module (audit), pgTAP (purge at every terminal state, including the disconnect and reconcile paths).

## Risks and notes
- The `act.approve` rewrite reads the action's type before the step-up check (a definer read of one column; an unknown id gets the standard window and then the same not_found as before).
- `ACTION_TYPES` in lane-config was NOT extended (it maps one to one to the brain module's employee permission table); `approvals.expire_after_hours` therefore cannot be set for Teams through the validated config (the database default of 1 hour applies). Logged in `docs/plan-review.md`.
- The Teams write client's existing one extra attempt after a 401 is the only way two POST requests can leave for one action (the first was not processed).
- A duplicate `action.proposed` audit line is written when the same client request id is proposed twice (the database returns the existing action).
- Channel read-back uses the newest 50 posts/replies (no allow-listed single-message route); a very busy thread can stay `sent_unverified` until the sweep (and end `reconcile_sent_unverified`).
- The Approvals page and the generic approve route are not changed: a Teams row is never listed or approved there until T-288 (the generic entry refuses it).
- `core.act_pending_count` and `core.act_list` are RLS-bound invokers and so show a person only their own Teams actions.
