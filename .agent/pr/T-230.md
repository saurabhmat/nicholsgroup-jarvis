**Part A (speed) is in this PR section. Part B (layout) is a separate later run and is not started.**

## Migration: NO
No SQL. No `.env*` file touched. One new optional server env var: `SERVER_TIMING` (see below); it is not in `.env.example` (that file was left alone on purpose).

## Part A: what changed

### Measure first (Server-Timing)
- `apps/web/lib/server-timing.ts` + `lib/timed.ts`: a request-scoped timing helper. Names and durations only (metric names are fixed literals, sanitised to `[a-z0-9._-]`; never an id, email, token or row). Off in production unless the **server** env var `SERVER_TIMING` is exactly `1` (`serverTimingEnabled` in `@nichols/core/env/server`); always on in `next dev`. No request header or query can switch it on.
- Where it shows up: the **proxy** sets a `Server-Timing` response header (`proxy.auth`, `proxy.lane`). A streaming server component cannot set headers and Next 16 App Router has no trailers, so **page spans** (`guards.session`, `guards.lane`, `guards.lanes`, `guards.role`, `lane.check`, `lane.list`, `load.home`, `load.inbox`, `load.onboarding`, `load.google`, ...) are written as one log line each: `[timing] {"req","name","start","ms","at"}` (`req` is a random per-request group id).
- Cache Components safe: no clock or random value is read before request data (`timed()` awaits `connection()` first; the id and clock are lazy). Found the hard way: an eager `randomUUID()` failed the prerender.
- Measurement spec `apps/web/e2e/perf-measure.spec.ts` (skipped unless `PERF_MEASURE=1`; not in the e2e:brain list) and `E2E_SPECS` override in `scripts/e2e-brain.sh`; `e2e-server.mjs` passes `SERVER_TIMING=1` through.

### Repeated work removed
- `lib/guards.ts`: **one guards object per request and session** (React `cache()` keyed by the auth cookie contents, so a changed cookie, for example after a sign-in action, builds fresh guards). Inside: the session is read and verified **once**; `getLaneClient` per lane, `listLanes`, and `requireRole` per (lane, sorted roles) are memoised (a rejection is memoised too, so every caller in the render gets the same AuthError or outage). Outside a render (route handlers, actions) `cache()` does not memoise: unchanged behaviour.
- `lib/lane-page.ts`: lane check and lane list run together (`allSettled`; the lane check's error wins, as before).
- Settings: one `guards()`, `searchParams` read once, the five independent loaders in `Promise.all`; Google and Composio loaders read the lane's mailbox config alongside their other query.
- Home / Inbox: the header renders as soon as the lane is verified; data sections stream in behind it (Suspense with a card skeleton); on Home the slow setup lookup (banner) has its own boundary.
- Layout and the Get started page run the lane check and the setup lookup together; `loadProgress` reads the snapshot and the completions together.
- `refreshSession` (core auth) now returns the verified session it already had, and the proxy builds its guards from it: **no second cookie read and verification** in the proxy.
- Proxy lane/onboarding 404 verdict is skipped for **script fetches** (`Sec-Fetch-Dest: empty`: client-side navigation and prefetch). See "Not changed" for why this is safe.

### Instant feedback
- `loading.tsx` in `/[laneId]` and every segment below it (re-exports of one neutral `components/page-skeleton.tsx`, `data-testid="page-skeleton"`); the page-level `<Suspense fallback={null}>` wrappers were removed so the boundary is the skeleton. Sidebar and tabs keep `next/link` with the default prefetch (partial prefetch of the static shell and the loading boundary; no per-user data is prefetched: pages are dynamic behind `connection()`; Inbox rows stay `prefetch={false}`).

Reading the numbers honestly:
- **Click to skeleton: ~60 ms (target < 300 ms): met.** Before, the old page stayed on screen until the new one was ready (no feedback).
- **Content ~330-360 ms (target < 1 s): met, but not faster, and that is React, not the server.** React holds a Suspense reveal for about 300 ms after a fallback was committed (its fallback throttle), so with a skeleton at ~60 ms the content cannot appear before ~360 ms even when the data is ready at 106 ms (Calendar). The "before" page had the same floor (`Suspense fallback={null}`). Server work is what "RSC done" shows.
- **Sequential round trips dropped a lot** (Settings 16 to 4, Home 10 to 5, Get started page 22 to ~12 not counting the wizard call, hard loads about halved). On the local stack a query costs 3-10 ms, so this cannot show up as milliseconds there. In fact the **local Settings RSC time got worse (199 to 313 ms)**: ten parallel requests at once make the local PostgREST/Postgres container answer each in 40-60 ms instead of 3-5 ms. With a real round trip of 30-80 ms between Vercel and Supabase, 12 fewer sequential stages are worth roughly 0.4-1 s on Settings (estimate, not measured: no hosted environment was touched). Worth re-measuring on a Preview deployment with `SERVER_TIMING=1`.

## Session verification finding (`getClaims`)
The local stack signs its access tokens with **ES256** (asymmetric; read from the token header in the measurement spec, nothing else printed). `getClaims(token)` therefore verifies **locally** against the cached JWKS (about 10 ms per verification here, no network call per request). If a project still uses the legacy HS256 secret, supabase-js falls back to a network `getUser()` for every verification (about one extra Auth round trip per request, and the proxy and page both paid it). **Needs a human:** confirm the hosted Supabase projects (staging, production) use JWT signing keys (Dashboard, Settings, JWT Keys: "ECC (P-256)" current key, legacy secret only as "previously used/revoked"). Projects created before mid-2025 may still be on HS256. Nothing in the code can safely change that; identity and AAL still come only from the verified claims. This PR removes the second verification in the proxy and the repeated ones in the page, which is what matters most if a project is on HS256.

## Not changed (and why)
- **Proxy lane check is not "passed along" to the page.** The proxy and the page are separate executions; the only channel is a request header, which a client can forge, and a signed header is more machinery than a security fix is worth. Both still check. What changed: the proxy no longer repeats the check for client-side navigations/prefetches. Next strips the `rsc` header and `_rsc` query before the proxy runs, so the proxy uses `Sec-Fetch-Dest: empty` (set by the browser for script fetches; page script cannot change it). A non-browser client without it is checked as before. A client that lies only changes the HTTP status of its own response; the layout and page still verify session, MFA, lane and role. Document loads (typed URL, reload, link to a new tab) keep the real 404 status (H-042 and `zz-lane-shell-http.spec.ts` unchanged).
- **No `getUser()` removal:** there was none; `cookieSessionReader` already verifies with `getClaims(token)`. Nothing weakened.
- **The layout/page waterfall on a hard load** (page content renders after the layout's lane check because the layout awaits before returning `children`) is left alone: fixing it needs the shell to accept promises (client `use()`), which touches the shell Part B restyles. On client navigation the layout does not re-render, so the click path is not affected.
- `loadOnboarding` is still a chain of about six sequential reads (role, brain lanes, lane info, home lane, documents + completions); only `loadProgress` was parallelised. It now runs behind Suspense on Home and does not block the header.
- Global `fetch` call counter used for the round-trip numbers was a throw-away preload (not committed: `nichols/no-external-fetch`). Re-measuring counts the page spans from the log instead.
- No `prefetch={true}` on the menu: that would run every page's database work for every link in view.

## Risks / judgement calls
- `cache()` keyed by auth cookie content: React's cache is per render so nothing is shared between requests or users; the key keeps a mid-request session change from being answered by a stale read. Needs the security review the task asks for.
- Memoised rejections: an AuthError or outage for a lane/role is repeated to every caller in that request (intended).
- `loadLane` now also queries the lane list for a refused lane (result unused; still a 404). The existing "no further reads" test was changed to match; the Google loader keeps its early return when there are no connections.
- `SERVER_TIMING=1` in production publishes only proxy timings in a response header and writes span lines to the server log. Leave it off unless measuring.
