  - Checks, in order: same site (`Sec-Fetch-Site` absent or `same-origin`) -> lane id shape -> AAL2 session in the lane with `own_mail` (owner, admin_technical, viewer) -> the `messages` module is shown -> the person's OWN usable Teams connection (read under RLS; the route takes no connection id) -> strict address (each of the five parameters at most once, no other parameter, `message` and `hosted` match the connector's id format and are not a dot segment, a chat key or team + channel key that decodes to a valid id, never both) -> the connection has `chat_read` (chat) or `channels_read` (channel) -> the connector: guard (owner = signed-in user, lane, tenant, domain, lane feature AND connection feature) -> fixed template -> bytes.

  - Nothing is stored or cached; the route file exports GET only.
- Converter (`packages/connectors/src/teams/message-html.ts`, new `hosted-content.ts`): an `image` node carries `hosted: <id>` ONLY when the `<img src>` is exactly `https://graph.microsoft.com/v1.0/chats/<chat>/messages/<message>/hostedContents/<id>/$value` (or the `teams/<team>/channels/<channel>/messages/<message>/...` form) AND the chat/team/channel/message in it equal those of the message being converted. Previews, replies and unknown shapes stay plain placeholders.

## How each channel state is decided
(`apps/web/lib/teams-messages.ts` `channelsAvailability`, from the connect state; no Microsoft request is made for any state except "ready")
1. Company's `teams.features` lacks `channels_read` -> "Channels are not switched on for this company." (neutral, no button, no error).
2. Company lists it, connection's `teams_channels_read` is false (connected before, or the admin consent was not given when it connected) -> "Reconnect Teams to add channels" + the administrator-approval text + Reconnect button. The old page-level note leaves channels out while the Channels tab is open (no duplicate).
3. Ready: teams are read. A refused team list (403) -> "Channels need your Microsoft administrator's approval" + admin text (no retry button). A refused channel (403) -> "A private channel can be read only by its members". 429 -> "Teams is busy, try again in N seconds". 401 refresh failure -> Reconnect Teams. Others -> "could not read your teams", Try again.
The guard enforces the same at the connector: lane feature AND connection feature, so a token without the channel scopes never reaches a channel endpoint (tested: no token read, no request). Chats are unaffected in every state.

## Decisions made (safe defaults; listed for the caller)
- **Cross-tenant shared channels:** shown as "Shared" with "Open in Teams", NOT read (no workaround attempted, no tenant segment ever sent). A shared channel the person is a direct member of whose host team is not in `joinedTeams` is not listed at all (spec section 2 non-goal).
- **Tabs are always drawn** when the person is connected (the task asks for a neutral "not switched on" state where channels would be; spec section 11 says the Channels tab only when the lane has the feature). Changing it is one line in `messages-page.tsx` (`ConnectedWorkspace`).
- **Only the open team's channels are read per click** (not every team's), so a click is at most 4 requests to four different Microsoft resources.
- **Pictures in channel replies are placeholders** (no reply hosted-content template in the fact sheet; none added).
- **Channel posts are shown as Graph orders them** (thread with the newest activity first, "More posts" for older), not re-sorted.

## Risks
- The `<img src>` shape of a real inline image is NOT in the fact sheet. The parser accepts only the documented `.../hostedContents/{id}/$value` v1.0 address of the same message; a different real shape just stays a placeholder (safe). H-081 must show what a real one looks like.
- Hosted content ids may contain characters outside `[A-Za-z0-9._:=@-]` (the connector's bound; the fact sheet gives no format): such an image stays a placeholder.
- A message with many pictures waits on the 1 request/s per-chat pacing (each picture is its own request; they load lazily).
- `no-store` on every image: each view re-fetches (rule 6: an image in a chat is message content).
- Posts' `$skiptoken` next link is unconfirmed (no "More posts" without it; no log line, by design).
- The 403 on the team list is read as "needs administrator approval"; a tenant policy that blocks the app for another reason would show the same text.
