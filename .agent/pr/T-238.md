# T-238: Sync freshness (Gmail delta schedule, Sync now, Reconnect per connection, sync status line, failure alerts, stale-data line)

Branch `agent/T-238`, from `agent/T-197`. Push and merge the stack before it. Brief verbatim in `.agent/tasks/T-238-brief.md`; decisions in `.agent/notes/T-238.md`. No production changes; production SQL is the gitignored part 18.

## What changed
- **A. Gmail delta on its own schedule.**
  - New Inngest cron `mail-ingest-delta` (`7-59/15`, offset from the calendar tick): one `conn/sync.requested` per usable Gmail mailbox, event id `mail-ingest:<connection>:<slot>`.
  - New optional `streams` on that event (`["mail"]` or `["calendar"]`) reaches the Google runner, so each stream runs once per tick. cal-ingest asks for `["calendar"]`; manual, connect and webhook syncs still run both.
  - After a scheduled mail-only run that wrote at least one message, `briefing/refresh.requested` (one per lane per 15-minute slot) starts `briefing-refresh`. It runs each owner's briefing through the EXISTING run claim (new `core.briefing_claim_refresh` calls the same gates as Home: 3 h stale, one running, 6 a day, 10-minute pause). A refusal never calls the model.
- **B. Sync now** (owner and admin_technical at AAL2): `POST /api/lanes/<lane>/sync-now`, 403 other roles, 404 other lanes, cross-site refused, one per lane per 2 minutes (atomic SQL claim), audited before anything is sent. Buttons on Home (beside the status line) and Settings -> Connections, with a live region and fixed texts.
- **C. Reconnect per Google connection.** Each row has its own Reconnect. The start route binds the connection id into the state; the callback accepts only that row's account, replaces its tokens, sets it active and never creates a second row. A different Google account is refused (`wrong_account`, fixed text, nothing written). Disconnected Google rows are now listed so they can be reconnected.
- **D. Home status line.** "Mail synced 4 min ago · Calendar synced 12 min ago" (oldest last-good sync per stream; Eastern times in the title and accessible name) replaces "Sync issue". A failed stream shows its real error as fixed text per error code, with "N of M mailboxes" when several. Settings -> Coverage shows the same text.
- **E. Failure alerts.** `withFailureTracking` wraps every cron function and scheduled conn.sync runs (per stream) in the Inngest route: Inngest's `onFailure` counts a run that failed after its retries, a completed run resets. The third failure in a row logs one error line (ids and code only) and shows a banner (Home and Settings, owner/admin_technical) until the next success. New table `core.job_failures`.
- **F. Stale-data line.** One deterministic line in the summary card when mail or calendar data (oldest last-good sync of that kind, or never synced) is older than 24 h; one combined line for both; the summary's own age is folded into the same line.

## Risks
- **The local database was reset by mistake while building this** (details in `.agent/notes/T-238.md`): `node scripts/test-db.mjs --help` ignored the unknown flag and reset the local stack. The local Google connections and their tokens are gone; reconnect them in Settings. Nothing else was touched.
- The refresh shares the lane-wide 6-a-day cap with Home, so overnight mail can use up runs (bounded: 3 h staleness, at most 8 candidates a day).
- A mail-only run still clears the connection's single `last_error`, so a calendar error can be cleared by a later mail success; per-stream freshness (cursors) and the per-stream failure counters are not affected.
- Reconnect and Sync now were not exercised against a real Google account.
- Each tracked function registers one extra `<id>-failure` handler in Inngest.
