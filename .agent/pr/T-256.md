## Tests (about 110 new, 7 files in `microsoft/`)
- Token canary: access and refresh tokens (old and new), the client secret and the fake's error text, which echoes the bearer token, are absent from logs, thrown errors (message, JSON, stack), error-log rows, reconnect records, health results and responses; the test first checks that logs were produced, and that no `[redacted]` marker is in them (the harness logger redacts before its sink, so a logged token would show as the marker).
- Lost refresh race (two token managers, both refresh, one rotation stored, loser re-reads), plus `invalid_grant` while a newer set was stored (not reconnect) and an unreadable store (transient).
- 429 storm on one tenant: seven requests, the four slot holders asleep on `Retry-After: 30`, another tenant's mailbox served meanwhile, then the storm ends as `rate_limited`. Synchronisation is on conditions (`vi.waitFor`, fake counters), not on time.
- Refused before any call, each proving zero Vault token reads and zero requests to the fake: tenant removed from `tenant_ids`; `microsoft` removed from `mail.providers` with the block kept; `microsoft: null`; `gcc_high` lane; cloud changed; missing identity; domain or mailbox list changed; unusable status; another provider's or another lane's connection; a path outside `/me`.
- Fresh decision at send time: a call queued behind a full mailbox is refused (no Graph request for it, no token read) when the provider is switched off, or the tenant removed, while it waits; a call asleep on `Retry-After` does not send its retry when the provider is switched off during the sleep; with an unchanged config the retry decides again and goes out.
- Lane `["google","microsoft"]` accepted end to end, with exactly one `mailProviderSettings` read for a call without retries.
- Paths and origins: encoded dot, slash and backslash (any case) refused by the `/me` rule on its own; path parameters with `/`, `\` or `%` refused before anything happens; `https://graph.microsoft.com:8443`, other ports and `http` refused; a `baseUrl` passed through `httpOptions` cannot move the client.
- Error log: our own refusals (bad path, bad parameter, guard refusal) are not recorded; a real answer or a timeout-class failure is.
- Daily health job (real job, real skip, real check): a Microsoft connection whose provider is switched off for the lane, whose block is missing, or whose lane is on `gcc_high` is skipped with no status change (an already degraded row stays degraded), no `last_error`, no alert, no token read and no request; an unreadable config is a retryable failure that changes nothing; a removed tenant is still a real failure (degraded, `forbidden`, alerted); a healthy connection is checked as before.

## Risks
- The OAuth `error` string alone decides `reconnect_required` (V-7); AADSTS codes are not consulted, so an unlisted error string is treated as a normal failure until a person looks.
- A Microsoft connection whose provider is switched off for the lane (or whose lane is on an unsupported cloud) is skipped by the daily health job: nothing is checked, changed or raised, and the job reports the existing "nothing done" outcome (`connection_not_usable`) with a log line `conn.token_health.skipped` giving the reason. A tenant removed from `tenant_ids` is not skipped: it stays a real failure. The skip is an optional per-provider hook of the job; Google and QuickBooks paths are unchanged.
- The guard now decides inside the mailbox slot and again before every later attempt, so a call with retries makes one extra lane-config read and connection read per retry.
- The refresh response's `scope` is stored as received; the token set stays under Vault only.
- 4 in flight and 4 requests/s are our own limits (V-16); lower real Microsoft limits only cause more 429s, which are honoured.
- `loginOriginFor` and the host sets serve `commercial` only: T-267 must add the `gcc_high` hosts and its own app registration.
