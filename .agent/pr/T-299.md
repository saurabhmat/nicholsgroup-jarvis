# T-299: response headers against framing and content sniffing (security finding F-01)

## Why
The security test suite (T-170, `docs/security/pilot-test.md`, finding F-01) found that the app sent no header forbidding other pages to show the portal inside a frame, and no `nosniff`. Approvals are live for the pilot company, and a Teams Send is one click for a signed-in person, so a page able to frame the portal with the session could trick that click. The session cookie is `SameSite=Lax`, which protects against other sites but not against other pages on the same registrable domain.

## What changed
- `apps/web/next.config.ts`: one exported list, `SECURITY_HEADERS`, applied to every path (`/:path*`): `Referrer-Policy: strict-origin-when-cross-origin` (unchanged), `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`.
- `apps/web/lib/teams-api.ts`: the Teams image route's own policy is now `default-src 'none'; sandbox; frame-ancestors 'none'`, so framing is refused whichever policy header a browser honours.
- No script or style policy is added. A full Content-Security-Policy is a separate decision (docs/plan-review.md).
- No SQL, no setting, no dependency.

## Tests
- `apps/web/tests/security-headers.test.ts`: the expected-failure pin for F-01 is replaced by seven passing tests: one rule covers every path with no conditions; Referrer-Policy kept; framing forbidden with both headers; `nosniff`; no header twice and no script or style policy; a route's own policy still forbids framing; no route, page, library file or `proxy.ts` sets a looser framing header. F-02 stays pinned.
- `apps/web/tests/teams-image-route.test.ts`: the image route's policy string.
- Checked: the app has no `<iframe>`, `<frame>`, `<object>` or `<embed>`.
- Run on the final tree: web typecheck, web lint, the web build (the three headers are in the built `routes-manifest.json`), the web tests, the root script tests. See the PR conversation for the numbers.

## Risks
- A page that some other site legitimately embeds would stop working; the portal has none.
- The headers are set by the framework's config rule. That they reach the browser on every kind of response in production (pages, API routes, static files, error pages) has not been seen in a browser.
