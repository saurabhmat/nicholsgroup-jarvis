# T-299: response headers against framing and content sniffing (security finding F-01)

## Why
The security test suite (T-170, `docs/security/pilot-test.md`, finding F-01) found that the app sent no header forbidding other pages to show the portal inside a frame, and no `nosniff`. Approvals are live for the pilot company, and a Teams Send is one click for a signed-in person, so a page able to frame the portal with the session could trick that click. The session cookie is `SameSite=Lax`, which protects against other sites but not against other pages on the same registrable domain.

## What changed
- `apps/web/next.config.ts`: `SECURITY_HEADERS`, applied to every path (`/:path*`): `Referrer-Policy: strict-origin-when-cross-origin` (unchanged), `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`.
- A second, later rule for the Teams image route (`/api/lanes/:laneId/messages/image`): `Content-Security-Policy: default-src 'none'; sandbox; frame-ancestors 'none'` and `Referrer-Policy: no-referrer`, the same values the route sends itself. Reason (found by the security review of the first commit): on the framework's own server a config header replaces a route handler's header of the same name, so the general policy would have dropped the route's stricter one, and the general Referrer-Policy had been dropping its `no-referrer` since T-281.
- `apps/web/lib/teams-api.ts`: the image route's own policy also names `frame-ancestors 'none'`.
- No script or style policy. A full Content-Security-Policy is a separate decision (docs/plan-review.md). No SQL, no setting, no dependency.

## Tests
- `apps/web/tests/security-headers.test.ts` (19 tests, 1 expected failure for the unrelated finding F-02): the rules and their order; twelve sample paths (pages, sign-in, API routes, the webhook and Inngest endpoints, a static file, a trailing slash, a file extension) each get exactly the four headers, matched with Next's own rule compiler; the image route gets its stricter values and the next path does not; the image route's own headers equal the config's for every header both set; every policy the config can send forbids framing; no other file under the web app or the core auth package names a framing, policy or referrer header; the proxy names none.
- Mutations tried by hand, each turned the file red and was reverted: the general rule skipping `/api`; the image rule removed; `sandbox` removed from the image rule; a policy header set in the proxy through a variable.
- `apps/web/tests/teams-image-route.test.ts`: the real image response carries the new policy string.
- The app has no `<iframe>`, `<frame>`, `<object>` or `<embed>` (checked by the author and by the security reviewer).
- Run on the final tree by the lead agent: web typecheck and lint pass; the web build passes and both rules were seen in the built `routes-manifest.json` (seen in a local build, not guarded by a test); the root script tests pass (221 of 221); `pnpm test:security` passes. The full web test run on the first commit: 2,396 passed, 1 failed (`components/reply-drawer.test.tsx`, unrelated, passes alone: a timing flake diagnosed in docs/plan-review.md), 1 expected failure, 3 skipped.

## Review
Security review and code review of the first commit: no BLOCKER or HIGH. MEDIUM (security): the image route's own policy was dropped, fixed as above. MEDIUM (code): the tests did not show that the rule reaches each kind of path and the "nobody loosens it" check had holes; both rewritten. LOW: a header set by the proxy replaces the config's (now forbidden by a test); the trailing-slash redirect carries no headers (accepted).

## Risks
- A page that some other site legitimately embeds would stop working; the portal has none.
- The headers are set by the framework's config rules. That they reach the browser on every kind of response in production has not been seen in a browser.
- How the hosting platform combines a route handler's own header with a configured one of the same name has not been seen. The image route sends the same values on both sides, so the result is right either way; the production check records what arrives.
