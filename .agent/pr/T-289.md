### T-290: the dot, refresh while open
- `GET /api/lanes/<lane>/messages/activity`: database only, the signed-in person's own usable connection, same-site, AAL2 + `own_mail` role, lane, `messages` module gate, 20 requests a minute per person and lane (in memory), `no-store`; answers `{ live, liveUntil, dot, lastNoticeAt }` (a boolean and times: nothing about a chat). No usable connection or notices off is `live: false` with 200. `POST` on the same address is `teams_activity_seen`.
- The dot (`components/messages-dot.tsx`) is a client component in the side menu, the iPhone More tab and the More list (`AppShell` gets an optional `navAccessory` prop). It draws nothing on the server and reads nothing while a page renders: it asks after mount, on a page change and when the tab becomes visible, at most once per 20 s, with no timer, one shared answer.
- `components/messages-live.tsx` (`MessagesLiveProvider`, `ChatListLive`): opening the page calls `teams_activity_seen`; while the tab is visible the provider asks the activity route every 30 s (stops when hidden, resumes with an immediate ask). A move of `last_notice_at` bumps a version once: the chat list is re-read through `GET .../messages/chats` and the open conversation through `GET .../messages/newer?chat=&since=` (the `lastModifiedDateTime gt` date range, `since` = the newest message shown), then `teams_activity_seen` again so the dot clears. Refresh (the conversation's, and a new one on the list) and window focus read at most once a minute (they say "Already up to date. You can refresh again in N seconds."). Without working notices there is no loop and no dot. Nothing is stored in the browser. The loop's comment says it asks OUR database, not Microsoft.
- Settings: the Last sync cell of the person's own Teams row says "Live updates until <time> ET" or "Live updates unavailable" (H-083 step 3), fetched from the same route after the page rendered.

## How requests to Microsoft are bounded (rule 5, the mail pattern, nothing widened)
- A **separate** client, `createTeamsSubscriptionClient` (`teams/subscription-client.ts`), the mirror of `microsoft/subscription-client.ts`: an exact allow-list of three method + path templates (`POST /subscriptions`, `PATCH /subscriptions/{id}`, `DELETE /subscriptions/{id}`), allowed body keys per route (a POST takes `changeType, notificationUrl, lifecycleNotificationUrl, resource, expirationDateTime, clientState` and nothing else, so `includeResourceData` can never be sent), everything else refused before the slot, the guard and any token read; never retried (`retry: false`); a 401 refreshes once. Beyond mail: a POST must have `changeType` exactly `created` and `resource` exactly `users/<uuid>/chats/getAllMessages`. The guard runs with `chat_read` (lane AND connection).
- Built in ONE file, `teams/index.ts` (restricted name in `packages/eslint-plugin/src/config.js`, tests listed one by one); the logic imports it as a TYPE only. `createTeamsHttp` gets a third kind `subscriptions` (the same three routes, method and path paired), requested only by the subscription client.
- The Teams **read** client is still GET only; the Teams **write** client is still three message POST templates and approvals-only; `teams/write-boundary.test.ts` keeps its meaning: it now names the four files that mention a subscription route (`constants.ts`, `http.ts`, `subscription-client.ts`, `subscriptions.ts`) explicitly and asserts the write client names none and the subscription files name no message route, no write template and no write client. `microsoft/subscription-boundary.test.ts` names the Teams copies in the same way; new `teams/subscription-boundary.test.ts` pins who may name the client, the instance and the renewer.
- Called only from `ensure`/`stop` in the renewal job. D-61 (delete at Microsoft on disconnect) is still open: Disconnect marks the rows removed locally and deletes the Vault secret; nothing is sent to Microsoft.

## What the receiver reads and stores
- Reads from a notification: `subscriptionId`, `clientState`, `lifecycleEvent` (and, new, only the presence of the key `encryptedContent`). Never `resource`, `resourceData`, `tenantId`, `changeType` or anything else. The lane and connection come from the stored subscription row.
- Stores: the dedupe receipt in `core.webhook_events` (as for mail: ids and a hash of the bytes) and, through the job, `comms.teams_activity` (our clock and a capped counter). No chat id, message id, sender or text anywhere.

## Risks and decisions for the reviewer
- **Resource string without a leading slash** (`users/<oid>/chats/getAllMessages`), as the acceptance and spec 7.4 write it; Microsoft's page shows `/users/{id}/chats/getAllMessages`. One constant (`teamsSubscriptionResource`); H-083 shows which Microsoft accepts (a 400 shows in `teams.subscription.unsupported` with `status` and `provider_error_code`).
- `unsupported` covers 400, 403, 404, 501 of a create (refused resource, quota, missing permission): no way to tell them apart without Microsoft's text, so the status and short code are logged. A refusal and a too-short lifetime are retried by every scan (twice a day; a too-short one is created and deleted each time).
- The receiver does not read `tenantId` (it never did, for mail either); the subscription id and its clientState are the proof. Hostile "another tenant" tests pin that the stored row alone decides.
- The renewal job's scan lists ALL usable Teams connections (not only lanes with `teams.enabled` + `chat_read`): a paused lane's connection must be visited so its subscription row is stopped locally. `ensure` decides.
- A notice that arrives between the page's server read and its first activity request is absorbed (a few seconds); the next notice or Refresh shows it.
- Rate limits are in memory per process (a serverless instance keeps its own).
- `webhooks/microsoft.ts` doc comment and `lookupMany`: one lookup per served lane is now two store calls (mail/calendar, Teams) inside it.
