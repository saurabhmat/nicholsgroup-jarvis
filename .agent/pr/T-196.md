# T-196: QuickBooks sync and API error log + export

Branch `agent/T-196`, stacked on `agent/T-195`. Brief: `.agent/tasks/T-196-brief.md`. Decisions and reasons: `.agent/notes/T-196.md`.
The backlog status is NOT set to done here.

## What changed
- **Run logging for every QuickBooks job.** conn.sync (initial load, CDC, and the webhook-triggered CDC, which is conn.sync with trigger
  `webhook`) already wrote a `core.sync_runs` row per connection. The report pull and the normalizer did not: they now do (`job` column,
  kind `snapshot`, counts, redacted error). The one-running rule is per (connection, job). A run-log failure never changes a job's result.
- **`core.connector_api_errors`** (migration `20261117100000_connector_api_errors.sql`): lane_id, connection_id, at, provider, endpoint,
  http_status, provider_error_code, provider_message, provider_tid, kind, disposition, retry_after_seconds. RLS: owner and admin_technical
  of the lane at AAL2 read; service role inserts; nobody updates or deletes; database CHECKs refuse `@`, Bearer and 5+ digit runs in the
  message/endpoint. Purge `core.connector_api_errors_purge(lane)`: fixed 90 days, wired into the retention job.
- **One sink** (`packages/connectors/src/error-log`): every Intuit API error after the T-195 error map writes one scrubbed row and one
  redacted log line (same fields). Message = the error map's fixed text, never Intuit's; endpoint = path template. Failures to record are logged
  by code only. **Sentry:** not added (T-041); `ApiErrorTransport` is the seam, the default transport is the redacted logger.
- **Export** `GET /api/lanes/<lane>/connector-errors/export?from=YYYY-MM-DD&to=YYYY-MM-DD&format=csv|json&dataset=errors|runs`: owner or
  admin_technical at AAL2, max 90 days, CSV (formula-injection safe) or JSON, audited (`connector_errors.export`: who, lane, range, format,
  dataset, row count) before the file leaves. `connectorErrorExportUrl()` helper for T-197's button.

## Risks
- A 6-digit Intuit code is allowed in `provider_error_code` and Intuit's opaque `intuit_tid` is stored as is; both are ids, not personal data.
- The export reads with the user's client, keyset-paged on `id`; it stops only on an empty page and refuses above 10,000 rows (413), so a lower PostgREST max-rows only means more round trips.
- sync_runs is not purged (the normalizer cutoff reads it); the error log is, at 90 days.
- Existing tests that read `sync_runs` rows get `job = 'sync'` by default (no behaviour change for them).
