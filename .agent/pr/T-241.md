# T-241: QuickBooks full initial load on connect; normalizer failure reasons

## Why
In production, a manual `conn.sync` of PKG's QuickBooks connection ran **incremental**. It received 2 records (Preferences and CompanyInfo) and loaded no Accounts, Invoices or Bills. The normalizer then failed as `fin.qbo_normalize failed: transient` after 2m35s.

Causes:
- Nothing started a sync when QuickBooks was connected.
- A QuickBooks sync does a full load only when no cursor is stored (`core.sync_cursors`, stream `default`), and that cursor survives disconnect and reconnect.
- The normalizer turned every non-refusal failure into one fixed "transient" text, so the logs could not say why.

## Changes
- **Full load on connect** (`apps/web/lib/connect-follow-up.ts`, `oauth/handlers.ts`, `api/connect/[provider]/callback/route.ts`). After a successful QuickBooks connect or reconnect, the callback:
  - deletes the connection's stored cursor (`core.sync_cursor_reset`, lane-checked);
  - sends `conn/sync.requested` with trigger `connect` (ids only, event id per connection and minute).
  The hook is bounded to 3 s, and a failure never changes the redirect.
- **conn.sync** (`sync/job.ts`, `runners.ts`, `store.ts`, `types.ts`):
  - Trigger `connect` always reloads everything.
  - A scheduled or manual run of a connection that has never completed a full sync also reloads, at most once per 6 h.
  - Webhook runs stay targeted fetches.
  - Failed forced full loads are logged as `kind = full`.
  - Only the cursor runner (QuickBooks) uses this; Google is unchanged.
- **Normalizer reasons** (`quickbooks/normalize-store.ts`, `core/inngest/fin-normalize.ts`):
  - Each failure says why, from the error code only: timeout, network, statement timeout, lock conflict, database connection or resources, a PostgREST code, a SQLSTATE, or "function not found" (no longer retried).
  - The Inngest run output shows the reason, but only for the normalizer's own fixed texts.
  - The timeout is 100 s, under the route's 120 s maxDuration.

## Tests
New unit tests cover:
- sync job: connect, no completed full sync, back-off, webhook stays targeted, unreadable history, Google not asked, failed full logged as full;
- runner: `full` with the compare-and-swap;
- store: history query and cursor reset;
- callback hook: only after success, a failure or hang never changes the redirect;
- connect follow-up: cursor reset first, Google untouched, reset failure still sends;
- normalizer: reasons per code, timeout vs network, no database text;
- run output: safe reason shown, any other message dropped.

`pnpm typecheck`, `pnpm lint` and `pnpm test` pass. No SQL migration.

## Production (gitignored SQL, run by hand)
1. `supabase/core/bootstrap/manual-migrations/check-pkg-qbo-full-sync.sql`: read-only; shows the connection, cursor, run history, raw counts per type, and any running sync.
2. `pkg-qbo-force-full-sync.sql`: deletes only this connection's cursor. It refuses unless this is PKG's usable QuickBooks connection and no sync is running.
3. Send `conn/sync.requested` `{ laneId: "PKG", connectionId: <id>, trigger: "manual" }` in Inngest Cloud. The run should show kind `full`, and the normalizer then starts by itself.

## Risks
- A full load that cannot finish within 120 s is retried at most once per 6 h per connection (the scheduled poll); it does not loop on every tick.
- The normalizer's database statement may keep running after the 100 s timeout; the retry then reports a lock conflict. This is logged in `docs/plan-review.md`.
