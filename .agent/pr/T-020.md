# T-020: Step-up helper

## Changes
- `@nichols/core/auth`: `requireStepUp(maxAgeSeconds)` (30 – 3600): AAL2 plus a TOTP code entered within the window, read from the verified token's `amr` claim (`totpVerifiedAt()`: latest `totp`/`mfa/totp` timestamp; the timestamp-less string form fails closed; a future timestamp beyond 30 s does not count, as in the approvals spec). `AuthError("step_up_required")` (403). `VerifiedSession.mfaVerifiedAt`. `createGuards` takes an injectable clock for tests.
- `/mfa?reauth=1`: an AAL2 user with a factor gets "Confirm it's you" and enters a fresh code (new `amr` timestamp).
- `GET /api/session/step-up?maxAge=…` (default 300): 200 or 403 `step_up_required`; no data. Screens use it before offering sensitive actions; the actions call `requireStepUp()` themselves (approvals, T-119/T-193, with `lane_config.approvals.step_up_max_age_s`).
- e2e helpers remember enrolled secrets per persona for the run (`completeMfa`, `nextTotpWindow`); `step-up.spec.ts`.

## Tests
- Unit: step-up window, missing/old/future timestamps, AAL1/no session first, invalid windows; `totpVerifiedAt` forms (auth suite 42).
- Playwright `step-up.spec.ts` (fresh code passes, 31 s later a 30 s window fails, `/mfa?reauth=1` restores it; 401 signed out): written, browser run pending (Chromium system libraries).

## Review (security, Oct 31, 2026; one HIGH, fixed)
- Checked on the local stack: token refresh keeps the old `amr` TOTP time (only a new verification moves it); email code, recovery, magic link and phone never count; `/mfa?reauth=1` goes through the normal verify path, so the attempt limit applies.
- HIGH (fixed): a stolen AAL2 session could enrol its own authenticator (satisfying step-up) and remove the owner's. Migration `20261031064926_mfa_enrolment_guard.sql`: the MFA hook now accepts a NEW authenticator only as a first enrolment or after an admin-granted, one-time reset (`core.mfa_enrolment_state`, granted in SQL per the runbook), and only while no verified factor exists; refusals are audited (`mfa.enrolment_refused`). In the app, sign-in/step-up codes count only for verified factors and enrolment codes only for the new unverified one. pgTAP (070, +5) and a live GoTrue probe: from an AAL2 session a second factor was created but its correct code was refused with the hook's message, and audited.
- LOW (fixed): clock-skew tolerance 30 s (spec); lockout and refused enrolment show their own messages (`locked`, `refused`) instead of "wrong code".
