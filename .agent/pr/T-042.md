# T-042: Retention purge job

## Summary
A daily Inngest job (`retention-purge-schedule`, 03:00 America/New_York) sends one `retention/purge.requested` per enabled lane. The worker `retention-purge-lane` (one run per lane at a time, 3 retries) calls each registered table's SQL purge function with that lane's retention for the table's class.
- **Where the retention comes from:** comms uses the lane policy (`lane_policies.retention_days`, PKG 90). Calendar, conversations and webhooks come from a new `lane_config.retention` section with these defaults:

  | Class | Default | Allowed range |
  |---|---|---|
  | Calendar | 180 days | 30–180 |
  | Conversations | 180 days | 1–3650 |
  | Webhooks | 30 days | 7–365 |

- **Deletes happen only inside SQL functions.** Each one filters by `lane_id`, refuses a disabled lane, and enforces its own floor and cap, so the TypeScript limits are only a first line of defence.
- **Raw records:** content records holding message bodies are deleted from `raw.source_records` when the lane's `store_content_bodies` is off, or when the lane has no policy row (fails closed). This matches the existing write trigger.
- **Failures stay contained:** one table or lane failing does not stop the others, and logs carry counts only.

## Changes
- **Migration `20261105180000_retention_purge.sql`:**
  - `core.retention_comms_purge` and `core.retention_cal_purge` are SECURITY INVOKER wrappers around the T-061 purge functions. They add a lane-enabled check and require an interval; the T-061 floors and caps still apply.

- **`packages/core/src/inngest/retention-purge.ts`:** the schedule and the worker.
  - The worker re-checks the event and skips lanes this deployment doesn't serve.
  - It runs every table and only then throws if one failed.

- **`packages/connectors/src/retention/`:**

  - `tables.ts`: the default tables are comms, calendar, `core.webhook_events` (through `WebhookStore.purge`) and raw bodies. Conversations have no table yet (T-103) and are reported as an empty class, not an error.
  - `store.ts`, `job.ts`, `index.ts`.
  - `settings.ts`: the policy and `lane_config` are read separately, so a bad config cannot stop the comms purge or the body purge.
- **Wiring:** `vault/index.ts` and `vault/lane-config.ts` (the reader), the `./retention` export, and the `/api/inngest` route.
- **Database files:** `packages/core/src/db/types.ts` regenerated; `tests/050_catalog.test.sql` allow-list entry.

## Risks
- **Bodies never age out.** While `store_content_bodies` is on, bodies in `raw.source_records` are never deleted. `raw.source_records` has no time-based retention at all.
- **Whole rows are deleted.** The body purge deletes the whole raw row, including GoHighLevel rows, rather than redacting the body.
- **Failures are silent.** Nothing alerts when a purge keeps failing (there is no `onFailure` handler), and deletion counts are logged but not audited.
- **Future tables must follow the contract.** When T-103 (conversations) and T-112 (approvals payloads) register their tables, their SQL purge functions must follow the contract in `retention/types.ts`.
