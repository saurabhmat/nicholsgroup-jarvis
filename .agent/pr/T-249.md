# T-249: GovCon news time budget (async Refresh) and no Reply for no-reply / security-alert senders

Follow-ups after T-247 went live (Nov 15, 2026). No SQL change, no production step besides the normal deploy.

## 1. "News could not be fetched: the fetch took too long"

**Cause (from the code; the production Inngest runs were not read from here):** one news fetch is one analysis-tier model call with
up to `news.max_searches` web searches and up to 2 `pause_turn` resumes. That regularly takes 1 to 3 minutes. Our own bounds were
60 s per request plus an 80 s abort (scheduled job, inside a 120 s Inngest route), and 60 s per request plus a 70 s abort (Refresh, inside Home's 90 s).
Hitting either bound is stored as `timed_out`, which the card shows as "the fetch took too long".

**Change:**
- `apps/web/lib/news-types.ts`: `NEWS_CALL_TIMEOUT_MS` 150 s per request (no SDK retry, so nothing is billed twice), `NEWS_FETCH_TIMEOUT_MS` 240 s for the whole
  fetch, and `NEWS_RETRY_BEFORE_MS` 100 s: the one retry after a reply cut off at the output limit may start up to this point.
- Scheduled job (`news-schedule.ts`) uses them; `app/api/inngest/route.ts` `maxDuration` 120 → 300 s.
- **Refresh is asynchronous now** (`app/[laneId]/news-actions.ts`), like the briefing. The action checks the role and the config and reserves
  the attempt in SQL (`core.news_begin_refresh`), so refusals still answer at once. The fetch then runs in `after()` with the
  owner's own lane client, and the action returns `status: "started"`. `app/[laneId]/page.tsx` `maxDuration` 90 → 300 s.
- The card (`components/news-refresh.tsx`) says "Fetching news in the background…". While the server reports a fetch in flight, it
  re-reads the page every 20 s, for 6 minutes at most. The poll only reads; it never starts a fetch.
- SQL unchanged: a pending attempt is closed as lost after 10 minutes, which is well above 240 s. Scheduled retries stay every 30 min, at most 3 a day.

## 2. No Reply on no-reply / security-alert senders
- `isNoReplyAddress` (`packages/modules/briefing/src/domain/sender.ts`) is a fixed rule on the local part. It matches a no-reply, do-not-reply or
  mailer-daemon token as its own segment (for example `no-reply@accounts.google.com`, `accounts-noreply@…`), and `postmaster`, `notification(s)` or `bounce(s)` at the start. No company data.
- `rankAttention` sets `replyable` on each row. It is false for the lane's automated senders, no-reply addresses, security alerts and repeated
  failures. Home shows Reply only when it is true, so an absent flag means no Reply (fail closed). Open stays.
- The server refuses too: `loadMessageRef` (`lib/reply.ts`) throws `no_reply_sender` (409) before any body read. That covers the drawer context, the AI draft and Save.
- The briefing auto-draft guard (`briefing-run.ts`) uses the same function instead of its own regex.

## Review fixes (security + code review, no BLOCKER)
- **HIGH (security):** the background Refresh keeps the owner's access token, and the token could expire inside 240 s. The action now renews the session when fewer than 300 s are left (`renewSessionIfExpiring` in `packages/core/src/auth`, `renewSessionFor` in `lib/guards.ts`). It then refuses (`unavailable`, nothing reserved) unless the verified token (`expiresAt`, from the `exp` claim) lasts 300 s.
- **MEDIUM (security):** a retry that is aborted is counted as the first call plus a reserve floor.
- The poll cap is now 10 min (SQL's lost window), followed by a "Still running. Reload…" note. `isNoReplyAddress` handles `noreply2@` and `Name <address>`. Stale comment fixed. Test for no polling of a scheduled run.
- Logged, not changed: `docs/plan-review.md` "T-249: review results".

- auth: `renewSessionIfExpiring` leaves a fresh token alone, renews a near-expiry one, fails (never throws) without a session or on refusal; the verified session carries `exp`. news action: renews before the guards, refuses short tokens without reserving.

## Risks / needs a human
- **maxDuration 300 s** needs Fluid compute or the Pro plan. The current 120 s already works, which implies one of them. If Vercel rejects 300 at build, use the plan's maximum and keep `NEWS_FETCH_TIMEOUT_MS` about 30 s below it.
- If news still fails after this, read the `[news] news.model_call` / `news.model_failed` log lines (codes and counts only) in
  Vercel for the news-daily run. A `model_busy` or `search_failed` code is a different cause from `timed_out`.
- If Next does not show the renewed session cookie to `guards()` within the same server action, a Refresh pressed in the last 5 minutes of a token's life answers "could not be refreshed, try again" (fail closed); the next request's proxy refresh fixes it. Worth one manual check after deploy.
