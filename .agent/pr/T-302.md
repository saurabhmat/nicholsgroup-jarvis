# T-302: Finance cash report (book balance per bank account by week)

Third of the controller's reports (spec `docs/specs/finance.md` section 15.4), on top of T-300 and T-301. A "Cash" tab, second in the row (Overview,
Cash, Receivables, Invoices & payments), at `/[laneId]/finance/cash`: today's book balance of each bank account and its book balance at the end
(Friday, New York) of each of the last N completed business weeks (N = `lane_config.finance.reports.weeks`), the change from the next older column, a
total row, and an "as of" per column. Every figure is computed in SQL. "Book balance" everywhere (rule 7). No money in and out.

## What changed
- **SQL** `supabase/core/supabase/migrations/20261208100000_finance_cash_report.sql`
  - `fin.bank_balances` (new table; `lane_id`, connection, `fin.accounts` row, date, `book_balance numeric(18,2)`, `as_of timestamptz`; unique per
    connection, account, date; standard finance-view RLS at AAL2; no write for authenticated).
  - `core.fin_bank_balances_put(lane, connection, date, as_of, balances jsonb)` (service_role only, invoker): validates lane, connection, date, item
    shape and that EVERY account is a bank account (`is_bank`, not deleted) of that connection in `fin.accounts` (payroll accounts are never there);
    one call writes one date, removes that date's other rows, removes rows older than 26 weeks.
  - `core.fin_bank_account_ids(lane, connection)` (service_role only): the ids the job may ask about.
  - `core.finance_cash(lane, weeks default null)` (invoker, stable, empty search_path): same gate and states as the other tabs.
- **Connector** `packages/connectors/src/quickbooks/bank-balances.ts` (+ `bank-balance-store.ts`): one Balance Sheet request per week end; the strict
  projection returns only `{ accountId, balance }` for the asked ids (see "Risks"). The nightly reports job (`reports-job.ts`) runs it after the
  report fetches; switch `finance.reports.cash_history` (default true). **`balance_sheet` is not a cached report kind and nothing of a Balance Sheet
  is stored in `fin.report_cache`: D-27 is unchanged.**
- **Web** `apps/web/lib/finance-reports.ts` (mapper, loader, wording, the tab), `components/finance-cash.tsx`, `app/[laneId]/finance/cash/{page,loading,error}.tsx`.
- **Config** `finance.reports.cash_history` (boolean, default true) in `packages/core/src/lane-config/index.ts`; `packages/core/src/db/types.ts` regenerated.
- **Tests updated (not weakened):** tab tests (Cash second), `050`, `335` (pins the new table: 40+7=47), `336` (98 callable functions, 80 lane
  functions), `339` (fin writers list), lane-config defaults, the reports test for default settings.
- Production SQL (gitignored): `supabase/core/bootstrap/manual-migrations/part-39-T-302.sql` and `part-39-T-302-check.sql`.

## Risks (for the security and code review)
1. **What of the Balance Sheet is kept.** Only `{ account id, balance }` of bank accounts in the asked set. The projection never returns a label,
   section, total, header, column or other account; errors have constant messages; logs carry counts and dates only (tested). The database writer
   accepts only objects with exactly `account_id` (digits) and `book_balance` (a figure string), and refuses any id that is not a bank account of the
   connection. The security review is asked to confirm that bank-account balances alone reveal no payroll figure (a bank account used only for payroll
   is flagged by the payroll classification and removed from the asked set; see the notes for the aggregate-exposure question and for excluded people).
2. **Own balance vs totals.** An account is kept only when it is on exactly one Data row and on no header/summary (parents with sub-accounts are not
   read). Unverified against Intuit.
3. **Delete in the writer.** It deletes (with WHERE) the date's other rows and expired rows; `service_role` therefore has DELETE on this one table.
4. **Wording.** "Book balance" in headings, field names (`book_balance`) and notes; the strings "bank balance" appear nowhere in the UI.
5. **Retry cost.** A failed cash date makes the run fail and be retried, which repeats the report fetches (bounded by the existing 3 retries).
