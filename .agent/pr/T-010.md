# T-010: Lanes and lane policies

Approved by Saurabh, Oct 31, 2026 (built on the combined branch `agent/pilot-build`; split into its own PR later).

## Changes
- Migration `supabase/core/supabase/migrations/20261031041722_lanes_and_lane_policies.sql`:
  - schema `core` (usage for `authenticated` and `service_role` only).
  - `core.lanes` (`id` uuid = the `lane_id` other tables reference, `code` `^[A-Z]{1,8}$` unique, `name`, `data_plane` core|nl, `enabled` default false, timestamps).
  - `core.lane_policies` (one row per lane, FK `on delete restrict`): `llm_allowed_categories`, `store_content_bodies`, `store_outbound_drafts` (default false; D-19), `indexing_enabled`, `retention_days` (1–3650, default 30), `cross_lane_summary_allowed` none|status|summary, `write_actions_allowed`. Category and write-class lists are check-constrained; every default is the most restrictive value.
  - RLS on both tables: select only, `authenticated`, `aal = aal2` and the lane in `core.allowed_lanes(auth.uid(), '<view>')` (architecture §5.4 pattern; views `lanes`, `lane_policies`). No DML for `anon`/`authenticated`; `service_role` has DML.
  - `core.allowed_lanes(uid, view)`: **placeholder that returns no lanes** (fail closed). T-012 replaces it with `create or replace` (same signature) reading `core.memberships`. Until then no user can read lanes or policies through RLS.
  - `core.set_updated_at()` trigger; both functions pin `search_path = ''`.
- Seed: `supabase/core/seed/sections/lanes.mjs` (registered after `auth-personas`): six lanes from `ctx.data.lanes` with their deterministic ids, only PKG enabled; policies per architecture §5.3 for PKG and NL, defaults for APK, PKI, NC, P. `seed.sql` regenerated.
- `supabase/core/supabase/tests/020_lanes.test.sql` (34 pgTAP tests).

## Decisions
- **Lane key:** uuid `id`, with `code` as the natural key (the seed framework already derives a stable id per lane).
- **Circular dependency:** T-010 needs `allowed_lanes()` for its RLS, and T-012 (memberships) depends on T-010. Resolved with the fail-closed placeholder above rather than reordering tasks.
- **`cross_lane_summary_allowed`** is a three-value text (none / status / summary) instead of a boolean, to express NL's "status-level only".

## Tests
- pgTAP (`pnpm test:db`, 3 files, 47 tests; `020_lanes` has 34): tables and RLS exist; functions pin search_path; six lanes, only PKG enabled, NL on the nl plane; every lane has a policy; only PKG stores outbound drafts; column default false; a new lane/policy gets the restrictive defaults; check constraints (data plane, code, NL stays on the nl plane, LLM category, write class); FK restrict; updated_at trigger; anon cannot execute `allowed_lanes` or read policies; authenticated has no DML; with the placeholder nobody reads anything; with a stand-in membership for the owner in PKG only (in-transaction, rolled back) the owner at AAL2 reads only PKG and no other lane's policy, and an outsider at AAL2 reads nothing; AAL1 and missing-aal sessions are denied.
- `node --test supabase/core/seed/*.test.mjs` (58), `db:seed:check` ok, eslint ok. `pnpm db:types`: no change (types cover the `public` schema only).

## Review (security, Oct 31, 2026; no BLOCKER or HIGH)
- M1 (fixed): the stand-in membership answered every caller, so a policy passing the wrong uid or view would still pass. The stand-in now answers only for the owner persona and the two view names, and an outsider at AAL2 is tested (reads nothing).
- M2 (recorded in T-012): `allowed_lanes(p_uid, …)` accepts any uid; once T-012 makes it security definer it must return nothing unless `p_uid = auth.uid()` (or service_role) and the session is aal2.
- L1 (fixed): `anon` explicitly revoked from the schema and both functions; `authenticated` revoked from the trigger function.
- L2 (recorded in T-012): disabled lanes are readable by their members in SQL; the lane router (T-016) rejects them, T-012 decides whether `allowed_lanes` excludes them.
- L3 (fixed): the policies evaluate `allowed_lanes` once per statement (`(select …)::uuid[]`).
- L4 (fixed): check constraint keeps NL on the nl data plane (tested).
- Checked and fine: grants and default privileges, RLS not forced (only bypass roles own or bypass), AAL check fails closed, invoker functions with pinned search_path, check constraints reject nulls, seed is synthetic, `core` not exposed to the API.

## Risks
- `core` is not in the PostgREST exposed schemas (`config.toml` `[api] schemas`), and `pnpm db:types` only types `public`. T-016 (lane router) must decide how server code reaches `core` (expose it to the API, or use RPC/views) and extend type generation.
- Production lane rows: migrations hold no data, and the seed runs locally only. Production needs the six lanes and their policies inserted once (see Needs human).
