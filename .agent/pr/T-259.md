# T-259: Microsoft: live body, search and header flags

`docs/specs/microsoft.md` §8.3, §8.4, §17 (test 16). TypeScript only: no SQL, no migration, no pgTAP change, no new dependency, no allow-list entry, no `eslint-disable`.

## Summary
`MailProvider<"microsoft">` now has a live `readBody`, a `search`, and header-derived flags on the mail sync. The facade's Microsoft entry answers `readBody` and `search` for real (owner check and provider gate first, then the T-256 guard); `prepareWrite` and the calendar sync still answer `unsupported_op`. Google behaviour is unchanged.
- `readBody`: `GET /me/messages/{id}?$select=body` with `Prefer: IdType="ImmutableId", outlook.body-content-type="text"`; the type is read from `body.contentType` in the ANSWER; HTML is converted by the same function the Gmail reader uses; cut at `maxChars` (default 200,000, as Gmail); returned in an `UntrustedBody`, freshness `live`; never persisted, logged or put in an error.
- `search`: the caller's text is reduced to plain words (letters of any script and marks, digits, spaces, `@ . _ -`; everything else becomes a space; stand-alone `AND`, `OR`, `NOT`, `NEAR` lower-cased; NFKC first), then sent as `$search="<words>"` (percent-encoded) with the T-258 index `$select` and a `$top`, no `$filter`, no `$orderby`. Results go through the T-258 strict mapper: metadata only, `folder` null (the select has no folder, so none is guessed).
- Header flags: for the INBOX messages of a sync page, one `GET /me/messages/{id}?$select=internetMessageHeaders` each, classified by the existing `mail-flags` rules; only the five booleans are kept.
- `is_auth_pass` is false for every Microsoft message. `is_calendar` is also true for an item whose `@odata.type` is `#microsoft.graph.eventMessage`.

## Bounds chosen
- Header reads, per page: as many as the page has messages (the page size, passed in by the sync, so the two cannot drift). A first load flags the whole page.
- Header reads, per connection (the real bound): at most **1,000 per rolling 10 minutes**, kept in memory per lane and connection (`HEADER_READS_PER_WINDOW`, clock injected). Newest messages first, 4 in flight (the Graph client's own per-mailbox cap). When the table of tracked connections (1,000) is full and nothing has expired, no reads are granted. Reads granted but never started (after a stop or the deadline) are given back to the budget.
- Header reads, in time: each read has an 8 s timeout and no retries of its own (the guard still runs before the attempt, the slot and the rate bucket still apply, a 401 still refreshes the token once); a page has a 20 s deadline (the provider's clock) after which the remaining reads are skipped exactly like a stop. Both are provider options.
- What remains, in plain words: on a first load of an inbox with more recent messages than the window allows, the messages beyond the budget are indexed without flags (bulk mail among them is shown in Home and the briefing) until they change. A bounded backfill of unflagged inbox rows is work for T-260.
- A message over a bound, or skipped, is indexed WITHOUT flags: false on a first insert, the stored flags kept on an update (the page writer keeps an absent flag); nothing is guessed. It is read again when it next appears in a delta page.
- A delta page cannot tell a new message from a changed one, and the provider cannot see the index (no SQL allowed), so the candidates are all inbox messages of the page; a re-read for a changed message gives the same booleans.
- A failed single read: 404, an unusable answer, or any other `provider_error` for ONE message skips that message and the rest go on; any other Graph answer (429, 5xx, 401, 403, a timeout) skips that message and stops the remaining reads of the page; the page is still applied. A refusal of ours (reconnect required, provider disabled, lane mismatch, `unsupported_op`, and `forbidden` or `invalid_input` without an HTTP status) is rethrown and fails the page; the cursor does not advance. The checks that can refuse a page (repeated link, link length, link validation, cursor size) run BEFORE the header reads, so a refused page makes none.
- Search: the words are cut at 200 code points on a word boundary BEFORE the operator words are lower-cased (`AND OR NOT NEAR ONEAR XRANK WORDS`); default-ignorable code points are removed first, and leading `-` and `+` are stripped from each word. At most 100 results.
- Body: default `maxChars` 200,000 (as Gmail); markup is cut at four times `maxChars` before conversion.

## Risks
- **Priority senders in a Microsoft mailbox rank one tier lower than in Gmail** until `is_auth_pass` can be trusted (it is false for every Microsoft message). The other flags (`is_bulk`, `is_auto`, `is_generated`, `is_calendar`) work.

A bounded backfill of unflagged inbox rows is work for T-260.
- The header-read budget is in memory, per instance; another instance has its own window. The per-read timeout, the page deadline and the window still bound each instance.
- The fake is built from the documentation as read by the calling session; real behaviour is unverified (see Needs human).
- **For T-260:** a search result has `folder` null and no `SENT` label (the index `$select` has no folder, so none is guessed). Callers must not read a null folder as "not in the inbox".
- The T-258 harness default is `headerFlags: false` so T-258's request-count tests stay unedited; production uses the default bounds (on), and the contract suite and the T-259 tests turn it on. The sync behaviours with header reads ON are covered by the "same state as with them off" tests.
