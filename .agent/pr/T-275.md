# T-275: a wrong redirect-address setting sends the person back to Settings instead of bare JSON

## Why
In production PKG, "Connect another Google account" answered `{"error": "unavailable"}`. The log line Saurabh pasted names the cause:
`[api/connect/start] unavailable: ConnectorError { kind: "connection_unavailable", message: "GOOGLE_REDIRECT_URI must end with /api/connect/google/callback" }`.
The production variable `GOOGLE_REDIRECT_URI` is wrong, so no Google connect can start (first or second account alike). The fix for that is the variable itself (backlog H-076, Saurabh). This PR only changes what the person sees in that situation.

## Changes
- `packages/connectors/src/oauth/handlers.ts`: when a provider refuses its own redirect-address setting (`<NAME>_REDIRECT_URI must end with <callback path>`; Google, QuickBooks, Microsoft), a person's Connect click (form post, valid lane code) is sent back to `/<LANE>/settings?error=<fixed code>`, the same banner a missing variable already gets ("Google isn't configured on this server. Check GOOGLE_REDIRECT_URI and NEXT_PUBLIC_APP_URL ..."). Scripts and any other lane value keep the JSON 503. The log line is unchanged. The two redirects share one helper (`notConfigured`), which looks the code up by own key only.
- `docs/backlog.md`: T-274 done; T-275 and T-276 added with Saurabh's words; H-075 answered (the log line); H-076 (correct the variable, steps).

## Tests
- `packages/connectors/src/oauth/handlers-env.test.ts`: the form post is redirected with the fixed code and still logged; another provider gets the generic code; a script caller and a lane that is not a lane code keep the 503; another `connection_unavailable` error (an outage) keeps the 503; the errors thrown by the real `assertRedirectUri` of Google, QuickBooks and Microsoft are recognised.
