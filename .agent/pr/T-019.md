# T-019: Enforced MFA (AAL2)

## Changes
- `@nichols/core/auth` (`src/auth/mfa.ts`, `src/auth/client.ts`): `mfaActions(cookies)` with `status()` (current AAL, verified TOTP factor), `beginTotpEnrollment()` (removes unfinished enrolments; refuses when a verified factor exists; QR returned as a validated `data:image/svg+xml` URI plus the secret for manual entry) and `verifyTotp(factorId, code)` (own factors only, 6 digits; session becomes AAL2). The auth-only client moved to `client.ts`.
- `apps/web`:
  - `/mfa`: enrolment on first sign-in, started with a "Set up authenticator" button (POST, `EnrollForm` with `useActionState`; a wrong code keeps the same QR code and key), then the authenticator code at every sign-in; sign-out; keeps the return path; rendered per request (`connection()`).
  - `proxy.ts`: AAL1 (email code only) page requests go to `/mfa`.
  - Home requires AAL2 (`requireSession()`); data routes already required AAL2 (T-017), and RLS requires it in the database (T-010 – T-014).
- `docs/runbooks/mfa-recovery.md`: lost-phone procedure (verify by another channel, remove the factor and sign the user out in the dashboard, `audit.log('…', 'mfa.factor_reset', …)`, re-enrol).
- Short sessions: 15-minute access tokens (T-017 review; H-026 for production).
- Playwright: `e2e/mfa.spec.ts` (enrol with a wrong then a right code, lane API 200 at AAL2, sign out, second sign-in shows only the code step and honours the return path; an outsider at AAL2 gets 403; unserved or malformed lanes 403), `e2e/totp.ts` (RFC 6238), per-project personas (`e2e/personas.ts`), global setup resets the local database (`scripts/e2e-reset.mjs`). `sign-in.spec.ts` now ends at the two-factor step and checks that AAL1 gets 403 `mfa_required` from lane APIs and is sent to `/mfa` by pages.

## Tests
- Unit: `mfa.test.ts` (10, incl. QR normalisation refusing non-SVG URIs), auth suite 36 in total. Full typecheck, lint, test and `test:db` pass.
- Against the live local stack (probe): email code → AAL1 session → TOTP enrolment (Supabase returns the QR as a data URI, which the code now handles) → a wrong TOTP refused, a computed TOTP accepted → AAL2. A second enrolment for an enrolled user is refused by Supabase below AAL2.

## Review (security, Oct 31, 2026; one HIGH, fixed)
- H1 (fixed): nothing limited wrong TOTP guesses, and an AAL1 attacker can call Supabase's MFA API directly. New migration `20261031063029_mfa_attempt_guard.sql`: Auth hook `core.mfa_verification_attempt` (security definer, supabase_auth_admin only) records failures in the private `core.mfa_verification_attempts` and rejects every attempt after 5 failures in 15 minutes (even a correct code); audits `mfa.lockout` once per window in each of the user's lanes. Registered in `config.toml`. pgTAP `070_mfa_guard` (14); live probe through GoTrue: after 5 wrong codes the hook's message came back and a correct code was refused; audit shows the lockout. Catalog test: reviewed `private_table_ok` list (RLS on, no policy, no API grants) and the hook on `security_definer_ok`.
- M1 (fixed): first successful verification of a new factor is audited (`mfa.factor_enrolled`, in the hook); Supabase security emails for factor added/removed enabled locally (H-028 for production); runbook: reset only while on the phone and confirm the new factor.
- M2 (fixed): enrolment no longer happens on GET; unfinished enrolments are removed only after 10 minutes; a wrong code keeps the QR code (e2e checks the key stays the same).
- L1 (fixed): runbook ends sessions in SQL (`auth.sessions`), calls back on a number on file. L2 (fixed): `connection()` on `/mfa`. L3 (recorded): every future data server action guards itself (plan-review §7).

## Verification review (Oct 31, 2026)
