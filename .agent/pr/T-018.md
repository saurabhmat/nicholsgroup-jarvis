# T-018: Sign-in

## Changes
- `@nichols/core/auth` additions:
  - `authActions(cookies)`: `sendSignInCode` (never creates users; unknown addresses and rate limits look like success, so the app's form does not reveal accounts (Supabase's public endpoint still can; see Review M1); malformed addresses refused; outages throw), `verifySignInCode` (6-digit email OTP), `verifyEmailLink` (token hash, secondary flow), `signOut` (this device).
  - `refreshSession(cookies)` for the proxy; `safeNextPath()` (same-origin paths only; refuses `//host`, backslashes, whitespace, schemes).
  - `CookieStore` now takes `setAll` (batch writes, as @supabase/ssr does).
- `apps/web`:
  - `proxy.ts` (Next 16): refreshes the session cookie on every matched request; signed-out page requests go to `/sign-in?next=…`; API routes are not redirected (their guards answer 401/403); static assets excluded.
  - `/sign-in` (email), `/sign-in/verify` (6-digit code; `inputMode=numeric`, `autocomplete=one-time-code`), `/auth/confirm` (email link), sign-out server action. The address between the two steps lives in a 10-minute httpOnly cookie scoped to `/sign-in`, never in the URL.
  - Placeholder home (signed-in check, sign-out) until the app shell (T-023, after D-20). Pages use the UI kit on provisional tokens; restyled with the signed-off designs.
  - Next 16 Cache Components: no `dynamic` route config; pages that read cookies/search params render inside `<Suspense>`.
- `packages/ui`: `Input`, `Label` (shadcn, provisional tokens) + test.
- Local Supabase: sign-in email template with the code first and the link second (`supabase/templates/magic_link.html`); the email provider switch (`[auth.email] enable_signup`) turned on (it was off, which disabled email sign-in entirely); sign-ups stay off (`[auth] enable_signup = false`, `shouldCreateUser: false`). `scripts/supabase-config.test.mjs` pins all of it.
- Playwright: `apps/web/playwright.config.ts` (desktop + iPhone viewport), `scripts/e2e-server.mjs` (starts `next dev` on :3100 against the local stack; keys passed in-process, never printed or written; refuses non-local URLs and `.env*` files), `e2e/sign-in.spec.ts` (9 tests: redirects with a safe return path, 401 JSON for APIs, code sign-in and sign-out, return to the requested page, wrong code, unknown address gets no email, email link, forged link, AAL1 session refused by lane APIs with `mfa_required`). Root `pnpm test:e2e`.

## Review (security, Oct 31, 2026; no BLOCKER or HIGH)
- M1 (accepted, recorded in plan-review §7): Supabase's public `/otp` endpoint reveals whether an address has an account; production CAPTCHA (H-027) closes it. The app's own form answers the same either way.
- M2 (fixed in the app, rest to production): 5 wrong codes per emailed code, then a new code is required (`signin_pending` carries the count). Supabase's own limits are per IP and do not cancel a code; CAPTCHA (H-027) and a rate-limit review for server-originated traffic (T-021). Mandatory TOTP (T-019) limits what a guessed code gives.
- M3 (fixed): session cookies are httpOnly, SameSite=Lax and Secure outside local (`SESSION_COOKIE_OPTIONS`, tested).
- L1 (fixed): `safeNextPath` normalises with `URL` (dot segments resolved; `/..//evil` → "/") and rejects control characters (tests).
- L2 (fixed): @supabase/ssr's cache headers reach the proxy response and redirects.
- L3 (fixed): matcher exclusions anchored; the proxy is documented as not the auth gate (every page and route calls the guards).
- L4 (accepted): email links sign in on GET (scanners may consume them); the code is the primary flow.
- L5 (fixed): the e2e server passes an allowlisted environment only. L6: the e2e link test already rewrites the host.
- Checked: no new users can sign up (`/signup`, `/otp create_user`, anonymous, phone all refused); public-path matching; cookie propagation on redirect; server-action CSRF (cross-origin refused); `/auth/confirm` single-use tokens and fixed type; template escaping.
