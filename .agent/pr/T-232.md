## What was built
**SQL (schema `act`, reached through `core.act_*` wrappers because `act` is not an exposed schema, like Brain)**
- `act.proposed_actions` (spec §4 subset), `act.status_history` (insert-only), `act.execution_claims` (PK = action id: a second claim violates it). Deny-list check on the type (second layer). `lane_id` + RLS + cross-lane tests on all three.
- Trigger-enforced state machine and immutability (payload/target/hash/connection/type never change except the D-19 purge shape; terminal rows frozen; every illegal transition raises; no deletes). **D-19: entering any terminal state removes `payload.bodyText`, rationale and source refs in the same statement.**
- `act.propose` / `act.supersede` / `claim_execution` / `claim_sent` / `mark_verified` / `mark_failed` / `expire_stale`: service_role only. `act.approve` / `act.reject`: authenticated. `act.approve` checks AAL2, **TOTP step-up from the JWT `amr` claim** within `lane_config.approvals.step_up_max_age_s`, owner role, hash seen = stored hash, not expired, `approvals_live`, `write_actions_allowed` has the type, the connection's `features.gmail_compose`. `claim_execution` re-checks all of it plus the approver still being an owner.
- `act.propose` refuses `email.*` unless `lane_policies.store_outbound_drafts` (D-19), a connection of another lane, more than 20 pending in a lane.
- RLS select: owner (approvals view) sees the lane; a proposer who is a lane member sees their own; nobody else; AAL1 nothing.
- Wrappers `core.act_list`, `act_get`, `act_pending_count` (invoker, RLS applies).

**Connectors**
- `packages/connectors/src/google/email-writer.ts` (+ `mime-build.ts`): approvals-only `ConnectorWriter` for `email.send` / `email.save_draft`. Checks before any request: lane/connection brand, provider, action lane+connection, approver, constant-time payload hash, authoritative connection row (status, **`features.gmail_compose`**), lane mailbox list, target mailbox = connection mailbox, payload schema, `fromMailbox` = mailbox. Idempotency: Message-ID `<portal-{actionId}@{mailbox domain}>` + `X-Portal-Action-Id`; `rfc822msgid:` lookup before sending (hit = no send); POST never auto-retried; after an ambiguous failure one more lookup, then `OUTCOME_UNKNOWN_MESSAGE` (never a blind resend). Replies: `threadId` + In-Reply-To/References (parent's Message-ID read live; thread must match). `verifyWrite` reads the message back: label SENT/DRAFT, thread, Message-ID (or the marker header), To, Cc, Subject.
- `google/api.ts` is still GET-only (its test passes); the two POSTs live only in the writer. Exported only via `@nichols/connectors/write` (`googleEmailWriter`, `loadGoogleWriteConnection`, constants). New boundary test `email-writer-boundary.test.ts`; the existing write-subpath boundary tests still pass.
- Scope behind the flag: `GMAIL_COMPOSE` constant; `OAuthProvider.scopesFor(lane)`; the Google provider asks for `gmail.compose` **only** when `core.lane_policies.write_actions_allowed` has `email_send` or `email_draft` (new `vault/write-policy.ts`, fail closed). The callback accepts it only then (otherwise `forbidden`, any other write scope still refused) and **always** records `features.gmail_compose` true/false on the connection (a reconnect without it clears an earlier true). `GOOGLE_SCOPES` and the default consent URL are unchanged (PKG today: the read-only connect). Existing "never a write scope" assertions are unchanged and still hold for the default; both modes are in `connect-compose.test.ts`.

**Approvals module** (`@nichols/approvals/server`, wiring in `@nichols/approvals/wire`): see the interface below.

**Web**: `/[laneId]/approvals` (pending cards + recent history), `POST /api/lanes/[laneId]/approvals` (`save` | `approve` | `reject`), `ApprovalsWaiting` Home component in its own file (+ 4 lines in `home-page.tsx`: one import, one Suspense), `apps/web` gained deps `@nichols/approvals` and `zod`, `next.config.ts` transpiles `@nichols/approvals`.
- Card: "Sends as <address>" always, to/cc/bcc/subject/plain-text body editable, Save changes (= new proposal), "Approve & send" or "Save as Gmail draft", Reject (reason), short hash, expiry, derived-from-email banner, assistant note labelled unverified. Reconnect Google with send permission in Settings` ("Settings" links to `/${laneId}/settings#connections`) when the scope or the policy type is missing, with `Approvals are not live for this company yet.` when only the gate is off, and while there are unsaved edits. ## Public interface for T-231d (the briefing job)
```ts
import { proposeEmailAction } from "@nichols/approvals/server";
import { approvalsDeps } from "@nichols/approvals/wire";

const { id, hash } = await proposeEmailAction(approvalsDeps, laneId, {
  actionType: "email.send",            // or "email.save_draft"
  connectionId,                        // the lane's Google connection (uuid); the sender is ALWAYS its mailbox
  compose: { to: ["dana@..."], subject, bodyText, inReplyTo: { threadId, messageId } /* optional */, cc?: [], bcc?: [] },
  rationale: "Dana asked for the Q3 numbers", // optional, <= 2000 chars, shown as "not verified"
  sourceRefs: [{ kind: "message", id }],        // optional, <= 20, ids only
  proposerKind: "job",
  proposerUserId: ownerUserId,         // the owner the briefing is for (they see it as their own)
  derivedFromRetrieved: true,          // recipient/thread came from email: the UI shows the banner
});
```
- Never sends: it only stores a proposal (service role through `core.act_propose`). Throws `ApprovalsError` with a fixed `code` (`drafts_not_allowed`, `sender_mismatch`, `too_many_pending`, `invalid`, ...), never row text.
- Also exported: `editEmailProposal`, `approveAndExecute`, `rejectAction`, `executeApproved`, `listApprovals`, `pendingApprovalCount`, `emailWriteCapability(deps, laneId, connectionId)`, `capabilityOf`, `ApprovalsError`, `NOT_ENABLED_MESSAGE`, `NOT_LIVE_MESSAGE`, `hashOfRow`. A job must run where `getLaneJobClient` and the connector env are available (Inngest function); the `approvals` package is the only allowed caller of the job client and the write subpath (lint rule).
- A proposal while `store_outbound_drafts` is false is refused by the database (D-19). Proposing does NOT need `write_actions_allowed` (so proposals can be reviewed before sending is switched on); approving does.

## Risks
- **SQL unexecuted.** Written carefully (and desk-checked against `050_catalog` rules), but expect small first-run fixes in the migration or pgTAP file. Most likely spots: the `plan(83)` count, the 050 catalog lists, a throws_ok SQLSTATE, `alter table ... disable trigger` in the expiry test (needs the table owner, which `postgres` is).
- **Gmail may rewrite the Message-ID** of an API-sent message. The lookup then cannot find a resend candidate and verification falls back to the `X-Portal-Action-Id` header; the "never twice" guarantee after a crash relies on the Message-ID lookup. Verify on the first live send (see Needs human).
- **Executes inline in the approve request** (route `maxDuration` 60), not through an Inngest `action/approved` event. A crash between the send and `mark_verified` leaves the action `executing` (claim row says `sent` when `claim_sent` ran). No `action.reconcile_stuck` (T-192) yet, so such a row needs a manual look (verify-only path is designed, not built).
- `gmail.compose` is a restricted Gmail scope: for an external consent screen Google may require verification. If the company's Workspace app is "Internal" none is needed.
- Retrieved content never approves: nothing in this task reads or acts on email text; `derivedFromRetrieved` is stored and shown.
- `executeApproved` writes the `action.execute_started` audit row first; if auditing is down after an approve the action stays `approved` (not sent) until it expires.
