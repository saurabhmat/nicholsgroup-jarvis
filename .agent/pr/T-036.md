# T-036: Webhook receiver framework

## Summary
One shared pipeline for provider webhooks (QuickBooks, Stripe, Gmail push, monday). Providers plug in with a `WebhookProvider` entry; the pipeline owns method, size, content type, signature, replay window, dedupe, lane resolution and the hand-off to Inngest. Nothing is processed inline, nothing is written to an external system, and no payload is stored or forwarded.

No real provider verifier ships. The generic `hmacSha256Verifier` (hex or base64, optional prefix, optional signed timestamp) is complete and fully tested; Intuit's scheme (base64 HMAC-SHA256 of the body, header `intuit-signature`, no timestamp) is exactly that configuration, so T-053 can use it as is. Stripe's `t=...,v1=...` grammar needs its own `WebhookVerifier` in T-058. The registry (`WEBHOOK_PROVIDERS`) is empty, so every `/api/webhooks/<x>` answers 404 until a provider task registers itself.

## Design
```
POST /api/webhooks/<key>        (proxy matcher excludes api/webhooks/: no cookies, no Supabase call)
  1 method POST only .............. 405 (Allow: POST)
  2 key in WEBHOOK_PROVIDERS ...... 404   (own-property check, key regex)
  3 jobs available ................ 503 jobs_not_configured   (Preview / no Inngest keys: nothing accepted)
  4 signing secret configured ..... 503 webhook_not_configured (getSecret() null/throws/under 16 chars: FAIL CLOSED)
  5 content type allowed .......... 415
  6 raw body, streamed, capped .... 413 / 400   (default 1 MiB, hard max 4 MiB; Content-Length checked, stream cut at cap)
  7 verifier(raw bytes, headers) .. 401 one body for missing/malformed/wrong signature (reason only in the log)
  8 timestamp within tolerance .... 401 (either direction; null tolerance must be explicit: dedupe-only providers)
  9 parse -> events (ids only) .... 400 (<= 200 events, field lengths, no control characters)
 10 per event: account -> lane + connection from SERVER data (core.webhook_resolve_connection, asked per enabled lane,
    D-23 predicate: lower(account), status not in disconnected/pending)
      unknown or ambiguous account  -> skipped, SAME 200 as success
 11 per event: core.webhook_event_claim  -> process | duplicate | conflict (duplicate/conflict: skipped, 200)
 12 per event: sendLaneEvent("webhook/received", ids only, Inngest id = wh:<lane>:<provider>:<hash(event id)>)
      ok -> mark enqueued; fail -> mark failed + 503 so the provider retries (the retry re-claims the failed row)
200 {"status":"ok"}  (accepted, duplicate and unknown-account look the same)
```
Decisions:
- **Unknown account: 2xx, no work.** The sender is already authenticated by the signature (secrets are app-level), so a 404 would only help an enumerator and would make providers retry for days. Same body as success. Tested.
- **Dedupe key `(lane_id, provider, event_id)`.** The lane is always known at receipt (resolved before anything is recorded), so there is no cross-lane collision, and D-23 means an account belongs to one lane anyway. Tested in pgTAP and Vitest (same event id in two lanes is two events).
- **Lane never from the payload.** The payload gives an account id; the lane and connection come from `core.connections` through the lane router, one enabled lane at a time. A `laneId` inside the payload is ignored (tested). An account found in more than one lane (possible only across separate lane databases) is treated as unknown.
- **Replay.** Outside the tolerance: 401. Inside it: the claim returns `duplicate` and nothing is queued twice. Inngest's own event id (derived from lane, provider, event id) is a second line of defence.
- **Crash safety.** `received` (claimed, hand-off in flight) is re-claimable after 2 minutes; `failed` is re-claimable at once. A retry of an unfinished hand-off is claimed whatever its body hash (a provider may change delivery metadata) and the newest hash is kept; `conflict` (same id, different hash, already queued) is only logged.
- **Fail closed** is the default: no `getSecret()` result means 503 and nothing is looked up or queued. T-053 must still give the Intuit receiver a required env shape (T-050 review L5); the framework guarantees the unset case refuses.
- **Logging:** provider, lane and connection once known, event id, outcome, request id (from `x-vercel-id`/`x-request-id` if it is a plain token, else generated). Never the signature, secret, body or error text from `getSecret()`.

## Table and RLS matrix: `core.webhook_events`
Columns: id, lane_id (FK lanes), connection_id (composite FK `(connection_id, lane_id)` to `core.connections`), provider, event_id, event_type, payload_hash, status (received/enqueued/failed), attempts, received_at, updated_at. Unique `(lane_id, provider, event_id)`. No payload column.

| Role | Table | Functions |
|---|---|---|
| anon | nothing | none |
| authenticated | SELECT of 10 columns (not `payload_hash`) under the standard lane policy for the `health` view (owner, admin_technical, own lanes, aal2); no write grants | none |
| service_role | no table grants | execute `webhook_resolve_connection`, `webhook_event_claim`, `webhook_event_mark`, `webhook_events_purge` (all SECURITY DEFINER, `search_path = ''`, lane-checked against `core.connections` and `core.lanes.enabled`) |

Reads exist so an admin can see "was it received and queued" next to sync health; the same audience as `core.sync_runs`.
Retention: `core.webhook_events_purge(lane, keep)` (default 30 days, floor 7: providers retry for days and the row stops a late retry running twice). The T-042 purge mechanism does not exist yet; T-042 must call it per lane (`WebhookStore.purge`). Logged in plan-review §6.

## How other tasks plug in
Each adds a `WebhookProvider` to `WEBHOOK_PROVIDERS` (key = URL segment) and a handler for `webhook/received` filtered on `provider`:
- **T-053 QuickBooks:** `verifier: hmacSha256Verifier({ signatureHeader: "intuit-signature", encoding: "base64" })`, `toleranceSeconds: null` (Intuit signs no timestamp: replay protection is dedupe), `getSecret` from a REQUIRED env shape for the verifier token, `parse` maps `eventNotifications[].realmId` to `accountId` and each entity change to an event with a derived stable id (realm, entity, id, operation, lastUpdated). The job calls the QuickBooks CDC through the connector; the payload is never used as data.
- **T-058 Stripe:** own `WebhookVerifier` for `Stripe-Signature` (`t=`, `v1=`, 300 s tolerance, several `v1` allowed), `accountId` = `account` (Connect) or the platform account, `eventId` = `evt_...`.
- **T-065 Gmail push:** Pub/Sub push carries a Google-signed JWT, not an HMAC: write a verifier for it (audience, issuer, `exp`); `accountId` = the mailbox (`emailAddress`), `refs` = the history id. Bodies are not stored (rule 6) and the job fetches via the connector.
- **monday:** challenge handshake for the first request needs a small pre-step in its provider (not in the framework); signature per monday's scheme.

## Risks
- A provider whose scheme cannot be checked with a shared secret (Gmail JWT) needs a verifier that does network/JWKS work; the interface is synchronous. Allow `Promise<VerifyResult>` when T-065 needs it (small change in `handler.ts`).
- Unknown-account deliveries are dropped (200). If a connection is created just after the first event, that event is lost; the connector's sync catches up (webhooks are a trigger, not the source of truth).
- `received` rows older than 2 minutes are re-claimable; a very slow Inngest send (> 2 minutes) could be sent twice. Inngest's event id dedupes that.
- Migration timestamp `20261104140000` may need renumbering when merged with other SQL tracks.
