# T-050: QuickBooks OAuth (sandbox) + health

## Summary
Intuit OAuth for QuickBooks Online on the T-035 connect framework, with token refresh, a read-only API client and a CompanyInfo health check. One Intuit app ("Jarvis") serves every company; each lane's file is its own connection (own `realmId`, own Vault tokens). Scope is `com.intuit.quickbooks.accounting` only. Everything is tested with MSW and in-memory twins (rule 10); nothing here has talked to the real Intuit sandbox (see "Needs human").

## Changes
- `packages/connectors/src/quickbooks/` (new)
  - `discovery.ts`: authorization, token and revocation endpoints from Intuit's OpenID discovery document for `INTUIT_ENVIRONMENT` (sandbox or production document), cached 24 h with a stale copy kept up to 7 days, one in-flight request. Endpoints must be https on `*.intuit.com` with no userinfo, port or (for token and revocation) query.
  - `provider.ts`: the `OAuthProvider` (slug `qbo`, scope only `com.intuit.quickbooks.accounting`, Basic client auth). `precheck` runs before the code exchange; `identify` returns the realm and the refresh-token expiry. The registered redirect URI must end in `/api/connect/qbo/callback`.
  - `realm.ts`: the callback must name exactly one numeric `realmId`; when `lane_config.qbo.realm_id` is set it must equal it (checked before any token is requested, so a refused company never gets a token set).
  - `token-manager.ts`: proactive refresh when under 5 minutes remain; refresh on demand for a rejected token; single-flight per connection; the rotated refresh token is stored by a compare-and-swap that discards the old set; `invalid_grant` becomes `reconnect_required` and is never retried.
  - `api.ts`: read-only client (the object has `get` only). 401 refreshes once and retries once. `intuit_tid` is captured by the HTTP client into the redacted log for every response. Intuit's Fault code is kept as `provider_error_code`.
  - `company-info.ts`: `GET /v3/company/{realm}/companyinfo/{realm}`; keeps an allowlist (id, names, country, fiscal-year start, start date), never address or email; a response for another company is refused.
  - `connector.ts`: the contract `Connector<"quickbooks">`. `connect` refuses `vault_secret` (QB-7), requires the registered redirect URI and realm and enforces the lane's realm before exchanging the code; `health` reads CompanyInfo and reports without throwing; `read` op `company_info`; `disconnect` (minimal, see Risks). No sync, subscribe or write.
  - `index.ts`: production wiring over the real Vault, lane router (through the vault module), connector env (`requireConnectorEnv("intuit")`, read at call time) and discovery cache. `oauth/registry.ts` registers it, so `/api/connect/qbo/start` and `/callback` now exist.
- `vault/lane-config.ts` (new): reads only `lane_config_current.config.qbo.realm_id` for a lane with the job client (malformed realm fails closed; outage is `transient`).
- `vault/tokens.ts`: `rotateToken(..., replaces)` is a compare-and-swap and returns `false` when it lost the race.
- `oauth/flow.ts`: `exchangeAuthorizationCode` extracted so the connector's `connect` shares it; `OAuthProvider.endpoints(laneId)`, optional `precheck`, optional `requestIdHeader`; exported `defaultOAuthHttp`.
- SQL (see below).
- `packages/core/src/env/schema.ts`: `INTUIT_WEBHOOK_VERIFIER_TOKEN` is optional in the connector env (it is added with the webhook endpoint, H-024; T-053 fails closed when unset). `.env.example` comment.
- `apps/web/next.config.ts`: `NEXT_DIST_DIR` (used only by the client-bundle check) so a build can run beside `next dev`. `.gitignore` and ESLint ignore `.next-canary`.
- Test support: `testing/msw/quickbooks/handlers.ts` (stateful fake Intuit: discovery, token with rotation, revoke, CompanyInfo) and `testing/quickbooks-harness.ts` (the real connector over in-memory Vault, connection rows, lane config and connect state).

## Risks
- **Cross-instance refresh** assumes Intuit keeps the previous refresh token valid for a grace period after a new one is issued (the fake models it). If not, add a per-connection refresh lease. Check on Nov 12 (manual step 9). Logged in plan-review §6.
- **PKCE**: the T-035 framework always sends `code_challenge`; confirm Intuit accepts it (manual step 4).
- **Disconnect** here is the minimum the contract kit needs (revoke the refresh token at Intuit, delete the Vault tokens, status `disconnected` via the existing SQL). A transient revoke failure stops before anything is deleted; a 4xx from Intuit continues to local deletion. T-195 owns the audit actor, error map, `reconnect_required` persistence and admin notification.
- `invalid_grant` from a refresh surfaces as `reconnect_required` from the call, but the connection row is not moved to that status and no admin is notified (T-195).
- A lane with no `lane_config.qbo.realm_id` accepts any company the signed-in owner or admin authorises. Set the realm in `lane_config` before H-024.
- The same realm in two lanes is still possible (T-035 security M1, undecided).
