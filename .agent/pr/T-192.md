# T-192 action.reconcile_stuck

## Summary
A 5-minute Inngest cron (`action-reconcile-stuck`) finishes email actions left in `executing`. Verify-only: it never takes a second claim, never calls `executeWrite`, never sends. It is type-dispatched (`ActionReconciler` per action type); only the email handler exists (monday plugs in with T-113).

Not-found rule (spec approvals section 6a): nothing found, a lookup error, an unhealthy connection or a missing scope is "undecided". Before `reconcile_give_up_minutes` (default 60) the action stays `executing` and is looked up again on the next run (no state change, no audit). At or after it, the action ends `failed` with `outcome_unknown` and a specific code (`marker_not_found`, `reconcile_lookup_failed`, ...). Not finding a marker never proves nothing was sent (Gmail search lag; a crash between the provider accepting and anything being recorded cannot be told apart from a crash before the send), so it is never a retry-safe failure. Found and matching: `verified`. Found, not matching: `failed` / `verification_mismatch`. Two matches: `failed` / `ambiguous_match`. Tampered stored content: `failed` / `reconcile_payload_changed`.

Settings per lane (`lane_config.approvals`): `reconcile_after_minutes` (default 10, 5 to 1440), `reconcile_give_up_minutes` (default 60, 10 to 2880, never below the first).

## Risks
- A late-finishing execute that loses the race (the sweep already made the row terminal) ends with an `unavailable` error even though the single claim keeps it to one send; the threshold floor of 5 minutes makes this unlikely.
- A row whose message Gmail rewrote (Message-ID replaced, plan-review T-232 M4) is never found: it waits 60 minutes and ends `outcome_unknown` (safe).
- A not-found action keeps its body for up to the give-up time (D-19 purge happens at the terminal transition).
- Home has no failed-action spot; only the Approvals history shows the outcome-unknown line.
