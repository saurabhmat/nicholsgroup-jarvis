# T-130: cal.ingest_delta

## Summary
Two of the three parts of this task already existed:
- **Delta updates to `cal.event_index`.** T-064 built the Google Calendar delta sync, and T-038's `conn-sync` Google runner runs it.
- **Retention at 180 days.** T-042's daily purge covers this; the lane's calendar retention is bounded to 30–180 days in SQL.

The missing piece was that nothing started a sync. This task adds the scheduled job `cal-ingest-delta`:
- It runs every 15 minutes.
- For each enabled lane, it sends `conn/sync.requested` with trigger `"schedule"` to every usable connection of a calendar-capable provider (Google today).
- Each request has a fixed event id per 15-minute slot (`cal-ingest:<connectionId>:<slot>`), so retries and double ticks don't queue the same sync twice.
- A run syncs mail and then calendar.

## Changes
- **`packages/core/src/inngest/cal-ingest.ts`** (new): the cron function.
  - `planCalIngest` lists the connections for each enabled lane. A lane that fails to list is recorded by id only, with no error text.
  - The fan-out step sends the events.
  - A run fails, without retrying, after the healthy lanes have been sent if any lane failed to list. The next tick retries.
  - A missing or invalid schedule time is refused.
- **`events.ts` and `conn-sync.ts`:** `trigger` is now required on `conn/sync.requested`, as the T-038 review asked. It no longer defaults to "manual".
- **`packages/connectors/src/sync/targets.ts`** (new): `listCalendarConnectionIds`.
  - It uses the lane router's job client, filters on `lane_id`, and lists only `active` or `degraded` connections of `CALENDAR_PROVIDERS`.
  - It returns ids only, drops anything that isn't a UUID, and caps the list at 200.
- **Wiring:** `vault/index.ts` (`syncTargetLister`), `sync/index.ts` exports, and the `/api/inngest` route.

## Tests
- **`cal-ingest.test.ts`:**
  - cron, id and retries;
  - fixed ids across ticks, and a bad schedule time refused;
  - only enabled lanes, each listed once, with connections deduped;
  - a lane that fails to list doesn't block the others and leaks no error text;
  - non-UUID ids dropped;
  - the fan-out event is a valid `conn/sync.requested`;
  - forged or invalid events are refused by `conn.sync` without running a sync;
  - handler order: healthy lanes are sent first, and then the run fails.
- **`targets.test.ts`:** the table, the lane filter, the providers, the statuses, the limit, non-UUID rows dropped, and errors carrying no database detail.
- Existing tests were updated for the required `trigger`.
- **Results:** `pnpm typecheck`, `pnpm lint` and `pnpm test` pass in all 17 packages (core 313, connectors 1068, web 102), and `pnpm --filter @nichols/web build` passes. No SQL changed.

## Risks
- **Load on Google.** Every Google connection now syncs mail and calendar every 15 minutes wherever Inngest is configured. An unchanged delta is one cheap request per calendar.
- **No Calendar access fails the whole run.** A Google grant without the Calendar scope fails the whole `conn.sync` run every tick, after mail has synced. The reconnect flow should surface this.
- **Queued events without a trigger.** A queued `conn/sync.requested` without `trigger` now fails permanently. This only affects dev or pilot queues.
- **Stale-run limit (T-038 M4).** `maxDuration` can't be set with `cacheComponents` on, so the T-038 stale-run note still stands. The default function duration is well under the 30-minute stale limit today.
- **Not tested live.** The fan-out was tested with unit tests and fakes only, not against a live Inngest server.
