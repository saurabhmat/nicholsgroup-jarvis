# T-053 QuickBooks webhooks (owns QB-11)

## Changes
- `POST /api/webhooks/qbo`: provider entry in the T-036 receiver (`packages/connectors/src/webhooks/quickbooks.ts`, registered in `registry.ts`). `intuit-signature` = base64 HMAC-SHA256 over the raw body, constant-time compare, token from `INTUIT_WEBHOOK_VERIFIER_TOKEN` through the new required env shape `intuit_webhook` (unset, empty or under 16 characters = 503, nothing processed). No signed timestamp exists, so replay protection is the dedupe claim in `core.webhook_events`. Token, signature and body are never logged or queued.
- Parsing is strict and capped (512 KiB, 50 notifications, 5000 changes): entity names are matched to the T-051 entity set (Employee, TimeActivity and unknown names are dropped), ids/realms pattern-checked. Both the legacy `eventNotifications` shape and CloudEvents are read. Dedupe key = sha256(realm | entity | id | operation | lastUpdated); a very large delivery is grouped per realm/entity/operation so it fits the receiver's caps.
- Realm to lane/connection from `core.connections` through the lane router (existing T-036 store); unknown or ambiguous realms are dropped and logged (event ids and counts only), answer 200.
- Follow-up `qbo-webhook-sync` Inngest function (`packages/core/src/inngest/qbo-webhook-sync.ts`): batches `webhook/received` per lane + connection (10 s), checks the connection is active/degraded (no sync for `reconnect_required`, disconnected, pending, missing), and sends ONE `conn/sync.requested` (`trigger: webhook`, `objectTypes`, laneId, deterministic id). The webhook never calls Intuit and never writes externally.
- `conn/sync.requested` gets an optional `objectTypes` (plain names, max 16); threaded through `conn.sync` -> job -> runner -> `Connector.sync` options (already supported by T-051). A targeted run with no or an unusable cursor falls back to a whole-connection run.
- Env: `connectorEnvShapes.intuit_webhook` (required token); `.env.example` comment; the optional field in `intuit` stays for connecting.
