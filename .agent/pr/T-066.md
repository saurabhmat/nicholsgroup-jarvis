# T-066: Microsoft Entra connect (multi-tenant) and identity

`docs/specs/microsoft.md` §5, §7, §17 tests 4 - 9. TypeScript only: no SQL, no migration, no pgTAP file added or changed, no new dependency, no allow-list entry. It uses the existing T-254 function `core.connection_set_microsoft_identity` and the T-254 own-mail state functions. Google behaviour is unchanged; no existing test file was edited. ## Verify decisions this relies on
Recorded in `docs/plan-review.md`, section "T-066: spec §15 verify items checked against the documentation (Nov 21, 2026)", plus V-1, V-7 and V-8 in "T-256: spec §15 verify items...". The documentation was read by the calling session (web-fetch subagents), not by the builder, who has no web access; this build follows those decisions and did not re-verify them.
- V-6: no id_token signature check (OpenID Connect Core §3.1.3.7 rule 6). Each of these refuses the grant instead: `tid` is a lower-case GUID, not a personal-account tenant, and in the lane's `tenant_ids`; `iss` is the v2.0 issuer of that same `tid`; `aud` is our client id; `exp` is in the future; the `nonce` sent comes back. Only `tid` is used from the token. The mailbox comes from Graph `GET /me`.
- V-5: `scope` split on whitespace, compared case-insensitively, a Graph scope accepted short or with the `https://graph.microsoft.com/` prefix, every requested Graph scope required, `openid` and `offline_access` neither required nor refused, a refresh token required.
- V-7: the OAuth `error` string decides (`consent_required` is a consent error); the AADSTS code in `error_description` only refines for `access_denied` and `interaction_required` (65001, 90094). Everything else is `denied`.
- V-3: GCC is not detectable, so no metadata call is made; `microsoft.allow_gcc` is the documented manual gate (spec §5.4 as updated). There is nothing for the connect to enforce.
- V-4/V-6 for `/me`: `$select=id,mail,userPrincipalName,userType`; refused when `mail` is missing or empty, `userType` is not `Member`, or the UPN contains `#EXT#`.
- Authority: the lane's single tenant id, or `organizations`; never `common`.

## Risks
- The tenant is recorded BEFORE the token is stored (the acceptance lists store, then identity). Otherwise a failure between the two would leave an active row with no tenant, which the guard refuses, while the user is told nothing was stored. A failure after the identity write leaves a pending row with its tenant and no token, which is harmless and is reused by the next attempt of the same mailbox.
- No signature check on the id_token (V-6 decision, for Saurabh to confirm with this PR). A signature check would be an addition in `microsoft/id-token.ts` and needs no schema change.
- Granted scopes are strict like Google's: any Graph scope that was not requested refuses the grant, including a broader scope a tenant admin consented earlier. That is intended (a write scope is never accepted under a read-only lane policy) but could refuse a connect in a tenant that granted the app more.
- `userType` missing from `/me` is treated as "not a Member" and refuses. If Graph ever omitted it for a normal member despite `$select`, every connect would refuse; the fake follows the documented behaviour.
- Reconnect to a different tenant, or a row whose recorded tenant differs, is `wrong_account` (spec: "same address and tenant else wrong_account").
- The new result codes `wrong_tenant` and `admin_consent_required` reach Settings as `?connect=<code>&provider=microsoft`; the page maps unknown codes to no message until T-257 adds the fixed texts (`apps/web/lib/connect-result.ts` is untouched).
- The real SQL token functions were not run for a Microsoft row (no `pnpm test:db` here). The migrations were read: none limits the provider. If a pgTAP case for `connection_token_store/read/rotate` on a `microsoft` row is wanted, it is a SQL-test-only addition for a human or the next SQL task.
- `microsoft.allow_gcc` stays a manual gate (V-3): the connect cannot tell a GCC tenant.
