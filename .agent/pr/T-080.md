# T-080: Business calendar SQL

## Summary
SQL helpers for the business calendar: a week runs Saturday to Friday in America/New_York, and a month starts at 00:00 ET on the 1st.
- Every function converts with the fixed zone `America/New_York` and never reads the session timezone. The results are identical under UTC, Tokyo, Kolkata and Los Angeles sessions (tested).
- Every range is half-open `[start, end)`.
- This is the base for the MTD, YTD and weekly figures in the finance query layer (T-081).

## Changes
- Migration `20261105170000_fin_business_calendar.sql`. All functions are `language sql immutable parallel safe`, use the caller's rights, and set `search_path = ''`.
  - `fin.et_date(ts)`: the calendar date in New York.
  - `fin.month_start(d)`, `fin.next_month_start(d)`, `fin.ytd_start(d)`: 00:00 ET on the 1st of the month or year.
  - `fin.business_week(ts)`: returns `(week_start, week_end)`, Saturday 00:00 ET to the next Saturday 00:00 ET.
  - Period helpers:
    - `fin.month_range(d)`
    - `fin.ytd_range(d)`, which runs from Jan 1 to the end of `d`'s month
    - `fin.mtd_range(ts)`, which runs from the month start to `ts`, so a past `ts` never includes later events
  - Execute is granted to `authenticated` and `service_role` only, and revoked from public and anon.
- `tests/050_catalog.test.sql`: allow-list entries for the eight functions.
- `packages/core/src/db/types.ts`: regenerated.

## Tests
pgTAP `190_fin_business_calendar.test.sql` has 13 assertions:
- **32 expected values in 4 session timezones.** Each timezone must return the expected values, every timezone must run all 32 cases, and the results must match across timezones.
- **Boundaries covered:**
  - November 2026 is 721 hours, because 00:00 Nov 1 is still EDT; March 2026 is 743 hours.
  - The week DST ends is 169 hours, and the week DST starts is 167 hours.
  - The Dec 31 to Jan 1 boundary.
  - Friday 23:59:59 versus Saturday 00:00 ET, and one microsecond before Saturday.
- **A 97-minute sweep over all of 2026.** Every week starts on a Saturday at 00:00 ET, spans 7 local days, and contains the timestamp it was built from.
- **Properties:** every function is immutable, runs with the caller's rights and has an empty `search_path`. anon and PUBLIC cannot execute them.

## Risks
- **`immutable` depends on tzdata.** A tzdata update could change results, the same as for Postgres's own `timezone()`. Don't use these functions in indexes or generated columns.
- **The lane rule doesn't apply.** These are pure helpers with no data access, so they take no `laneId`.
