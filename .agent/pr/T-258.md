# T-258: Microsoft: mail delta sync (metadata)

`docs/specs/microsoft.md` §8.1, §8.2, §8.5, §6.3, §17 (tests 11 – 15, 17). TypeScript only: no SQL, no migration, no pgTAP change, no new dependency, no allow-list entry, no `eslint-disable`.

## Summary
`MailProvider<"microsoft">.sync` is real: per-folder Graph `messages/delta` into `comms.message_index` through the existing provider-generic page writer (`core.comms_mail_apply_page`, T-252). One Graph page per call, newest first, no `$filter`, `Prefer: IdType="ImmutableId", odata.maxpagesize=N` on every request, metadata only. The facade's Microsoft `syncMail` entry (and the Microsoft `conn.sync` runner's mail stream) runs it; every other Microsoft operation (live body, search, prepareWrite, calendar sync) still answers `unsupported_op`. Google behaviour is unchanged.

## Verify decisions this relies on
`docs/plan-review.md`, section "T-258: spec §15 verify items checked against Microsoft's documentation" (commit 6ced534). The documentation was read by the calling session (a web-fetch subagent); the builder has no web access and did not re-verify. Relied on:
- **V-10** no `$filter` (a filtered delta returns at most 5,000 messages): each folder is read in full with `$orderby=receivedDateTime desc`; messages older than the window (90 days or the lane's retention, whichever is shorter) are dropped in the mapper and never indexed. Well-known names are resolved to ids with `GET /me/mailFolders/{name}` and the id is used in the delta URL (the fake refuses a name there). Any `@removed` is a `{message_id, folder}` removal for that folder. `410`, or a 4xx with `syncStateNotFound` / `resyncRequired` (any letter case), on a stored link is `fullResyncRequired`. Links are opaque and sent back unchanged.
- **V-11** `Prefer: IdType="ImmutableId"` applies only to the request it is on, so it is on every request, including those made from a stored nextLink or deltaLink and the folder lookups. The id character set and length are not documented: ids are stored as given, bounded at 512 characters (the table's limit), a folder id at 256 from `[A-Za-z0-9_=+.-]`.
- **V-12** link length unknown: our bound is 2,800 characters per link; a longer link fails safe (full resync answer), never truncated. With three folders the largest allowed state encodes to about 12.6 KB (12,634 characters of 16,384) (test asserts under 16 KB).
- **V-15** `webLink` host unknown: allow-list constant `OUTLOOK_WEB_HOSTS.commercial` = `outlook.office.com`, `outlook.office365.com`, marked in the code as an unconfirmed assumption; anything else gives `source_url` null.
- Field values (`flagStatus`, `importance`, `inferenceClassification`) and the strict mapper (the fake returns `body`, `bodyPreview`, `uniqueBody` and headers on every message).
- From the T-252 review: explicit booleans for `is_read`, `is_starred`, `is_important`, `has_attachments` on every record; removal `folder` is a string or absent (never null). From the T-256 review (code LOW-5): links are parsed and re-validated, never followed blindly.

## Risks and assumptions
- **Real link shape.** The decision says a link's path is exactly the delta path of the cursor's folder id. Microsoft's examples show both `/me/mailFolders/{id}/messages/delta` and the OData key form `/me/mailFolders('{id}')/messages/delta`; the validator accepts both (the id compared after decoding), and the request is ALWAYS sent to the slash form built from the id. A link in another form (for example `users('<guid>')/...`) is refused: the first page's link is an error (`provider_error`, fixed message), a stored one a resync. If the real service answers in another form, every sync fails visibly until the rule is widened: live check.
- A link longer than 2,800 characters, a folder id outside `[A-Za-z0-9_=+.-]` or longer than 256: fail safe as above (full resync answer, then the runner fails the run on the second one), never truncated.
- `Prefer` goes as one comma-separated header (`IdType="ImmutableId", odata.maxpagesize=N`); `$orderby=receivedDateTime%20desc` and `$select=id` (folder lookup) go as raw queries. All standard, all untested against the real service.
- The window start is fixed per folder when the folder first loads and stored in the cursor; it does not slide. A message older than it is never indexed, including when it changes later.
- A 410 on a stored link is recorded by the T-196 error log (the sink sits in the Graph client) although the sync treats it as an answer; one row per expiry.
- Provider decisions per call read the lane config twice (the guard, then the sync) plus once per request attempt (T-256 design): bounded, and every read fails closed.
- `microsoftMailSync` has a 150-second run budget (`MICROSOFT_MAIL_RUN_BUDGET_MS`), checked between pages only. One healthy page takes about a second; the worst case of ONE request is four attempts of 30 s plus three waits of up to 30 s (about 210 s), so against a 300 s job limit the budget bounds a healthy run, not a failing one. T-260 should check it against the job's limit.
- **The calendar stream is not built, with two effects.** (i) A Microsoft `conn.sync` run without `streams` (a manual Sync now) applies mail and then fails on calendar with `unsupported_op`: the run row is failed and `last_error` is set (cleared by the next mail tick; no alert). (ii) Since T-255 the scheduled calendar tick already lists Microsoft connections, so in a lane with Microsoft enabled it fails with `unsupported_op` on every tick, builds a failure streak and raises the 3-in-a-row alert until T-067 is merged. **Conclusion: no lane should enable Microsoft before T-067 and T-260 are merged.**
- `last_sync_at` advances only when a load completes, so a long first load (no `$filter`, many pages over several runs) shows no freshness until it finishes (T-260).
- Link queries are restricted (see Changes): a real link that carries other parameters than one token (and our own `$select` / `$orderby` byte for byte) fails visibly (`provider_error` for the first page's link, a resync for a stored one) and the rule would then be widened deliberately after the live check.
- A timestamp without a zone is read as UTC; a non-ISO string makes the message unusable.
- `is_bulk`, `is_calendar`, `is_auto`, `is_generated`, `is_auth_pass` are absent for Microsoft rows (T-259 sets them); absent = false on insert, keep on update.
