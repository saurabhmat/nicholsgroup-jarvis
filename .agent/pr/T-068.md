## Changes

Shape (why this and not another): subscriptions are created, renewed and stopped ONLY by the existing T-040 `conn.subscriptions_renew` scan (every 12 h): one `ensure(lane, connection)` per usable Microsoft connection creates what is missing, renews what expires within 24 h, recreates what is gone, and stops what must not exist. No user request, no connect hook and no new cron. Lifecycle events from Microsoft only mark the row and queue that same per-connection job.

Design facts the spec did not say
- **Dedupe key** = (lane, subscription, kind, 10-second slot of OUR clock, SHA-256 of the delivery's bytes) (changed in the review fix round). Identical bytes in the slot are a replay (duplicate, 202); different bytes are a new event; identical bytes in a later slot queue another idempotent sync. The sync job BATCHES for up to 10 s from the batch's first event (not aligned to the slots; a batch of 5 closes it early): a change after that batch's delta read waits for the next notification or the 15-minute poll.
- Lifecycle: `reauthorizationRequired` marks the row and queues the connection's renewal job; `subscriptionRemoved` marks it removed and queues the job, which creates a new subscription; `missed` queues a delta sync like a change. The queued renewal event goes through T-040's `conn-subscriptions-renew` function, which is rate-limited to one run per connection per hour: if the scan ran inside that hour the lifecycle request is dropped and the next scan (12 h) picks the row up (polling covers the gap).
- Disconnect and a paused provider cannot call Graph (no token, or the guard refuses), so their subscriptions are marked removed locally and lapse at Microsoft within 6 days; until then the receiver drops everything for them. The brief said "stopped"; sending a DELETE from a user request is not allowed (jobs only), and after the token is deleted it is impossible.
