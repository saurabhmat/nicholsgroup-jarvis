# T-014: Append-only audit log (SQL)

## Changes
- Migration `20261031051320_audit_log.sql`: schema `audit`; `audit.events` (id, lane_id, actor_kind user|service|system, actor_id (user only, no FK so entries outlive users), dotted `action`, `target` reference, `metadata` jsonb object < 16 KB passing `core.jsonb_has_secret`, `at`).
- Append-only for every role: no insert/update/delete/truncate grant to anyone (service_role included), and a trigger that refuses update, delete and truncate even for the table owner.
- `audit.log(lane, actor_kind, actor_id, action, target, metadata)`: security definer, the only write path; executable by service_role (and by postgres-owned definer functions). Signed-in users cannot write or forge entries.
- RLS: standard lane policy with the `audit` view (owner).
- Tests: `060_audit.test.sql` (27): write path; direct inserts refused for service_role and authenticated; update/delete/truncate refused for authenticated, service_role and the owner; constraints; RLS (owner reads enabled lanes only; admin_technical, finance_operator, AAL1 and anon get nothing). The catalog test covers the new schema with no exceptions.

## Decisions
- Audit reading is owner-only for now (the `audit` view). Architecture §6 M13 mentions an audit log viewer in the admin area; giving admin_technical the view is a one-line change in `core.role_views` if wanted.
- Retention: 7 years (architecture §7); nothing deletes events. Retention jobs (T-042) must not touch `audit.*`.
