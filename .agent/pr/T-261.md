## De-duplication of the same meeting in a Google and a Microsoft calendar: actual behaviour (differs from D-58's default)
Decision for Saurabh. Not changed (no SQL in this pass).
1. **Home meetings** (`core.home_meetings`) and **briefing events** (`core.briefing_events`, which feeds Today, the 7-day look-ahead and the briefing facts): both keep ONE row per `coalesce(ical_uid, calendar_id || ':' || event_id)` and start time over all of the person's connections, choosing the row with a title, a meeting link, a link, then (home) a location or (briefing) attendees, then the lowest calendar id. The same meeting on both calendars normally has the same iCalUID, so ONE row comes back, and it carries its own connection id: the labelled row is the survivor's own provider and account (pinned in `briefing-microsoft.test.ts`). The SQL is not run by Vitest; pgTAP 322 pins per-user visibility, not this de-duplication (a pgTAP case for "same iCalUID in a Google and a Microsoft connection of one user returns one row" is a candidate for the human check).
2. **Today** (`analyzeDay`, TypeScript): even when two rows come back, events with the same title, start and end are shown once (unless their meeting links differ, then both), and `summarizeAhead` counts them once. The survivor is the first row. Pinned.
3. D-58 says "shown twice". To get that, both SQL readers and `analyzeDay` / `summarizeAhead` would change; Google-only lanes with two Google accounts would then also show such a meeting twice (today once). Not done.
