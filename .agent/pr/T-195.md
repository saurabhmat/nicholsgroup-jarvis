## What changed
- **Disconnect is an approvals action, `qbo.disconnect` (D-24, rule 5).**
  - Same life cycle as email (T-232): propose, approve the exact hash with step-up (AAL2), claim once, execute, read back, audit.
  - Owner or admin_technical of the lane may propose, approve and reject. Email stays owner only. Jobs and the assistant cannot propose it.
  - The proposal holds only `{realm_id}` and `{}`: no tokens, no company name (SQL enforces both).
  - Executor = the existing connector writer (`quickbooksWriter`): revokes at Intuit once, the Vault deletes the tokens and marks the row
    `disconnected`. Then a read-only read-back confirms the row is `disconnected` and the Vault hands out no token.
  - The executor takes `payload_sha256` and `approved_by` from the claimed, locked `act.proposed_actions` row, never from the caller.
  - No T-113: it runs inline after the approval, like email. A stuck one is finished by `action.reconcile_stuck` (new read-only handler).
  - Gate (same as email): lane policy class `qbo_disconnect` + `approvals_live`, at approve and at claim.
- **Approvals page:** a "Disconnect QuickBooks" card (what will happen, company by realm id, who asked, fingerprint, expiry) with Approve and disconnect (step-up) and Reject. History lists it. No Settings button yet (T-197).
- **Propose:** action `propose_qbo_disconnect` on the existing approvals POST route. Owner or admin_technical at AAL2; other roles 403; another lane's connection id is 404.
- **Reconnect:** reuses the T-050 connect flow and the existing row. Fix: `connection_token_store` now clears `last_error`.
- **invalid_grant / revoked / expired refresh token:** the connection is recorded `reconnect_required` (with the redacted error), one `conn/attention.needed` event
  (reason `reconnect_required`) goes to the admin, and nothing retries. conn.sync, the reports job and the webhook CDC skip it.
- **Error map (QB-14):** `quickbooks/errors.ts`, applied to every Intuit API call: 400 Fault codes, 401, 403, 404, 429 + Retry-After, 5xx, timeouts, each to retry (capped exponential backoff), `reconnect_required` or failed-with-a-fixed-message.
- **Shared JCS vector** (T-050 F-M1): two vectors, computed independently, run by the connector's `computePayloadSha256` and the approvals module's `hashOfRow`.

## Behaviour changes to know about
- The connector's action type is now `"qbo.disconnect"` (was `qbo.revoke_grant`): the approval hash covers the type, so one name end to end.
- A 401 that survives one refresh+retry, and a 403 with Intuit code 3100, are now `reconnect_required` (they were `forbidden`) and record the status. Three existing tests were updated for this.
- `intuitErrorCode` also reads the gateway's lower-case `fault.error[0].code`.
- Disconnect cannot be approved until a person adds `qbo_disconnect` to the lane policy and `approvals_live` is true (see "Needs a human").

## Risks
- **Intuit codes are from memory of the documented format** (2xxx validation, 4xxx query syntax, 6xxx business, 3200/3100 auth, 003001 throttle, 10000 system). If the sandbox answers differently, the map in `errors.ts` is the one place to fix. Unknown 400 codes fall back to "failed, refused the request".
- A 403 with code 3100 now marks the connection `reconnect_required`. If Intuit also uses 3100 for a transient problem, a connection would need a reconnect it did not need; the QB-14 sandbox check should look at this.
- `reconnect_required` notices are best effort (jobs not configured = no event). The status is still recorded.
- The `qbo_disconnect` policy class is new; production has none until a person adds it (deliberate).
- Manual-migration files are gitignored (like part 14): `part-15-T-195.sql` and `check-part-15.sql` exist only in this checkout and must be carried to the production run by hand.
