## Decisions
- Identity: Gmail `users/me/profile` (no extra scopes); `hd` not usable, mailboxes allowlist only (see docs/plan-review.md Nov 5, T-063).
- Watch/renew/stop: polling, no Gmail request, no Pub/Sub (T-065).
- `LaneConfigReader` gained `mailboxes(laneId)`; QuickBooks deps now take `Pick<LaneConfigReader, "qboRealmId">`.
- Sync mail store is created in `vault/index.ts` (the lint rule restricts `getLaneJobClient` to the vault folder), re-exported from `google/index.ts`.
- `persistedContentWrites` in the harness counts every write into the Vault, index, cursor and audit twins plus every log line that contains the body, snippet or attachment canary; a test proves the detector fires.

## Live check (human present, Saurabh's own mailbox; do not do this unattended)
Nothing here has touched a real Google account. All of it is local; nothing goes to staging or production.
1. `.env.local` already has `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` (H-008). Optionally add `GOOGLE_REDIRECT_URI=http://localhost:3000/api/connect/google/callback` (same as the default in local).
2. Make sure local Supabase is up (`pnpm db:start`) and the migration is applied (`supabase db reset --local --workdir supabase/core` or `pnpm test:db`, which resets). Sign in as the owner or admin_technical of PKG (6-digit code + TOTP, aal2).
3. Set the lane's mailboxes. The connect is refused unless the address you will use is listed in `lane_config.mailboxes` for PKG (add it through the lane config update path / seed for local; never hard-code). Use the exact primary address of the Google account you will consent with.
4. Start the dev server: `pnpm dev` (http://localhost:3000). Start the connect with a same-origin POST to `/api/connect/google/start?lane=PKG` (Settings -> Connections if the button exists; otherwise a small `curl`-free form in the browser console: `fetch('/api/connect/google/start?lane=PKG',{method:'POST',redirect:'manual'})` does not follow the 303, so navigate with a form `<form method=post action="/api/connect/google/start?lane=PKG">` from a page on localhost:3000).
5. Google's consent screen must list exactly three permissions: read email, read calendar, read Drive files (all "View"). Approve. You return to `/?connect=ok&provider=google`. Any other result code (`account_refused`, `denied`, `exchange_failed`) means nothing was stored: for `account_refused` after consent, remove the app at https://myaccount.google.com/permissions.
6. Verify in the local DB (psql on port 54322): `select provider, external_account_id, status from core.connections where provider='google';` shows your lower-cased address, `active`. The token is only in the Vault (`vault.secrets`), never in a table column or a log.
7. Run one sync from a scratch script (server-side only, e.g. `pnpm --filter @nichols/connectors exec tsx -e` with `APP_ENV=local` env loaded): `mailSync.run("PKG", await connectionLoader.loadConnection("PKG", "<connection id>"))` from `@nichols/connectors/google`. Check: `select count(*), min(received_at), max(received_at) from comms.message_index;` has rows; `select cursor_value from core.sync_cursors;` has `g1.<connection id>.h:<n>`; no column holds a body or snippet; `last_sync_at` is set on the connection. Run again: zero or few writes. Send yourself a mail, run again: the new message appears. Delete one: `deleted = true`.
8. Body check: `gmailProvider.readBody("PKG", conn, "<message id>")` returns an UntrustedBody; confirm `select count(*) from comms.message_index` and the logs show no body text.
9. Reset afterwards: in Google, https://myaccount.google.com/permissions -> remove the app (revoking in code is approvals-only). Locally: `supabase db reset --local --workdir supabase/core` (or `pnpm db:reset` if present) to drop the connection, the Vault secret and the index rows; remove the mailbox from the local lane config if you added it by hand.
