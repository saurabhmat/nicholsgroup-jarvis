## Part 3: Reply from the dashboard

Built on top of the T-232 approvals path only; no SQL, no new dependency, no connector write import.

### Decisions
- **Route, not server actions.** New strict-Zod actions on `/api/lanes/[laneId]/approvals` (`lib/approvals.ts handleApprovals`): `reply_context` (read), `draft_reply` (AI, read-only), `propose_reply` (create or edit the proposal). Guard order is unchanged: same-origin, content type and size, body schema, `requireRole(owner)` for all of them, `requireStepUp` only for `approve`. The body schema carries only `messageId` (+ `to`, `cc`, `bodyText` for the save): thread, subject, mailbox, connection, bcc and inReplyTo are refused by the strict schema.
- **Send = two calls, one hash.** The drawer calls `propose_reply` (create, or `editEmailProposal` supersede, or the same id when unchanged) and then `approve` with the `id` + `hash` that save returned. A step-up redirect therefore leaves the exact edited text saved in Approvals as well as in sessionStorage; reopening reuses it (unchanged, same id).
- **Metadata only (rule 9).** `lib/reply.ts loadMessageRef` reads `core.inbox_message_ref` with the owner's own RLS client on every call; subject = `Re: <subject>` (`reSubject`, one line, <= 990), thread id, connection (so the sending mailbox via the T-232 `readFacts`) and the reply-to message id all come from there. A message without a real Gmail thread (`m:` key or none) is `not_replyable`.
- **Existing proposal** = the newest `email.send` row from `listApprovals` (user's `act_list`) with `status proposed`, not expired, not purged and `payload.inReplyTo.messageId = messageId`. The T-231d job draft is such a row. An edit passes only `to`, `cc`, `bodyText` (the module keeps subject, bcc, thread). `derivedFromRetrieved` for a new user proposal = the To list equals the default (the sender).
- **In-doubt guard (T-192).** `findReplyState.blocked` = a row for this message that is `approved`/`executing`, or `failed` with an outcome-unknown code in the last 24 h. Then Save and Send are off ("Check the Sent folder...") and `propose_reply` refuses with `check_sent_first`. This is what stops a "blind Send again" when the drawer is reopened after an unknown result.
- **Result mapping.** `approve` now also returns `outcome`: `sent` (verified), `unknown` (`already_in_progress`, or failed with `isOutcomeUnknown` code: outcome_unknown, verification_*, marker_not_found, ambiguous_match, reconcile_*), `failed` (did not go out). `lib/reply-messages.ts resultMessage` gives fixed text; verification_* never says "failed". The drawer also treats no answer (network) or HTTP >= 500 on approve as unknown. After unknown, Send and Save stay off. `isOutcomeUnknown` moved to `lib/outcome.ts` (client-safe) and is re-exported from `lib/approvals.ts`.
- **AI draft** (`draftReply`): only when no proposal exists (the drawer does not call it when a proposal or restored edits exist). Gate `llm_allowed_categories` has `email` (read with the user's client; unreadable = off), provider configured, limiter, then one live body read (<= 4000 chars) wrapped with `wrapUntrusted`, `UNTRUSTED_DATA_RULE` in the system prompt, `getLLMProvider` (mock in tests). The output goes through the briefing's own `checkContent` (grounding, foreign links and addresses) via a one-ref `BriefRef`, then `maskContent`; a masked figure, an ungrounded one, a foreign link or the placeholder = `awaiting_input` with an empty body ("Awaiting your input"). Never stored (D-19). Drafting works while `store_outbound_drafts` is off (Copy works); Save/Send are then off with `DRAFTS_OFF_MESSAGE`; the server also refuses `propose_reply` (`drafts_not_allowed`).
- **Rate limit**: new `createLimiter` (in memory, per process): 1 draft per thread per user per lane per minute (`rate_limited`, 429). No limiter existed that fits (the chat one is a SQL per-minute turn limit, not per thread). Known limit: per instance on serverless.
- **Thread preview**: first 2,000 chars (not the last: the start is the new text, the end is usually quoted history), `displayText`-cleaned, in a `<pre>`, read live in `reply_context`, never stored. Deviation from the brief's example "last 2,000" noted here.
- **Step-up**: on `step_up_required` the drawer saves To/Cc/Body to sessionStorage (`lib/reply-draft-store.ts`, try/catch everywhere, key per lane + message) and goes to `/mfa?reauth=1&next=/<lane>?reply=<messageId>`. `ReplyAction` reopens the drawer when the URL has `?reply=<its messageId>` (and removes the param). Edits are autosaved on change; cleared after a successful send and after Save draft (the server holds it then).
- **Roles**: `HomeSections` computes `isOwner`; `AttentionSection canReply`; `ReplyAction` renders the drawer button for the owner, else a plain link to the thread (same as Open). Default `canReply=false`.
- **UI**: own dialog (no new dependency): portal, `role=dialog`, `aria-modal`, `aria-labelledby`, focus in, Tab trap, Esc closes (not while a send is in progress), focus returned to the Reply button, body scroll locked, `fixed inset-0` sheet below md, `md:w-[480px]` right drawer from md, 44 px buttons/inputs via the existing `max-md:min-h-11` / `min-h-11`. Recipient flags (outside your company, Bcc) update live as To/Cc are edited. One load per message at a time (module-level promise map) so React strict mode never asks the AI twice.

Status `pending|ok|partial|failed` (pending is the reservation), fixed `failure_code`, `searches`, `est_cost numeric(18,2)`. RLS: standard lane expression on the **`briefing` view** (Home's own view: owner, finance_operator, viewer; admin_technical has none) + AAL2; not owner-private (news is lane-wide). Reads through `core.news_latest` (invoker) and a boolean `core.news_enabled` (so members see "News not configured" without reading policy/config). `core.news_spend` (definer; owner + admin_technical): configured flags, cap, month-to-date, last status, for Settings and the Home budget state.
- **Gates in SQL, before any model call** (`brief.news_reserve`, advisory lock per lane): lane enabled; `web` in the policy AND `lane_config.news.enabled` (`not_configured`); scheduled: one per New York day, any status (`already_fetched`); one in flight (`busy`, pending older than 10 min is closed `failed/timed_out` first, cost kept, applied by the next successful reserve); owner refresh: 1 per hour counted from the attempt start (`rate_limited`); cap: month-to-date `est_cost` (this New York month) + the reserve > `news.monthly_cap_usd` read from lane_config in SQL, default 20 (`cap_reached`). The reserve (worst case of one fetch incl. resumes) is stored as `est_cost` while pending and replaced by the actual estimate at finish. Writers: `core.news_begin_scheduled` / `news_finish` (service_role), `core.news_begin_refresh` / `news_finish_own` (definer; AAL2 + owner + briefing view; own pending row only).
- **Residual risk (owner path).** `news_finish_own` lets the lane owner set items and est_cost for their OWN pending refresh, so an owner calling the RPC directly could store arbitrary https items or under-report cost for that row. The reserve still counted against the cap, the rate limit still applies, and nothing leaves the system; accepted (owner is the highest-trust role in their lane).
- **Retention.** `brief.news_purge` / `core.news_purge` (default 30 days, floor 1, lane cap, never deletes this month's rows = the spend ledger); registered as `brief.news_digests` in the inngest route next to `brief.briefings`.
- **Job.** `news-daily` (core `news-daily.ts`): every 15 min; per lane `newsDue` (config enabled + `news.time` reached today, New York) then `runScheduledNews` with the job client; SQL decides. Refusals are "skipped:<code>", model failures are stored ("failed:<code>") not thrown, infrastructure faults fail that lane only (lane ids in the error). SDK retries 0.
- **Model call (`lib/news-run.ts`).** `analysis` tier, system prompt = topics + preferred domains from lane_config, the 48 h window, output schema, UNTRUSTED_DATA_RULE + a web-specific rule; no Jarvis tools, no lane data (only the lane display name, sanitised). `max_uses` = `news.max_searches` (6), `blocked_domains` from config only (preferred domains are prompt-level, trade press stays allowed).
- **Validation (`lib/news-domain.ts`).** Candidate items only; each kept iff: plain text (control/invisible chars stripped, tags and markdown links flattened, caps 200/300/80), https URL with a public host, in the evidence (the `web_search_result` URLs or the citation URLs of THIS response; the stored link is the tool's own string), not blocked, published time (when known) within 48 h (a bare date counts to the end of its day), unique, max 6. 4+ = ok, 1-3 = partial, 0 = failed `no_valid_items`. All searches errored = `search_failed`. The DB re-checks; a DB refusal closes the attempt as failed `output_unusable`.
- **Rule 7 note.** This is news, not our finance figures: amounts and dates in headlines stay as the source wrote them (not masked, not run through grounded()).
- **Spend estimate.** `reserveUsd` = (150k input tokens x input price + (1+2 resumes) x 4000 output tokens x output price)/1M + 3 x max_searches x price/1000, rounded up to cents (about $0.81 with defaults); `actualUsd` = real tokens (cache included) + searches. Prices are lane_config (`news.input_usd_per_mtok` 3, `output_usd_per_mtok` 15, `cost_per_1000_searches_usd` 10): NOT verified against the vendor's price list (H-050).
- **UI.** `home-news.tsx` + client `news-refresh.tsx`; states: "News not configured" (admin Settings hint link `/<lane>/settings#news`), "No news yet today", "News could not be fetched: <fixed reason>", items (headline link https + `target=_blank rel="noopener noreferrer"`, why, source - date, "Updated <time>" in the viewer's zone, "Last refresh failed: <reason>" when a newer attempt failed). Owner-only Refresh: disabled "Next refresh available at <time>", "Monthly news budget reached", in flight; refusal texts are fixed. 44 px targets on the phone. Model text is React text only. `refreshNews` server action (owner role only, AI configured, SDK retries 0, 80 s abort, `revalidatePath`).
- **Settings.** `NewsSection` (owner + admin_technical): configured, web category, switched on, spend vs cap (estimate), last fetch; read-only.
