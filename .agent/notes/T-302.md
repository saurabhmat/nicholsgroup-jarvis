# T-302 notes: decisions beyond the brief, and what could not be verified

## The QuickBooks request (UNVERIFIED against Intuit: only the synthetic MSW fake exists; check in the sandbox, H-035 style)
`GET /v3/company/{realm}/reports/BalanceSheet?start_date=D&end_date=D&accounting_method=Accrual|Cash` (+ the client's `minorversion`), one request per
Friday D. How `balance_sheet` is planned today (`planReports`) is `start_date`/`end_date`/`accounting_method` (+ `class` when tracked); I reuse the same
parameter names with start = end = the date, the lane's `finance.accounting_method`, and NO class filter (a cash account's balance is the whole account, D-18).
No `summarize_column_by`: one value column, so a row is { account cell, amount cell }. Assumed, not verified: the balance is "as of end_date" for a
one-day range, and the amount is the second cell. Nothing in the repo proves either; the live check should compare one account against QuickBooks'
register for a past Friday.

## How a row is recognised as a bank account's OWN balance (connector `quickbooks/bank-balances.ts`)
A report row is kept for account id X only when ALL hold: X is in the set passed in (the connection's cash accounts from `core.fin_cash_accounts`: bank, active, mapped to the own entity,
not deleted, minus every id the payroll classification flags); the row is a leaf `type: "Data"` row whose FIRST cell carries `id = X` (digits; no label
match; a row without an id is dropped); it has exactly two cells and the second is a plain figure; and X appears on NO other cell anywhere in the
report (not on a second Data row, not on a section Header or Summary). Consequences, by design (the brief's "store nothing rather than a possibly wrong
figure"): a parent bank account with sub-accounts is not read (its header and "Total ..." carry its id and include the children); an account that
QuickBooks omits from the report (zero balance? unknown) is not stored. In both cases the cell reads "Not available" / "Not read yet" and the total of
that column is null. If the live check shows QuickBooks puts the parent's own balance on a Data row with the parent's id AND a header/total with the
same id, relax rule 3 for that shape only after seeing the real report.

## Review round (security + code review fixes, Nov 27)
- **Names.** Table `fin.cash_book_balances`; functions `core.fin_cash_accounts`, `core.fin_cash_account_ids`, `core.fin_cash_book_balances_put`,
  `core.fin_cash_book_balances_purge`, `core.fin_cash_history_enabled`, `core.business_week_start`, `core.finance_cash`. TypeScript:
  `cash-book-balances.ts` (`CashBookBalance`, `projectCashBookBalances`), `cash-book-balance-store.ts` (`CashBookBalanceStore`). pgTAP asserts no
  table, column, function or argument in `fin`/`core` is named like "bank balance".
- **Local database for the rename (no reset).** The old objects were applied locally by `supabase migration up`. I ran, in one transaction as postgres:
  `drop function core.finance_cash(text,integer)`, `drop function core.fin_bank_balances_put(...)`, `drop function core.fin_bank_account_ids(...)`,
  `drop table fin.bank_balances`, `delete from supabase_migrations.schema_migrations where version = '20261208100000'`; then edited the unmerged
  migration in place and ran `supabase migration up --local`. No data was lost (the tables held none). Production has never seen the old names.
- **Switch default.** `finance.reports.cash_history` defaults to FALSE (fail closed). `core.fin_cash_history_enabled(lane)` (one boolean; the second
  small definer after `finance_report_weeks`; true only for a finance reader at AAL2 when the config holds the JSON boolean `true`) feeds
  `finance_cash`, which then returns the Today column only and `history_enabled = false` (page sentence: "Weekly history is not switched on for this
  company"). Stored rows are ignored while it is off.
- **Stored history is not kept while off.** `core.fin_cash_book_balances_purge(lane, connection, all)` (service_role, top-level WHEREs) is called by the
  reports job at the start of every run on its own: it removes rows older than 26 weeks (any connection of the lane), every row of a DISCONNECTED
  connection (chosen: at once, at the next run of any connection of the lane, not after the retention period), and, with the switch off, every row of
  the connection. Retention no longer lives in the writer.
- **Writer.** An EMPTY call clears that date for that connection (fixed: `= any(NULL)` was a no-op; now `coalesce(v_ids, '{}')`), a partial call removes
  the date's other rows, both asserted in pgTAP. The insert repeats the validated conditions (bank, active, not deleted, same lane and connection) and the
  number of rows written must equal the number of items (else 22023, nothing kept). An inactive account is refused.
- **Store only what is shown.** `core.fin_cash_accounts(lane, connection)` evaluates the same rule as "Cash by account" in `core.home_finance` (bank,
  active, not deleted, mapped in `lane_config.entities.bank_accounts` to `entities.own_entity`; ~10 lines in SQL, no large predicate), and both the
  job's id list and the writer use it, so an account of a shared file that is not the own entity's is neither read nor accepted.
- **Zero balance, missing accounts.** Not invented: an asked account absent from the report stores nothing. The page says what a "not available" can
  mean (zero balance, account opened later, parent with sub-accounts) and that closed accounts are not listed so earlier totals cover today's accounts
  only. A column nothing was read for says "Not read yet" in the total row too.
- **Business week arithmetic** is `core.business_week_start(date)` (immutable). `finance_cash` uses it; the T-301 functions are untouched. pgTAP and the
  TypeScript `cashHistoryDates` tests use the same fixed instants and Fridays (Friday, Saturday, Sunday, year end, both DST weeks); each file's comment
  points at the other.
- **Permanent vs transient cash failures.** Transient (disposition retry: network, rate limit, 5xx, store outage) fails the run so it is retried.
  Permanent (unexpected report shape, too many ids, a database refusal) does not fail the run: a log line `qbo.cash_history.not_stored` with the step,
  the date and the error kind only, and the reports run succeeds. The run row (`core.sync_runs`) has no warning field, so the log line is the record.
  Token and connection problems still stop the run at once.
- **`plausibleAsOf`** is now one shared helper in `reports-job.ts`.
- **Payroll wording corrected.** A payroll-only bank account is flagged only by its NAME (the safety net pattern) or by its id listed in
  `finance.payroll.account_ids`; NOT by account type (a bank account has no payroll subtype). Hence the default-off switch and
  `pkg-cash-accounts-list.sql`: a person looks first.
- **Production files** (gitignored): `part-39-T-302.sql` (+ check, 21 rows), `pkg-cash-accounts-list.sql`, `enable-cash-history-T-302.sql`,
  `check-enable-cash-history-T-302.sql` (6 rows), `undo-enable-cash-history-T-302.sql`. Tested locally in rolled-back transactions (enable twice, check,
  undo twice, check; the config version the enable file wrote was parsed by `parseLaneConfig`).

## Earlier decisions (still true; items superseded by the review round are marked)
1. **Storage and retention.** unique (connection, account, date); FK to `fin.accounts (id, connection_id)` and `core.connections`. Retention 26 weeks
   (now in the purge function, see above). The writer refuses a date older than 26 weeks or in the future (New York) and an `as_of` > 5 minutes ahead.
2. **The writer replaces a date**: upserts the call's accounts and deletes the date's rows of accounts not in the call; an empty list clears the date.
   One call = one date = one transaction; any account that is not a cash account of the connection refuses the whole call (22023, constant message).
3. **Which accounts are asked about**: `core.fin_cash_account_ids` (see "Store only what is shown"); the job also removes every id the payroll
   classification flags (defence in depth).
4. **Not gated on `excluded_entity_ids`.** The reports job withholds P&L/BalanceSheet kinds while people are on `finance.payroll.excluded_entity_ids`; the
   cash history is not withheld then (same figure as today's balance). The switch default-off is the control.
5. **Job placement.** After the report loop, same concurrency key and run row. N requests (<= 13) + 2 database calls per connection per night.
6. **Settings.** `ReportSettings` has `weeks` and `cashHistory` (required). Harness default `cashHistory: false`.
7. **Refusals of the report as a whole (fail closed, constant messages):** end period or basis different from the request; a currency other than USD;
   more than 20 000 rows; nesting deeper than 10; a row of the wrong shape.
8. **`finance_cash(p_lane, p_weeks default null)`**; extra columns `reason` and `history_enabled`.
9. **Total and change semantics.** Total null when ANY listed account of that column has no balance (`missing` counts them). Change = this column minus
   the next older column, null when either side is null. Today's total equals `home_finance.cash_total` (tested). Week-end `as_of` = the oldest read.
10. **Balances of a disconnected connection** are ignored and, now, purged.
11. **Existing tests updated, not weakened:** tab tests, `050` (function entries incl. the definer in both lists), `335` (40+7=47), `336` (100 callable
   functions, 81 lane functions, 17 pure helpers), `339` (fin writers: put and purge), lane-config default test (`cash_history: false`), reports test.
12. **MSW fake:** default BalanceSheet echoes the requested dates; `balanceSheetByDate` for per-date answers.
