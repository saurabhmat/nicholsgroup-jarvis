## MEDIUM
M1 registry.ts:~75-100 schemaProblems default branch returns [] for unknown wrapper/container types. Verified on zod 4.6.7: def.type "catch" (innerType), "prefault" (innerType), "tuple" (items, rest), "set" (valueType) are not walked, so z.strictObject({x: z.object({laneId: z.string()}).catch({laneId:"A"}), t: z.tuple([z.looseObject({a:z.string()})])}) registers, and parses {x:{laneId:"NL",foo:1}} successfully. The "fails closed" claim is false for these. Fix: whitelist leaf types (string, number, boolean, enum, literal, null, undefined, date only if JSON-representable), recurse optional/nullable/default/readonly/nonoptional/array/union/tuple(items+rest), and reject every other type (default => problem). Add tests for catch, prefault, tuple, set, discriminatedUnion, .strict() method, .catchall(z.string()). The def names you used (object/optional/nullable/default/readonly/nonoptional/array/union/record/pipe/lazy) and strict detection are correct: strictObject and .strict() give catchall.def.type "never", looseObject gives "unknown", plain object gives undefined; exactOptional reports "optional"; discriminatedUnion reports "union"; .transform() and .pipe() report "pipe".
M2 registry.ts llmTools (~L130): z.toJSONSchema runs at call time and throws for unrepresentable types (verified: z.date() throws "Date cannot be represented in JSON Schema"). One bad tool then breaks every chat turn. Fix: build and freeze the JSON schema inside register() (try/catch => ToolRegistrationError), assert additionalProperties:false at every object node, and have llmTools only filter.
M3 gate.ts:~137-141 tool.args.safeParse can throw (async refinement => "Encountered Promise during synchronous parse"), violating "never throws". Fix: wrap in try/catch => invalid_args; also reject async schemas at registration.
M4 gate.ts:~146-153 withAudit rethrows when the final ".succeeded" audit write fails after the tool already ran; the gate then reports tool_failed and drops the result. For a propose tool the proposal exists but the model is told it failed (retry => duplicate). Fix: track "ran" and, if run completed, return ok with an auditIncomplete flag (and log); only a failure of the ".requested" write (or the run) is tool_failed.
M5 gate.ts:~91-118 denials from requireLane (cross-lane, not_member) are audited with actor {kind:"system"}, so the forensic record of who tried a foreign lane is lost (userId is only set after requireLane succeeds). Fix: add requireSession to GateDeps (or return the session in AuthError path) and resolve userId first; audit actor = user whenever a session exists. Add a test asserting actor.userId on the not_member denial.
M6 Interface gaps for T-104/T-105/T-103 (decide now, cheaper than later):
  a) ToolContext {laneId,userId,role} has no DB client and no AbortSignal. T-104 tools must read fin.* through the user's lane client (rule 1, RLS); without it they re-call requireLane. T-105 needs abort on disconnect and a wall-time budget. Add client: LaneClient (user client already returned by requireLane) and signal to ToolContext/GateCall.
  b) GateOutcome gives no parsed args, tool name or duration on denial/ok. T-103 ai.tool_calls stores validated args, status, denial reason: return { toolName, args (parsed.data), durationMs } in both branches.
  c) No way to get the tools to offer the model. llmTools(categories) needs the lane's llm_allowed_categories, which finance_operator cannot read (lane_policies), and views per role. Add a definer RPC (e.g. core.ai_tool_scope(p_lane) => categories + allowed views, same aal2/membership checks) and gate.availableTools(laneId); T-106's "disabled when no categories allowed" needs the same.
  d) tool.run output is not validated. T-105 streams sources/asOf/freshness straight to SSE and the data to the model. Validate the ToolResult envelope with Zod (sources array of {kind,id,label?,url?}, ISO asOf, freshness enum, notes string[]), require JSON-serializable data, and cap serialized size (e.g. 64 KB) => tool_failed.
