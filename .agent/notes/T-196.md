# T-196 notes: QuickBooks sync and API error log + export

Approved by Saurabh Nov 13, 2026 (away). Decisions, with reasons.

1. **Sync runs: gaps found and filled.** conn.sync (initial/CDC, schedule + manual + connect) and the webhook-triggered CDC (conn.sync with
   trigger `webhook`, objectTypes) already write a `core.sync_runs` row per connection. The reports pull and the normalizer wrote none.
   Added `core.sync_runs.job` (sync | reports | normalize), kind `snapshot` for the two new jobs, trigger `schedule`. The one-running-run
   unique index is now per (connection, job), so a normalizer or report run never blocks a sync (and the stale-run cancel is per job).
   Readers of sync_runs checked: normalizer cutoff reads `kind = 'full'` (unchanged, snapshots are never 'full'); briefing coverage reads
   Google/Microsoft connections only. A separate table was rejected: same columns, same RLS, one more thing to export.
2. **Best effort run log.** `sync/job-run.ts`: a run that cannot be started/closed is logged by code and the job goes on (work is idempotent;
   the outcome stands). `recordOutcome` (connection last_sync_at / last_error) stays conn.sync only.
3. **`core.connector_api_errors`.** Columns as the brief + kind, disposition, retry_after_seconds. Immutable (no update/delete for anyone;
   service_role can select/insert; purge is a definer function). Read policy = standard lane policy on the `health` view (owner and
   admin_technical at AAL2), the same audience as sync_runs, so `has_standard_lane_policy` pins it.
4. **DB-side guards (cheap, kept):** message: no `@`, no `bearer`, no 5+ digit run, <=300 chars; endpoint: `^/[A-Za-z0-9_{}./-]*$` and no
   5+ digit run; code: up to 6 digits or a word code; tid: id characters only; kind/disposition/status enums. Intuit codes such as 003200
   are 6 digits, which is why the code column allows a 6-digit run; provider_tid (Intuit's opaque `intuit_tid`) can contain long
   digit runs and is exempt from the digit rule (it is an id, not data about a person).
5. **Retention:** fixed 90 days, no parameter (`core.connector_api_errors_purge(lane)`: enabled lane only, service_role only), registered
   in the default retention tables as class `policy` (no lane setting; the contract says the SQL function enforces its own window). sync_runs
   is NOT purged here: the normalizer's full-reload cutoff reads it, and rows are small; revisit with T-042 follow-up if it grows.
6. **Redaction (`error-log/scrub.ts`):** endpoint is templated (query/fragment dropped, the segment after `company` becomes `{realm}`, odd or
   digit-heavy segments `{id}`); message comes from the error map (`classifyIntuitFailure(info).message`) passed in by the QuickBooks wiring,
   never from Intuit; a fixed message that still looks personal becomes a generic sentence. Canary test runs through the real API client,
   token manager and HTTP client over MSW with tokens, email, personal name, 14-digit run, realm and a SQL-like query string, for seven statuses.
7. **Single sink:** `error-log/sink.ts` (`createApiErrorSink`), called once in `quickbooks/api.ts` after the error map for every Intuit API
   error that reached Intuit (a status, a timeout or a network failure). Not recorded: our own input errors, lane mismatches, token-endpoint
   failures (not API answers, T-195 M1). Store/transport failures are logged by code and never thrown.
8. **Sentry:** no SDK, no DSN (T-041, H-011). One `ApiErrorTransport` seam; default transport is the redacted connector logger line
   `connector.api_error` (same scrubbed fields as the row). T-041 adds a Sentry transport to `transports` in `quickbooks/index.ts`.
9. **Export:** `GET /api/lanes/<lane>/connector-errors/export?from&to&format=csv|json&dataset=errors|runs`. Owner/admin_technical at AAL2 (403
   others, 404 other lane, 401 none); range max 90 days; read with the user's client so RLS is a second guard; fixed columns; 10,000 row
   cap (413); audit `connector_errors.export` written BEFORE the file leaves (audit failure = 503, nothing returned); CSV is formula safe.
   sync_runs export omits the error message (kind, status, code, request id, endpoint only). GET with `no-store`; no UI (T-197) but
   `connectorErrorExportUrl` helper added.
10. **Pre-existing test touched:** 050_catalog lists every security-definer function; added `core.connector_api_errors_purge`.
11. Not done on purpose: no backlog status change; no manual sandbox check (needs a human, see PR).
