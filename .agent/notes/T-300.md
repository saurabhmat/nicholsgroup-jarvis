# T-300 + T-301 notes: decisions beyond the brief, and what could not be verified

## Decisions (not in the brief or spec; take them out if Saturday/Friday dispute them)
1. **Weeks come from SQL, via a tiny definer.** `lane_config` is readable only with the `config` view; a finance-only reader cannot read it. So
   `core.finance_report_weeks(lane)` (SECURITY DEFINER, `search_path = ''`, returns one integer, null unless finance view at AAL2) reads
   `finance.reports.weeks` (1 to 13, default 4 when missing or invalid). `finance_weekly` and `finance_week_detail` take `p_weeks default null`
   and use it; an explicit 1 to 13 overrides (tests); out of range raises 22023. This is the only definer added. It had to be registered in
   `050_catalog.test.sql` and the counts in `336_security_function_isolation.test.sql` (92 -> 96 callable functions, 74 -> 78 lane functions).
2. **`weeks` is added to `finance.reports` in `packages/core/src/lane-config/index.ts`** (`z.int().min(1).max(13).default(4)`); the existing
   default-config test now lists `weeks: 4`.
3. **Payment entity.** `fin.payments.entity_code` is per row (an allocation takes its invoice's entity; an unapplied row the payment's). I filter
   rows by `entity_code = own_entity`, then count a payment once per (connection, source id) among the surviving rows. A payment split across two
   entities would therefore count once for each entity with only that entity's rows summed. Not expected in practice (the normalizer gives a
   payment ONE entity when all its allocations agree); noted for the review.
4. **Currency.** Invoices and payments counted only when `currency_code = 'USD'` (same rule as `home_finance_detail`, which is stated for AR; the spec
   says "same connections and entities" for weekly, I applied USD too so that a EUR amount is never added into a dollar figure).
5. **Payment date bucket.** `paid_at` is the QuickBooks `TxnDate` at 00:00 America/New_York (normalizer step 'payments'), so the business date is
   `(paid_at at time zone 'America/New_York')::date`. Tested with a Friday, a Saturday and a Friday 23:30 New York payment (a Saturday in UTC).
6. **Current week "to date".** Figures of the current week run to today (`least(week_end, today)`); a future-dated invoice or payment is in no row.
   The row carries `through` so the page says "This week, to <date>".
7. **Aged AR "Current".** Exactly the existing rule: `coalesce(due_date, issue_date) >= today` is current, i.e. not yet due, due today, or (no due date)
   issued today or later. An invoice with no due date ages from its issue date. The page states the rule. Days overdue shown are clamped at 0.
8. **Check line comparison rule.** The newest cached `ar_aging_summary` of a current connection (by `params.report_date`, then `as_of`); its TOTAL
   row's last column. Reasons: `not_cached`; `withheld` (Header.TotalsWithheld = true, or no TOTAL row: the reports job drops it when it removed
   payroll people); `unreadable`; `older_than_data` when the report date is before the New York date of the last data processing (the report is a
   picture of one day and the computed total is of the synced data). Difference = computed minus QuickBooks, computed in SQL. QuickBooks' report
   covers the whole company (aging reports are not class-split), the page says so with the credits note.
9. **Customer grouping.** By `customer_id`; invoices with no customer id share one row; the name is the one on the newest invoice that has one.
   Name null -> "Unknown customer" (so several customers with an id and no name show as several "Unknown customer" rows).
10. **Caps (stated on the page, counts from SQL):** 50 customers, 25 open invoices per customer, 50 invoices and 50 payments in a week's detail.
11. **Connection note / states.** The two new list functions also return `last_sync_at` and `connection_status` (from `home_finance_context`) so the
    tabs show the same connection note and the same empty-state words as the Overview without calling `home_finance` (heavier). `home-finance.ts`
    was refactored minimally: `emptyTextFor(state, lastSyncAt)` and `connectionNoteFor(status)` extracted; `emptyStateText` and `connectionNote`
    call them (behaviour unchanged, tests pass).
12. **Recharts was NOT a dependency of `apps/web`** (nor anywhere in the workspace). It is in the stack (CLAUDE.md), so I added `recharts` 3.11.1
    pinned exactly like the other dependencies (`pnpm --filter @nichols/web add -E recharts@3.11.1`); `pnpm-lock.yaml` changed (+306 lines).
    The lockfile passes the repo's supply-chain check (pnpm said so on install and on `--frozen-lockfile`).
13. **Chart and server rendering.** Recharts 3 draws its SVG only after measuring the container in the browser. The server document holds the sized
    wrapper (`recharts-wrapper`, from `initialDimension`) and no bars; the SSR test asserts exactly that and no errors. The chart is `aria-hidden`
    decoration; the table carries every figure. Not seen in a real browser (see below).
14. **Detail is native `<details>`** inside each customer row: no client state, no customer id in an address, works without JavaScript.
15. **DB types** regenerated with `node scripts/gen-db-types.mjs` (only the four new functions are added); `db:types:check` ok.
16. **console-sites test**: `apps/web/lib/finance-reports.ts` added to the reviewed list of files that log (it logs lane id and the error NAME only, like
    `finance-page.ts`).
17. The Cash tab is not added (T-302). The Overview now shows the tab row (Overview current); nothing else on it changed.
