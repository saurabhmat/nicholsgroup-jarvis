## Part 3: clock reads on /[laneId] and /[laneId]/settings
- Local production build (synthetic/local-only env, all .env.local variable NAMES pre-set to dummies so no real value loads): no clock error before or after; `next start` redirects signed-out requests in the proxy. A signed-in repro needs an AAL2 session; the e2e helper enrols a TOTP factor on a seeded persona (breaks later e2e: "enrolled outside this run"), so not used. Root cause taken from Next 16.4.2 source (node-environment-extensions/io-utils.js): with partialPrefetching a clock read in a static/runtime stage of a request is a sync-IO error. Note: the extension is installed "during builds and revalidates", i.e. it also fires at runtime revalidation, consistent with Vercel runtime logs.
- Fixed: nav.ts defaulted `now = new Date()` in greetingFor/homeHeading/pageHeading, and AppShell (every route) called pageHeading(active, firstName) -> a clock read on every render of the shell even for non-Home. Now the server passes `now` (layout, after the lane check) and AppShell never reads the clock. HomePage/SettingsPage `await connection()` first.
- Kept the `now = new Date()` defaults of server components (every production caller passes `now`); making them required churned ~30 tests for no behaviour change.
- Trade-off: the phone band greeting is fixed at the layout render (a layout does not re-render on client navigation).
- Regression: tests/clock-reads.test.ts, AppShell no-Date test, scripts/check-build-log.mjs (`pnpm --filter @nichols/web check:build-log`, stdin or file).
