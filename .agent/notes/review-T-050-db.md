# D-23 (cc9323c)
Result: no BLOCKER, no HIGH. Static review only: `pnpm test:db` aborted at "db reset" (DbSetupError, container exit 1) in this sandbox, and a manual `supabase db reset` was refused by the permission classifier, so the new 120 file and the edited 080/090 were NOT executed by me. ## Checks
- NULL external_account_id: column is `not null` (migration 20261102042312:87), so the "multiple NULLs allowed" gap does not exist. Providers without an account id cannot create a connection at all; no change needed.
- Existing rows: the migration builds a unique index on live data. Seed has no core.connections rows. Any local DB where one account was connected in two lanes (previously legal, 080 asserted it) would fail the migration with 23505. Fine for the pilot (PKG only); production not touched.
- Status coverage: table check allows pending/active/degraded/reconnect_required/disconnected; `<> 'disconnected'` is the safe default, so any later non-disconnected status holds the account automatically. Tested for degraded and reconnect_required; pending and active are covered via inserts.
- Reactivation: connection_token_store sets status active (20261102050000:102), so reactivating a disconnected row while another lane holds the account raises 23505 and the whole function rolls back (including the Vault create_secret and mapping insert, no orphan). Mapped in tokens.ts to ACCOUNT_IN_USE. Tested at 120 (direct update). Connect flow wraps storeToken in refuseInUse. Good.
- revoke only sets disconnected, which cannot violate the partial index. rotate does not change status.
- RLS: unchanged; select policy and column grants intact (authenticated has select only, no insert/update), so authenticated cannot trigger the 23505 and the index leaks nothing.

## Findings
- MEDIUM migration:10-12: the key is case-sensitive. For mailbox-style accounts (google/microsoft) `Ops@x.com` and `ops@x.com` are the same account but pass the index, so D-23 can be bypassed. Fix: `(provider, lower(external_account_id))` in the index (and use lower in the test), or normalise mailbox ids to lower case in the connector before ensureConnection. QuickBooks realm ids and Stripe `acct_` ids are not case-affected.
- MEDIUM tokens.ts ERRORS "23505" (diff line ~+55): the mapping is keyed on the SQLSTATE for every token function, but other 23505 sources exist inside them: connection_secrets primary key and the unique name on vault.secrets (`connection:<id>`). Those would be reported to the user as "already connected to another company", which is wrong and hides a real fault. Row lock makes these unlikely, so severity is MEDIUM. Fix: have connection_token_store catch unique_violation on the status update and re-raise with a distinct code or message (e.g. errcode 'P0001'/custom 55006 with `constraint` check via `get stacked diagnostics constraint_name = 'connections_one_lane_per_account'`), and map that instead of bare 23505.
- LOW ensureConnection 23505 (connections.ts:42): the upsert's `onConflict` names only the per-lane constraint, so 23505 from other causes (none today) would also read as "in use". Same fix as above: check `inserted.error.message`/constraint name contains `connections_one_lane_per_account` (the error is only compared, never passed on).
- LOW 120 test, cross-lane denial (last assertion): there is no positive control. The count 0 would also pass if the admin could see nothing at all. Add an assertion that the same role sees a PKG connection row (e.g. insert a fresh active PKG row for another account before switching role) and that a PKG admin with `aal1` sees 0 (missing MFA). anon-denial is not repeated here; it is covered by 080 for the table, acceptable since no policy is added.
- LOW 120: no test that the index does not block rows differing only by provider within the same lane or that `update ... status = 'pending'` from disconnected is also refused (only 'active' tested); and no test that tokens.ts-equivalent SQL path (core.connection_token_store on a disconnected row while another lane holds the account) raises 23505 and leaves no Vault secret/mapping. Add one pgTAP for the function path; it is the real reactivation route.
- LOW 120 relies on `update core.lanes set enabled = true where code = 'APK'` inside the transaction as the superuser after `reset role`; fine, rolled back. 080 line 59 message mentions 120 by name, good.
- LOW: 090 change renames the APK realm; confirm no other test file (T-050 TS integration, seed) inserts the same account in two lanes. grep of seed found none.

## D-23 v2 (ffa0fbd)

Reviewed statically (no db reset / test run, per instruction). Result: no BLOCKER, no HIGH.

Verified OK
- Order: 20261104110000 sorts after 20261104100000 (which creates the index it drops), so `drop index` (no IF EXISTS) is correct on a fresh reset; the migration runs once, create-or-replace and grants are re-runnable.
- Function: body identical to 20261102050000 (and not redefined by 20261104090000_rotate_cas) except the added `v_constraint` variable and the begin/exception block around the final status update. Still security definer, `set search_path = ''`, first statement is core.connection_for_token(lane, id, true), which does the lane check (same error for wrong lane) and `select ... for update`. Revoke from public/anon/authenticated and grant to service_role are re-stated, correct.
- `get stacked diagnostics ... = constraint_name` is valid for unique_violation; for a unique index (not a constraint) PG reports the index name, so the comparison with 'connections_one_lane_per_account' is right. Raising inside the handler leaves the subtransaction and aborts the whole function call, so the Vault secret and mapping rolled back (test asserts this). `raise;` re-raises with the original SQLSTATE.
- Pending semantics: two lanes storing concurrently both reach the `update ... status = 'active'`; the second blocks on the unique index until the first commits and then gets the violation -> D0023. First to store wins; no deadlock (each holds only its own row lock). Nothing in migrations or packages sets a row back to 'pending' after use, so no way for a usable row to leave the index except disconnect. Row-level token_revoke -> disconnected frees the account, as designed.
- pgTAP: plan(38) equals the 38 assertion calls I counted. Positive controls and aal1 case added; the l4 and race cases exercise the real function path; full-rollback check covers mapping, vault.secrets and audit.events.

Findings
- MEDIUM SQLSTATE class: `D0023` is in a class (first char A-H) that the SQL standard reserves; PostgreSQL docs say user-defined codes should use classes starting 5-9 or I-Z. PG accepts it and D0 is unused today, but a future PG/standard class D0 would collide, and a driver/pooler may treat unknown standard classes specially. Use e.g. `Z0023` (or `PD023`-style custom in class 5-9/I-Z) and change tokens.ts + tokens.test.ts + 120 together. Low blast radius now, cheap to fix before more code depends on it.
- MEDIUM test quality: the "other 23505 stays 23505" assertions never reach the new handler. The Vault-name clash raises inside vault.create_secret and the connection_secrets_pkey check is a direct INSERT, both before/outside the `begin ... exception` block. So the `raise;` branch is unexercised, and the tests would still pass if the handler mapped every unique_violation to D0023. In practice the only unique constraint the final UPDATE can hit is this index (the per-lane unique key is not changed by it), so the branch is near-dead; either drop the claim/branch comment or note it, or test it by a temporary second unique index on core.connections inside the test (e.g. a unique index on token_expires_at, then store two rows with the same expiry -> expect 23505, not D0023).
- LOW migration on non-fresh DBs: `create unique index` on lower(external_account_id) fails if an existing environment already holds two usable rows differing only by case across lanes (and `drop index` first means no index during the failed attempt only inside the migration transaction, so safe). Local/dev only today; add a pre-check note if a shared DB ever exists.
- LOW: indexdef regex tests (`WHERE.*disconnected.*pending`) depend on pg_get_indexdef text, which lists the NOT IN as `<> ALL (ARRAY[...])`; the ordering disconnected then pending holds, so it passes, but it would not catch the order being swapped or a third status. Acceptable; behavioural tests cover it.
- LOW: pending rows now let any lane create a pending row for an account another lane holds; ensureConnection in lane B for that account succeeds and leaves a pending row (test asserts it). Harmless (RLS keeps lanes apart, nothing stored) but the refusal now happens one step later (token store), so the connect flow must keep treating D0023 as the only "in use" signal; tokens.ts does.
- LOW: 080 and 120 insert second-lane rows with status 'active' directly as service_role; fine for tests, noted only because the default 'pending' no longer conflicts, so any other test inserting a second-lane duplicate without status would silently stop failing (grep found none).
