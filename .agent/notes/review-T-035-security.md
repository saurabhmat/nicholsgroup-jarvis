# T-035 security review (Nov 2, 2026, commit d5f469e): findings

**No BLOCKER, no HIGH.** The core binding is sound. The state is 256-bit random with only its SHA-256 stored. It is consumed atomically by `delete ... returning`, which makes it single-use, and it is bound in SQL to `auth.uid()`, the lane and a 10-minute expiry. Role and aal2 are re-checked at consume through `has_lane_role` → `may_resolve`. PKCE is S256. The table has RLS on, no policy and no grants (service_role included). Both SECURITY DEFINER functions use `search_path = ''`, execute is revoked from public/anon/service_role, and pgTAP covers other-user, other-lane, aal1, demoted, expired and replay. The start route is POST with an Origin check. The callback redirect is a fixed relative path with `no-referrer`. The HTTP client does not follow redirects, so the code and client secret cannot be re-posted elsewhere. Token values are registered with the redactor before anything can log them. Logs and audit carry only coarse reasons and error class names. The new dependency is the workspace package `@nichols/connectors` in apps/web, which is on the allow-list. The lockfile change only re-resolves the existing `@opentelemetry/api@1.10.0` peer of next, so no new third-party package is added.

## MEDIUM

- **M1 Cross-lane account mixing is not refused by the framework** (`packages/connectors/src/vault/connections.ts:34`, `packages/connectors/src/oauth/flow.ts:179`). `ensureConnection` is keyed on (lane, provider, external_account_id). The same provider account (one QuickBooks realm, one mailbox) can therefore be connected and made `active` in two lanes. A lane can also hold several accounts for the same provider.
  - Scenario: a bookkeeper who is admin_technical in both PKG and APK has Intuit access to both companies. While connecting APK, they pick the PKG company file at Intuit's consent screen. T-050's realm check only applies "when one is set" in lane_config. So APK gets an active connection to PKG's books, and every later sync writes PKG financial data into APK. That is lane leakage (rule 1) caused by a realistic mistake, not an attack.
  - Fix: in the framework, before `ensureConnection`, refuse (`account_refused`) an external account that already has a non-`disconnected` connection in another lane for the same provider. Back it with a partial unique index `(provider, external_account_id) where status <> 'disconnected'`, or check inside a security-definer function. Optionally add a per-provider `singleAccountPerLane` flag that refuses a second account in the same lane unless it is the same account (a reconnect). Add tests for both.

- **M2 Granted scopes are not checked against the requested scopes** (`packages/connectors/src/oauth/flow.ts:35`, `:171-180`). The token response's `scope` is parsed and stored, but never compared to `p.scopes`.
  - Scenario: Google with `include_granted_scopes=true`, as a future adapter might pass through `authorizationParams`, or an account that previously granted broader scopes to the same client. The provider returns a token carrying scopes beyond the read-only set (e.g. `gmail.modify`/`gmail.send`, Drive write), and that token is stored in the Vault. The read-only design and the rule that writes happen only through approvals then rest on code paths alone, and a leaked token does more damage.
  - Fix: when `tokens.scope` is present, refuse a token whose space-separated scope set is not a subset of `p.scopes`. Refuse with `account_refused`, store nothing, and revoke the token if the provider supports it. Optionally also refuse when required scopes are missing (granular consent). Forbid `include_granted_scopes` in `authorizationParams`. Add a test.

## LOW

- **L1 Failed state checks leave no trace** (`flow.ts:149-159`). An `invalid_state` result (malformed, unknown, other user, other lane, expired, replayed, or provider mismatch) is neither audited nor logged. So login-CSRF and replay attempts against the callback are invisible. Fix: log `connector.oauth_callback_failed` with `reason: "invalid_state"` (lane and provider only, never the state). Also consider an audit entry once the user is authorized (after line 151).

- **L2 The redirect URI is not constrained** (`supabase/core/supabase/migrations/20261102070000_oauth_states.sql:20`, `flow.ts:115-119,171`).
  - The DB check allows any `http(s)://` value.
  - Nothing asserts that `p.client().redirectUri` is `https` (loopback http in dev only), on the app origin, and ends in `/api/connect/<slug>/callback`.
  - The token exchange uses the redirect URI stored in the state row. The caller supplies that value: an owner can call `core.oauth_state_create` directly over PostgREST, since `core` is exposed (H-026). The provider's exact-match rule keeps this from being exploitable today, but the server should not trust the value.
  - Fix: validate the redirect URI in `createOAuthFlow` at registration/start (https except loopback, path `/api/connect/${slug}/callback`). At callback, require `stored.redirectUri === p.client().redirectUri`, or don't store it and use the configured value.

- **L3 `identify` gets raw credentials and the full callback query** (`flow.ts:56`, `:175`). `tokens` holds `access_token`/`refresh_token`/`id_token` as plain strings, and `callback` includes `code` and `state`. Provider adapters (T-050, T-063, ...) are one stray `log.info({ tokens })` or `JSON.stringify(input)` away from writing them out. Exact-match redaction catches the tokens but not `code`/`state`. Fix: pass `tokens` with credential fields as `SecretValue`, or pass only non-credential fields plus a ready `auth` SecretValue. Pass the callback params through an allow-list (e.g. `realmId`) instead of the whole query, and document that adapters must not log `input`.

- **L4 Callback parameters are user-controllable, and `identify` may trust them** (`flow.ts:56`, `:175`). The user finishing the flow can edit `realmId` in the callback URL before it reaches the server. T-050's "callback realmId must equal the lane_config realm" check is then a check of a value the user typed. Intuit tokens are realm-scoped, so the API calls would fail rather than leak, but the connection row would name the wrong realm. Fix: document in the `OAuthProvider.identify` contract that the account must be confirmed with the token (QBO: `CompanyInfo` for the realm, Google: userinfo/id_token `sub`/`email`), and carry that into T-050's acceptance.

- **L5 The state binds the provider, not the slug** (`flow.ts:119,159`). Two registered slugs that share a `Provider` value (e.g. separate Google mail/drive adapters with different scopes or endpoints) would accept each other's states and exchange a code at the other adapter's token endpoint. Fix: store and compare the slug (or slug + provider).

- **L6 Orphan `pending` connection rows** (`connections.ts:34`, `flow.ts:179-180`). If `storeToken` fails after `ensureConnection` inserted a row, the `pending` row remains for an account that never connected. It would show on Settings → Connections and could confuse admins about which file is connected. Fix: insert and store in one SQL function, or delete the row on failure when this call created it.

- **L7 No route-level tests** (`apps/web/app/api/connect/[provider]/start/route.ts:12`, `callback/route.ts`). The Origin check (missing, `null`, or another site → 403), the 404 for unknown providers, `no-store`, and the callback `Location` being a relative `/` path with `no-referrer` are untested. The acceptance asks for end-to-end coverage. Fix: add route tests with a mocked `oauthFlow`.

- **L8 The callback URL carries `code` and `state` in its query** (`callback/route.ts`). These reach Vercel request logs now, and Sentry breadcrumbs/transactions once H-011 lands. Both are single-use and PKCE-bound, so the risk is low. Fix: when Sentry is wired, scrub the `code`, `state`, `realmId` query params on `/api/connect/*` (`beforeSend`/`beforeBreadcrumb`, and a redaction test).

## Lint boundary (packages/eslint-plugin)
The new restricted names are correct and tested: `connectionStore` (connectors only) and `createConnectionStore` (vault only). `forgetSecretsForTests` is allowed only in `oauth/flow.test.ts`, which matches the existing exception for `http/client.test.ts`. apps/web now depends on `@nichols/connectors`. Its root export holds contract types only, `/internal` is restricted, `executeWrite` is a restricted name, `/testing` and `msw` are test-only, and `@nichols/connectors/oauth` pulls in the lane router, which starts with `import "server-only"`. So a client component cannot bundle it.
