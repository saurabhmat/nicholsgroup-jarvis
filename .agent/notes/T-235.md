# T-235 notes

## Part 1: AI summary, automatic and reliable (no Run button)

### Decisions
- Structured output: the installed `@anthropic-ai/sdk` 1.6.0 types `output_config.format` as `JSONOutputFormat { type: 'json_schema', schema }` (no name field); `tool_choice` is never forced. `LLMRequest.outputSchema { name, schema }` is sent as `output_config.format` (merged with `effort`), validated fail-closed in `buildParams` (name shape, object schema, never with `serverTools`). The mock reuses `buildParams`, so it validates the same way and records the schema in `calls`; new test helper `jsonResult`.
- One source of truth: the Zod schema `BriefingOutputSchema` in `apps/web/lib/briefing-output.ts`; the JSON schema is `z.toJSONSchema` of it (closed objects, six required fields). Parsing: whole text, then fenced block, then `extractJson` (first `{` to last `}`), then Zod. `checkContent` (refs, grounding) and `maskContent` run unchanged after Zod.
- Retry ONCE on a parse or Zod failure: previous assistant text + a user message listing issue paths and Zod codes (and the expected type name), no values and no new email content. Refused or truncated replies are not retried. Log line `briefing.model_output_invalid` (laneId, attempt, issues = path + code) on each failed attempt; the saved failure code stays `output_invalid`.
- Auto run: `ensureFreshBriefing` (owner + AAL2 via requireRole -> model configured -> policy -> SQL claim -> `after()`), `regenerateBriefing`, `briefingRunState` (poll). `after()` from `next/server` is supported in Next 16.4 server actions; the lane client is a bearer-token client (no cookies), the tz cookie, provider and policy are captured before `after()`. The run is `runBriefingBounded` (75 s abort guarding writes, single-flight). Home's `maxDuration = 90` covers the action plus `after()`.
- SQL (migration 20261114100000): `brief.briefing_runs` (RLS, own rows, aal2 + briefing view), `brief.briefing_claim` (internal gates), `core.briefing_claim_auto`, `core.briefing_claim_regenerate`, `core.briefing_claim_schedule` (service_role), `core.briefing_run_state`, `brief.briefing_runs_close`. Gates return `{id, gate}` and never raise, so the 10-minute lost-claim close commits. Gates: not_stale (3 h, auto only), running (2 min), cap_reached (6 per lane per New York day, all kinds), rate_limited (Regenerate 30 min), cooldown (auto, 10 min after an auto/regenerate/manual attempt). `core.briefing_save_own` skips its 2-minute cooldown only while the owner has an open claim, and both saves close the claim. `core.briefing_save` (job) closes the schedule claim.
- UI: `BriefingAuto` (client, owner only) mounts once per page load, calls `ensureFreshBriefing` only if the latest good briefing is older than 3 h (SQL decides again), shows "Updating summary…", polls every 12 s for up to 3 min, then one refresh via `requestRefresh` (waits while the reply drawer holds the gate). "Summary at 9:12 AM" (today's clock time, else date + time, viewer zone) is server rendered. The ⋯ menu has Regenerate with disabled states "Updating…", "Available at <time>", "Daily limit reached (6 a day)". Run now (button and `runBriefingNow`) removed.
- Schedule: `runScheduled` records a `schedule` claim before the run (failure to record never stops the run). The schedule stays off until H-046.
