## Decisions
### A. mail-ingest-delta
- Cron `7-59/15 * * * *` (:07, :22, :37, :52), offset from cal-ingest's :00/:15/:30/:45. conn.sync has concurrency 1 per connection, so two events for one connection queue; the offset keeps the two ticks from queuing behind each other. Slots stay the 15-minute floor of the cron time.
- `streams` is an optional field of `conn/sync.requested` (`["mail"]`, `["calendar"]`, 1 to 2 entries, enum). It is passed through conn.sync -> job.run -> runner options -> the Google runner. No `streams` = both (manual, connect, webhook, any other provider). cal-ingest now sends `["calendar"]`; its header comment is updated. QuickBooks' generic runner ignores it.
- `listMailConnectionIds` is a new lister next to the calendar one (same query: native transport, usable statuses, provider list in `MAIL_PROVIDERS`).
- A mail-only run still writes ONE `sync_runs` row and calls `recordOutcome`, which sets `connections.last_sync_at` and clears `last_error`. Known consequence: a mail success clears an error left by a failed calendar run. Per-stream times in coverage come from `sync_cursors`, so freshness is still per stream; only the single `last_error` field is shared. The failure tracker (E) counts per stream to avoid hiding a failing calendar.
- Briefing refresh: after a scheduled, mail-only Google run with `written > 0`, `afterSync` sends `briefing/refresh.requested {laneId}` with event id `briefing-refresh:<lane>:<15-minute slot>`. New function `briefing-refresh` (retries 1) loads owners with the briefing, comms and calendar views (same check as briefing-daily, extracted as `ownersWithViews`) and calls `runRefresh` per owner in its own step.
- Claim: new SQL `core.briefing_claim_refresh(lane, owner)` (service_role) calls the existing `brief.briefing_claim(..., 'auto')`, so the gates are exactly Home's automatic run: 3 h stale, one running, 6 a day, 10-minute pause. Any gate returns "refused" and the model is never called. A claim that cannot be read stops the refresh (throws, no model call).
- The claim is closed by a new `core.briefing_claim_refresh_close(lane, owner, status)` that the job calls after the run (done / failed / lost). `core.briefing_save` is NOT changed: my first draft made it close `auto` claims, which broke the T-235 test (a service save must not end a claim an owner's Home opened). The pgTAP test checks the close.
- Trigger recorded on the saved briefing: `schedule` (adding a value would change a CHECK constraint on `brief.briefings`; not trivial).
- The refresh does not need `lane_config.briefing.schedule_enabled`. Risk: the 6-a-day cap is lane-wide and shared with Home opens, so overnight mail can use up runs (bounded: 3 h staleness means at most 8 candidates a day, cap 6). Noted in the PR as a risk.

### B. Sync now
- `POST /api/lanes/<lane>/sync-now`: Origin must equal this site and `Sec-Fetch-Site` (if sent) must be `same-origin` (a state-changing POST, stricter than the export GET); lane gate first (not a member: 404), then owner or admin_technical (other roles 403, AAL1 403, no session 401).
- Rate limit in the database, not an event id: `core.sync_now_claim(lane)` (authenticated, owner or admin_technical, AAL2, `connections` view) does one atomic upsert on `core.sync_now_requests` (one row per lane) that only takes when the last request is more than 2 minutes old; it returns `{ok, retry_after_seconds}`. A slot-based event id would let two clicks across a slot boundary through. The route also sends event id `sync-now:<connection>:<2-minute slot>` as a second dedupe.
- A lane with no usable Google connection answers `no_connections` BEFORE the claim, so it does not use up the limit or write an audit row.
- Audit `connection.sync_now` (who, lane, number of connections) is written BEFORE any event; if the audit fails nothing is sent (503). If some events fail to send, the others still start; all failing is 503.
- Button: a real `<button>`, disabled while running, `role=status aria-live=polite` result text (fixed text by status or code, never the server's words), router refresh after 6 s and 20 s on success. Drawn on Home next to the sync status line and on Settings -> Connections above the list, only for owner/admin_technical (Home: `requireRole`; Settings: the Google view is already null for other roles).

### C. Reconnect
- Start route accepts `?connection=<uuid>`; non-UUID -> 404. `flow.start(slug, lane, authorize, {connectionId})` looks the connection up through the lane's job client (`findById`: lane, provider, native, id; any status) and refuses with `not_found` (404) when it is not this lane's: foreign lane, unknown id, another provider.
- The id is bound into the state as a third part, `PKG.<43 chars>.<uuid>`. The whole state is hashed and only the hash is stored, so a changed value is simply an unknown state (invalid_state). `login_hint` (the stored address) is sent only for a reconnect.
- Callback: after `identify`, the connection is read again; a different account (case-insensitive compare) is refused as `wrong_account` before `ensureConnection` or `storeToken`, so no row and no token. The stored spelling of the address is passed to `ensureConnection`, so the same row is reused. The grant exists at Google at that point, so the existing "remove the app's access" notice applies. New fixed text for `wrong_account` in `connect-result.ts`.
- Existing behaviour that already did the work: `ensureConnection` reuses a row for the same (lane, provider, account) and `core.connection_token_store` replaces the Vault secret, sets status active and clears `last_error`, also from `disconnected`. QuickBooks and the ordinary Google connect still go through the same code with no connection id.
- UI: every Google row has its own Reconnect (aria-label "Reconnect <mailbox>"); the section-level "Reconnect Google" is gone; "Connect another Google account" stays on the last row. Shown on healthy rows too (outline button) so access can be refreshed (for example to grant a new permission); primary (filled) when the row is reconnect-needed, disconnected or degraded. Disconnected Google rows are now listed (state "Disconnected") so they can be reconnected; before they were hidden.

### D. Sync status line
- Pure logic in `packages/modules/briefing/src/domain/sync-status.ts` (`syncStatus`, `easternTime`, `syncErrorText`). One sentence per stream with a connected source; the age uses the OLDEST last-good sync among the stream's sources ("not synced yet" if any has none).
- A stream is failed when a source is in error OR its connection still carries a `last_error` (active connections with an error were previously read as ok).
- Fixed text per connector error code with the provider name ("Google access expired. Reconnect in Settings."); several mailboxes say "failed for 1 of 2 mailboxes"; the code reported is the one needing a person first. Unknown or hostile codes (including `__proto__`) get the generic text (own-property lookup).
- Title and aria-label carry Eastern clock times ("Mail last synced 9:42 AM ET."); the visible text stays relative. Phone shows "Synced" or "Sync issue" (full text for screen readers). "Status unknown" and "draw nothing with no source" are kept. Settings -> Coverage shows "Latest sync failed: <fixed text>" for an active source whose connection has an error.

### E. Failure alerts
- `withFailureTracking(inngest, tracker)` wraps `createFunction` for the whole route: every function with a cron trigger (including those built with `cron()`), plus `conn-sync`, gets Inngest's `onFailure` (runs only after retries are used up, so one failed run counts once) and a success mark after the handler returns (idempotent; no extra step, so no handler body runs twice). Event functions other than conn-sync are not tracked. conn-sync counts only runs whose event trigger is `schedule`; a skipped result (already running) neither counts nor resets.
- conn-sync is keyed per stream (`conn-sync.mail`, `conn-sync.calendar`): otherwise a failing calendar tick would be reset by the mail tick that succeeds between its failures.
- Crons record against every enabled lane (empty connection id). Per-lane, per-function, per-connection key in `core.job_failures`.
- Storage `core.job_failures` (lane_id, function_id, connection_id '' or uuid, consecutive_failures, streak_started_at, last_failure_at, last_error_code, last_success_at, alerted_at, updated_at). `streak_started_at` is an addition to the brief's list (needed for "since 9:15 AM ET"; a time only). Written only by `core.job_failure_record` / `_clear` (definer, service_role); read by the `health` view (owner, admin_technical) at AAL2. Error code is a connector kind, `lane_unavailable` or `failed`; the function maps anything else to `failed`; a CHECK enforces a short snake_case code.
- Retention: not added to the retention registry. The table is self-bounding: one row per (lane, function, connection), updated in place, never one row per failure (functions x connections of a lane). Same for `core.sync_now_requests` (one row per lane).
- Alert: when the SQL says `alert` (first time a streak reaches 3, `alerted_at` set once) the wrapper writes one `console.error("[job-alert] ...")` with lane, function, connection, code and the count; no message text. The banner (owner/admin_technical on Home and Settings -> Connections, via `jobFailureBannerFor`) reads rows with `alerted_at` set and 3 or more failures; it disappears after the next success (clear resets the row). Friendly names are in `FUNCTION_NAMES`; unknown ids read "A scheduled job".
- No email or push sender was built (rule 5 and no sender exists): backlog H-060 asks which channel.

### F. Stale-data line
- `staleDataLine(items, now, summaryAt)`: older than 24 hours means strictly more than 24 h (exactly 24 h is fresh), using the oldest last-good sync among the connected sources of that kind; a source that never synced counts as stale. Mail only, calendar only, and both (one combined sentence); the summary's own age over 24 h is appended to the same line ("This summary was prepared 27 hours ago.") or, when the data is fresh, is the whole line ("This summary was prepared 26 hours ago, so it may be out of date."). Hours are floored; from 48 h it says days.
- Shown at the top of the "Today at a glance" card from `brief.coverage` (the same coverage rows Home already loads); not shown when coverage could not be read.

## Mail stall (mail ~6 days old on Home; the Inngest 401s began only ~1 day earlier)
**Status: cause not confirmed.** It needs production data. The read-only queries are in `.agent/notes/T-238-mail-stall-queries.sql`. The local DB cannot help: it was reset, and it never held production history.

Checked in code (origin/main), all fine:
- **Expired or invalid `startHistoryId`.**
  - `google/mail.ts` `historyPage` turns Gmail's 404 on history.list into `fullResyncRequired`. A malformed or foreign cursor does the same.
  - `mail-sync.ts` resets the cursor and reloads once per run, never in a loop.
  - Covered by `mail.test.ts` ("a historyId Gmail no longer has...") and `mail-sync.test.ts` ("an expired history..."), using the MSW fake's real 404.
  - New (lead): the same fallback through the scheduled path, i.e. the Google runner with `streams: ["mail"]`: a full reload, the new message written, calendar untouched, then incremental again.
- **Targets.** `listCalendarConnectionIds` selects native Google connections with status active or degraded. A Composio-transport connection is never synced natively (T-219). If PKG's mailbox were Composio, nothing would sync it on a schedule; query 1 shows `transport`.
- **Stuck run.** The unique "one running" index cannot block for good: a run still `running` after 30 min is cancelled by the next start (`sync/store.ts` STALE_RUN_MS). Query 6.
- **Silent skips.**
  - `conn.sync` returns ok without syncing only for `already_running`, `connection_not_usable` or `lane_not_served`.
  - A page conflict (D0409) ends the run with 0 written and no error, but only if another run moved the cursor meanwhile.
  - Queries 4 and 5 show whether runs "succeed" with 0 written while the cursor does not move.
- **Mail vs calendar on one tick.** Before T-238, mail and calendar ran in the same conn.sync, and a failure in either failed the whole run and was retried. A permanent mail failure (for example forbidden or a scope problem) would leave calendar fresh but mail stale. Each run would be `failed` with that error kind (query 5).

Leading hypothesis, from timing: 6 days back is about Nov 8, the first production Google connect (the night test). So mail may have loaded once (trigger `connect`) and never synced again. That happens if the scheduled ticks were never reaching the app before the 401s (functions not synced in Inngest Cloud after the T-130 deploy, or Vercel protection already on), or if every scheduled run failed. To tell which:
- **Query 5:** no `schedule` rows means the ticks never arrived. Failed rows with an error kind point to the cause.
- **Query 3:** per-day writes for mail vs calendar show whether calendar kept moving while mail stopped.
