# T-247 notes: per-person mail privacy and several Google accounts per user

Branch `agent/T-247`. Built from the approved plan (`.agent/plans/T-247-privacy-multi-mailbox-plan.md`, Decisions section) and the brief.
Decisions made while building (scope decisions the brief left to the builder), newest thinking first within each topic.

## Ownership
- **Column and constraint.** `core.connections.owner_user_id uuid references core.users`. Check `connections_owner_only_mail`: only Google/Microsoft
  rows may carry an owner (QuickBooks and the rest never do). The brief asked for "required for Google/Composio rows" as a DB constraint
  "written so existing rows pass". I did NOT make a NOT NULL-style constraint: ~20 existing pgTAP files insert Google rows without an owner,
  and a NOT VALID check still fails on every later UPDATE of such a row. A mail row without an owner is **invisible to everyone** (every
  policy and reader needs `owner_user_id = auth.uid()`), so it fails closed. Required is enforced in code (`ensureConnection` and Composio
  `ensurePending` always set it; the OAuth callback refuses a row owned by someone else), and part 25 STOPS if any Google/Microsoft row has no
  owner after the backfill and `check-part-25.sql` asserts none. Reviewer: if you want the DB constraint too, it costs editing the ~20 test
  fixtures (an `owner_user_id` per insert) and is a one-line `alter table ... add constraint ... check (provider not in ('google','microsoft') or owner_user_id is not null) not valid` plus `validate` after the backfill.
- **Immutable, set once.** `connections_identity_immutable` now also refuses changing or clearing an owner that is set. null -> value is allowed
  once (service role only), so a legacy ownerless row can be claimed: the OAuth callback does that for the user who just proved control of the
  Google account (`ensureConnection`: `update ... where owner_user_id is null`). A row that already has an owner is never touched; a different
  user connecting the same Google account to the same lane is refused (`account_refused`, "already connected by another person").
- **Backfill** from `created_by` for Google/Microsoft rows (native and Composio both). QuickBooks rows stay null.
- **RLS on core.connections:** `connections` view (owner, admin_technical) reads the lane's rows as before (health columns only; column grants
  unchanged, plus `owner_user_id` so the UI can tell mine from others) OR own rows (`owner_user_id = auth.uid()` and own_mail in the lane).
  A viewer therefore sees exactly their own connection rows; a finance operator none.
- **One definition of "my mailboxes":** `core.mailbox_ids(uid, lane)` (definer, `may_resolve` rules: the caller at AAL2, or service_role for
  jobs). Policies call it as an init plan, readers call it explicitly. `core.mail_reader(p_owner)` picks `auth.uid()`, or the named owner only when the
  caller's role is service_role.

## The own_mail view and the old views (case by case, every `allowed_lanes(..., 'comms'|'calendar'|'briefing')` use)
- `own_mail` is in `view_names()`; held by owner (all views), admin_technical and viewer (role_views); NOT finance_operator. Not viewer-grantable by
  name (a viewer has it through the role).
- `comms`, `calendar` stay in `view_names()` (removing them would need a data migration of `memberships.views`: a viewer may hold 'calendar'/'briefing'
  by name) but **grant no content any more**: every mail/calendar policy and reader checks own_mail plus ownership instead. Test 319 proves a viewer
  given the named `calendar` view reads nobody else's events.
- `comms.message_index`, `cal.event_index`: policy = AAL2 + own_mail + `connection_id = any(mailbox_ids)`.
- Readers: `home_meetings`, `home_mail_attention` (no row without own_mail; service_role gets no row: it has no user), `home_calendar_status`
  (own connections only), `briefing_coverage` (definer; own accounts only, see below), `briefing_events`, `briefing_threads`, `inbox_messages`,
  `inbox_message_ref`, `act_reply_state` (always one row, but only for a mailbox the caller owns). Bodies copied from the NEWEST migration that defined
  each (briefing_threads: 20261119120000; briefing_coverage: 20261119110000; inbox_message_ref: 20261113120000; act_reply_state: 20261113130000).
- `briefing_coverage` used to list the lane's configured mailboxes (as "not_connected" when unconnected) plus every connection. It now lists the
  caller's OWN connected accounts only (two streams each) or one `not_configured` row per stream: another person's address or status never
  appears on someone's Home. The lane `mailboxes` list only feeds the `configured` flag. Admin health per account stays in Settings.
- Job path: the three briefing reads gained `p_owner uuid default null` (old signatures dropped; PostgREST named args keep working). It is used
  ONLY when the caller's role setting is service_role; a signed-in caller always gets `auth.uid()` whatever they pass (tested).
- `briefing` view still gates the lane's shared **news** digest (not mail): left on owner-only as today.
- sync-freshness/sync_now/job_failures/token health use `connections`/`health`: lane-level operational data, unchanged.
- Assistant tools (`list_recent_mail`, `list_meetings`): `requiredView` is now `own_mail` (`TOOL_VIEWS` gains it); they call the invoker readers, so they
  return only the caller's mail. The assistant gate still denies `admin_technical` outright (spec §3), unchanged: Saurabh has no assistant. Logged, not changed.

## Briefings per person
- Gate everywhere: `core.may_brief(uid, lane)` = own_mail in the lane. Replaces "owner role + briefing view" in `brief.briefings_guard`, both SELECT
  policies, `briefing_save_own`, the claim wrappers (`auto`, `regenerate`, `release`, `schedule`, `refresh`) and `briefing_run_state`. The brief said
  "owns a mailbox in the lane or holds own_mail"; owning a mailbox already requires own_mail (the owner views follow the role), so I used own_mail only: a user who
  lost their role cannot keep briefing through an old mailbox.
- Run claims: "one running", "one Regenerate per 30 min" and "10-minute pause" are now per owner (two users must not block each other); the **daily
  cap (6 claims per lane and New York day) stays lane-wide** as the cost bound. With two people that is 3 each on average: raise it if it bites (follow-up).
- Schedule: `briefingOwners` = distinct `owner_user_id` of active/degraded Google/Microsoft connections of the lane (job client); `ownersWithViews`
  re-checks own_mail per user on every run. `loadBriefing(..., ownerUserId)` passes `p_owner` to all three reads; `readGmailBody(..., expectedOwner)`
  refuses a connection that is not the run owner's. Tests: web (two users, prompt and saved record contain only own content), pgTAP 319, job owners.

## Drafts and email approvals
- `act.proposed_actions` SELECT: email.* rows only through `mailbox_ids` + own_mail; other types keep the old three clauses. `status_history` /
  `execution_claims` through the definer helper `act.action_rows_visible(action_id)`.
- `act.write_roles`: email -> owner, admin_technical (was owner). A viewer cannot propose/approve email (read-only mail). The real gate is the owner check.
- `act.approve` / `act.reject`: the row lookup adds `connection_id = any(mailbox_ids(caller))` for email types, so another user's draft is the same
  `not_found` as an unknown id (no probing). `act.claim_execution` re-checks the approver still owns the mailbox (direct query, not role-dependent).
- `act.insert_proposal` (propose, supersede, briefing drafts): an email proposal needs `proposer_user_id` = the connection's owner who still
  holds own_mail (membership read directly: this definer function is reached only by service_role code). The briefing already passed the owner.
  Consequence: assistant/job email proposals with a null proposer are refused.
- App: approvals first-check roles for email = owner or admin_technical; `isOwner` on the Approvals page and Home means "may act on email".
  `googleEmailWriter` also checks `connection.owner_user_id === approved_by` and the domain policy.

## Connect flow
- `core.oauth_state_create/consume`: provider `google` needs own_mail; every other provider (QuickBooks, ...) still owner/admin_technical. `MAIL_CONNECT_ROLES`
  (owner, admin_technical, viewer) + `connectRolesFor(provider)`; `AuthorizeFn(laneId, provider?)` so the route's role list depends on the provider.
- **How the two allow-lists combine (fail closed):** an address is allowed iff its domain is in `lane_config.mail.allowed_domains` AND (the exact
  `mailboxes` list is empty OR the address is on it). Empty `allowed_domains` allows nothing (no connect starts, no Google call is made). The list only narrows. Checked
  at connect precheck/identify, on EVERY Google call (`google/guard.ts`, `mail.ts`, `calendar.ts` through the guard) and in the email writer.
  Lanes that relied on the exact list alone (any other than PKG) must add `mail.allowed_domains` to keep working: PKG's is in part 25.
- `mail.self_connect_domains` is in the schema (default `[]`) and read by nothing.
- `laneMailboxes` (approvals, reply drawer) is now "the lane's own addresses" = configured list + connected accounts (used only for never-reply-to-self and
  display); the sender check is the new `mailboxAllowed`.
- Reconnect: only the owner can start a reconnect of a Google connection (`findById` returns the owner; others get `not_found`).
- **Composio:** `ensurePending` sets `owner_user_id` (and the existing RLS applies). Composio allows ONE account per lane per toolkit and replaces the earlier one,
  so it can't comply cheaply with per-person ownership: **the Composio connect (start and callback) is switched off for a lane that sets `mail.allowed_domains`**.
  Lanes without domains behave exactly as before. No change to the Composio unique indexes.
- Settings: "Your Google accounts" (connect/reconnect for the signed-in user's own accounts; visible to owner, admin_technical, viewer) plus other people's
  accounts as health-only rows (no buttons, no content) for those with the connections view. "Sync now" only with owner/admin_technical (`canSync`).
  Several accounts per user: native already allowed it; tested (two accounts of one user both show for that user only: pgTAP 319, connector test).
