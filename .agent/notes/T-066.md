# T-066 plan notes

Scope: Microsoft connect flow and identity (spec §5, §7, §17 tests 4 - 9). Built on the T-035 flow; Google behaviour unchanged.

Plan
1. Flow gets small optional provider hooks (nonce, loginHint/omitOnLoginHint, scopeCheckedByProvider, tokenHttp, callbackErrorReason, storedTokens, identify -> beforeStore) and two result codes (`wrong_tenant`, `admin_consent_required`). The nonce is derived from the stored PKCE verifier, so no new storage and no SQL.
2. `microsoft/id-token.ts` (no signature, V-6 checks), `microsoft/provider.ts` (precheck, scopes V-5, /me, policy, identity once), `microsoft/identity.ts` writer for `core.connection_set_microsoft_identity` (existing T-254 function).
3. Fake Entra gets the authorization_code grant (PKCE, nonce, id_token, scope formats), Graph /me profile variants; harness gets the real flow over twins.
4. Tests first in `microsoft/connect.test.ts`, then wiring; real-vault test in `vault/microsoft-token-path.test.ts` (lint keeps `createTokenVault` inside `vault/`).

Decision to flag: the tenant is recorded BEFORE the token is stored (acceptance lists store then identity). A failure between the two would otherwise leave an active row without a tenant (the guard refuses such a row) while the user is told nothing was stored.
