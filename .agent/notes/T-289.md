# T-289 + T-290 plan notes (Teams new-message notices, the "new" dot, refresh while open)

Branch `agent/T-289`, stacked on `agent/T-291` (unpushed Teams phases 1, 2, 3 server side, images, channels). T-288, T-292, T-293 are not built.

## Source of truth
`.agent/notes/T-277-vendor-facts.md` A3 (nothing added from memory): delegated `/users/{id}/chats/getAllMessages` is listed for v1.0 but shown only in a beta example (may be refused);
`includeResourceData: false` carries ids only and needs no certificate; `clientState` validation; lifetime 4,320 minutes on one page and 60 on another (record what Microsoft gives);
`lifecycleNotificationUrl` required beyond 1 hour; lifecycle events `reauthorizationRequired` and `subscriptionRemoved` (not `missed`); quotas 10 per user for all-chats subscriptions and 10,000 per organisation;
no background polling (once a day at most); no delegated delta.

## Decisions
1. **Subscription requests to Microsoft** follow EXACTLY the mail pattern: their own client (`teams/subscription-client.ts`, exact allow-list of POST/PATCH/DELETE on `/subscriptions` and
   `/subscriptions/{id}`, body keys per route, never `includeResourceData`, never retried, guard with `chat_read`), built only in the Teams wiring (`teams/index.ts`), logic (`teams/subscriptions.ts`) takes it as a
   TYPE-only parameter. The Teams read client stays GET-only, the write client stays three POST message templates and approvals-only. `write-boundary.test.ts` only names the four subscription files explicitly.
   Extra rule beyond mail: a POST must be `changeType` exactly `created` and `resource` exactly `users/<uuid>/chats/getAllMessages` (no per-chat resource can be sent).
2. **Resource string**: sent and recorded as `users/<entra object id>/chats/getAllMessages` (no leading slash), as the acceptance and spec 7.4 write it. Microsoft's page shows a leading slash. H-083 shows whether
   Microsoft accepts this form; the string is one constant (`teamsSubscriptionResource`).
3. **Receiver**: logic unchanged. The only code change is the store: `lookupMany` asks `core.push_subscription_lookup` for BOTH providers (`microsoft`, `microsoft_teams`) together, because a notification does not
   say which kind of connection it is for. Plus ONE content-free log line when an item carries `encryptedContent` (never asked for). `tenantId` is not read today for mail either; unchanged (the subscription id and its
   clientState are the proof).
4. **SQL**: no function of `push_subscription_*` is replaced (provider-generic). One constraint replaced (`resource` check), two added (provider/resource tie, Teams path). New table `comms.teams_activity` and eight
   functions. Production part 36 verifies the md5 of every function it relies on and the exact definition of the replaced constraint.
5. **Notice job** `teams-activity` (core/inngest): `teams_chats.changed` -> `core.teams_activity_notice` through `@nichols/connectors/teams-notices`. No Graph call.
6. **Dot and refresh** (T-290): the dot is a client component fetched after the shell rendered; the Messages page polls OUR database every 30 s while visible and re-reads Microsoft only when `last_notice_at`
   moved, or on Refresh / focus at most once a minute. The re-reads are two small routes (`/messages/chats`, `/messages/newer` with the `lastModifiedDateTime gt` date range) with their own per-person limiter.
