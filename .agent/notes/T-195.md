# T-195 notes: decisions made while building (Saurabh away, Nov 13, 2026)

Brief: `.agent/tasks/T-195-brief.md`. Branch `agent/T-195`, stacked on `agent/T-237`.

## Decisions
1. **Action type string.** The connector's writer action was named `qbo.revoke_grant`; the approvals type is `qbo.disconnect`.
   The approval hash covers `action_type`, so the proposal row, the hash and the writer must carry the same string.
   I renamed the connector constant `QBO_REVOKE_ACTION` to `"qbo.disconnect"` (one string end to end) instead of translating
   between two names, which would have broken "the executor passes `payload_sha256` from the locked row".
2. **Gate for disconnect = same as email.** Lane policy class **`qbo_disconnect`** in `core.lane_policies.write_actions_allowed`
   (new value in the check constraint) plus `lane_config.approvals.approvals_live`, checked at approve and again at claim.
   Revoking our own grant is low risk, but D-24 says no exception to rule 5 and the brief says follow the existing gate unless the spec
   says otherwise (the spec is silent). Consequence: before the sandbox QB-4 check, a person must add `qbo_disconnect` to the lane
   policy (SQL in the PR body) and have `approvals_live` true. Nothing in this task switches either on. The seed (generated) is not changed.
3. **Who.** `act.write_roles(type)`: owner or admin_technical for `qbo.disconnect`; email stays owner only. A disconnect is proposed only by
   a person (`proposer_kind = 'user'`; jobs and the assistant are refused in SQL). The database checks the role again at propose, approve,
   reject and claim (`approver_revoked` if the approver lost the role between approve and claim).
4. **Visibility.** admin_technical has no `approvals` view, so a new select-policy clause lets the `connections` view (owner, admin_technical)
   read `qbo.disconnect` rows of their lane. Email rows stay hidden from admin_technical (pgTAP proves it).
5. **Proposal content.** target = `{realm_id}` exactly (SQL checks it equals the connection's realm and nothing else), payload = `{}` exactly.
   No tokens, no company name. One pending/approved/executing disconnect per connection (`disconnect_already_pending`).
6. **Read-back.** `quickbooksDisconnectVerifier` (read-only): the authoritative row is `disconnected` and `vault.getToken` refuses.
   `vault.revokeToken` already deletes the secret and sets `disconnected` in one function, and the trigger
   `connections_no_orphan_secret` forbids `disconnected` while a secret exists; so the row ends `disconnected` by construction. The verifier checks both anyway.
7. **Failure semantics.** The writer keeps the Vault tokens unless Intuit confirmed (or said "already revoked"), and a repeat revoke is harmless,
   so a failure before the read-back is a plain `failed` (a new proposal is safe). A read-back that mismatches or cannot run is `outcome_unknown`.
   `external_id` for the claim is `connection:<id>` (nothing at Intuit to point to).
8. **No T-113.** Executes inline after the approval like email; a stuck one is finished by `action.reconcile_stuck` through a new read-only
   `qbo.disconnect` handler (verified when the connection is disconnected, else undecided until the give-up time).
9. **invalid_grant.** One hook (`onReconnectRequired`) in the token manager and the API client covers conn.sync, webhook CDC, reports, health and
   the connection test. It records `reconnect_required` + `last_error` with one conditional update (active/degraded only), so parallel
   failures notify once. Nothing retries: the refresh POST is `retry: false`, and sync/reports/webhook CDC skip any connection that is not
   active or degraded (tests assert no Intuit request after the status is recorded).
10. **Notification.** Reused `conn/attention.needed` (T-040), added reason `reconnect_required`, id `attn:<lane>:<conn>:reconnect_required:<UTC day>`
    (the health job's alert now uses the same reason and id, so Inngest drops the repeat). Best effort: if jobs are not configured only the notice is lost.
11. **Error map (QB-14).** `quickbooks/errors.ts`, applied at the end of `QboApi.get`. 401 that survives one refresh+retry, and 403 with Intuit code
    3100 (app not authorized), become `reconnect_required` (and record it). Other 403 = failed with a message. 404 = failed. 400 = failed with a
    category message (validation 2xxx/5xxx/6xxx/610, syntax 4xxx, other). 429 and 5xx and timeouts = retry; backoff is the shared client's
    capped exponential (500 ms base, 30 s cap, 3 retries, jitter) now set explicitly as `QBO_RETRY`; a Retry-After over the cap is not slept and is passed on as `retry_after_seconds` (conn.sync turns it into an Inngest RetryAfter).
    Messages are fixed text: Intuit's `Message` and `Detail` are never copied (a canary proves it). Also: `intuitErrorCode` now reads the gateway's lower-case `fault.error[0].code`.
    **Review change:** only 403+3100 (and invalid_grant) record reconnect_required; a 401 after a refresh is `forbidden`, status unchanged; token-endpoint errors are never classified as API errors.
12. **Reconnect.** Already worked through the T-050 connect flow (`ensureConnection` reuses the row, `storeToken` sets active). Gap fixed in SQL:
    `connection_token_store` now also clears `last_error`. Tests: after reconnect_required, after disconnected, different realm refused (existing connection untouched).
13. **Routes.** `propose_qbo_disconnect` is an action of the existing approvals POST route (no new route file). Roles are decided per action type
    (the action's type is read from its row via RLS, never from the request). A non-member of the lane gets 403 from `requireRole` (existing guard
    behaviour for every approvals action); another lane's connection or action id under the caller's lane is 404. No Settings button (T-197).
14. **Shared JCS vector.** `JCS_TEST_VECTORS` (`@nichols/connectors/writer`), values computed independently in Python; run by the connector test and by `hashOfRow` in the approvals module.
15. **Production SQL** is part 15 (`supabase/core/bootstrap/manual-migrations/part-15-T-195.sql` + `check-part-15.sql`). That folder is gitignored (as part 14), so the files exist only in this checkout.
