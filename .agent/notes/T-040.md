# T-040 conn.token_health and subscriptions_renew: design notes

No SQL, no new table: `core.connections` already has `token_expires_at`, `status` and `last_error`. No migration, no types change.

## Shape
- Events (packages/core/src/inngest/events.ts, all require laneId, all in LANE_EVENTS): `conn/health.check.requested`,
  `conn/subscription.renew.requested` (ids only), `conn/attention.needed` (laneId, connectionId, provider, reason enum,
  optional errorKind, daysLeft; never a message). The attention event has NO consumer: the backlog says "T-181 consumes
  it" but T-181 is now "Scheduling proposals" (stale reference, logged in plan-review).
- Core (conn-health.ts): four Inngest functions. Cron scans `conn-token-health-scan` (`0 11 * * *` UTC, daily) and
  `conn-subscriptions-renew-scan` (`15 */12 * * *`) list ENABLED_LANES, ask the injected lister for usable connections,
  and send one event per connection (`step.sendEvent`, Inngest event id per connection+day/hour so a retry dedupes).
  Workers `conn-token-health` and `conn-subscriptions-renew`: concurrency key connectionId limit 1, retries 2, validate
  the event again, lane check, injected job (core cannot import connectors), then send `conn/attention.needed` events with
  id `attn:<conn>:<reason>:<UTC day>` (one notification per reason per day). A lane whose listing fails is skipped.
- Connectors (packages/connectors/src/health, export `@nichols/connectors/health`): `createTokenHealthJob` (expiry rule +
  provider `health` checker), `createSubscriptionRenewJob` (interface), `createTokenHealthStore` (list + guarded update;
  wired in vault/index.ts with the lane job client). apps/web/app/api/inngest/route.ts registers the functions.

## Rules implemented
- Expiry: `token_expires_at` <= now + 7 days -> `token_expiring` (daysLeft), already past -> `token_expired`; 7d+1s not flagged.
  Pure expiry changes no row (the column already says it); the alert is the flag.
- Health: QuickBooks `connector.health` (a read-only CompanyInfo call). Google has no health op yet: expiry rule only.
  Failed check (non-retry kind) -> alert `health_check_failed`, `last_error` = redacted error, active -> degraded.
  A passed check heals degraded -> active and clears last_error. A transient/timeout/rate-limited result is inconclusive:
  no write, no alert (next day's run retries; avoids flapping on a network blip).
- reconnect_required is NOT applied as a status (T-195 owns that transition, the notification and stopping sync): the
  failure is flagged in last_error and alerted, status unchanged. Updates use `status = <loaded status>` as a guard so the
  job never overwrites a transition made meanwhile. Reconnect_required/pending/disconnected connections are not listed or checked.
- Renewal: `SubscriptionRenewer` interface; the registry is EMPTY (no provider implementation, no external call). Rule 5:
  renewing a subscription is a provider-side state change; before any implementation is registered it must be reviewed
  (it should go through the approvals module or be explicitly ruled infrastructure, not a data write). A permanent failure
  would set last_error and alert `subscription_renewal_failed`; success writes nothing (no column holds subscription expiry).
- Health checks are read-only; tokens are read only inside the connectors; events/rows/logs carry kinds, never messages from providers.
