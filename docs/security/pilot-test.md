# Pilot security test report (T-170)

Date: Nov 24, 2026 (revised after an independent mutation review). Branch `agent/T-170`. Written for the technical lead and the sponsor.
Synthetic data only; nothing here touched production, a live provider or a real person's records. Plan and inventory: `docs/security/pilot-test-plan.md`.

## 1. Verdict

**No open BLOCKER and no open HIGH finding was found.** The one MEDIUM (F-01, missing anti-framing headers) is fixed in code by T-299 (Nov 24, 2026) and waits for its production check (section 5, step 2); several LOW findings are listed in section 4. None of them lets someone read
another company's data, skip the approval chain, or reach a token, as far as the tests below can show.

"Found" is the honest word: the verdict is that these tests, which were themselves attacked on purpose (section 8: every property below was broken in a
rolled-back copy and the named test went red), found nothing. It is not a statement that none exists. Section 6 says what a passing suite does not prove, and
section 5 lists what still needs a person or a staging run.

## 5. What could not be tested here, and what a person must do

These need a browser, a hosted project, a live provider or a database reset, which this run was not allowed to use.

1. **Hosted Supabase settings.** In the hosted project's dashboard (Authentication): confirm "Allow new users to sign up" is OFF, e-mail OTP length 6 and expiry 600 s, and the rate limits for sending and verifying codes are on (these back F-02). Confirm MFA (TOTP) is enabled. Compare with `supabase/core/supabase/config.toml` (the `[auth.email] enable_signup = true` line is for the local code flow; production must have new accounts impossible).
2. **Response headers in production (after T-299 is deployed).** Open the portal in a browser, DevTools, Network, click the document request, then one `/api/...` request: each must show `x-frame-options: DENY`, `content-security-policy: frame-ancestors 'none'` and `x-content-type-options: nosniff`; note whether `strict-transport-security` is present. Then open a Teams chat that has a picture, find the request to `/api/lanes/.../messages/image` and note its `content-security-policy` (expected `default-src 'none'; sandbox; frame-ancestors 'none'`, once or twice) and `referrer-policy` (expected `no-referrer`): send both values to the agent, because how the hosting platform combines a route's own header with the configured one has not been seen. Then try to embed the portal in an `<iframe>` on a test page on another origin: the browser must refuse to show it.
3. **Cookies.** DevTools, Application, Cookies: the session cookies must be `HttpOnly`, `Secure` and `SameSite=Lax`.
4. **Inngest signing.** In Vercel (Production variables) confirm `INNGEST_SIGNING_KEY` and `INNGEST_EVENT_KEY` are set and `APP_ENV` is not `local`. From outside the company, an unsigned `GET https://portal.pub-k.org/api/inngest` must not list the functions.
5. **Real provider signatures.** Intuit: send a test notification from the Intuit developer page and check the portal queues it; resend with a wrong verifier token in staging and check 401. Microsoft: create a subscription in staging, post a notification with the right `subscriptionId` and a wrong `clientState` to the staging endpoint and check nothing is queued.
6. **Real approval, end to end.** In staging with a throwaway mailbox and a throwaway Teams account: propose, approve with a fresh authenticator code, confirm one message is sent; approve again (refused); set `approvals_live` false in a new lane config version and confirm approve is refused; remove the policy class and confirm the same. This is the live-provider half of what `338` proves in the database.
7. **Full database reset run.** A person runs `pnpm test:db` (with reset) on a spare machine; this run could only use `--no-reset`.
8. **Real-model injection run.** `INJECTION_REAL_MODEL=1 pnpm test:injection` with the Anthropic variables set on a developer machine.
9. **Production state.** Read-only query: `core.lane_policies.write_actions_allowed` and `approvals_live` for PKG in production match what the owner expects (the immediate off switch for any write path is `approvals_live` false in a new `lane_config` version).
10. **MFA attempt hook.** In the hosted Supabase project, Authentication, Hooks: confirm the MFA verification attempt hook is enabled and points at `core.mfa_verification_attempt`. Without it, authenticator-code guessing from an AAL1 session is not throttled.
11. **Same registrable domain.** List everything served from the portal's registrable domain (`pub-k.org` and its sub-domains: the website, marketing pages, anything a third party or a contractor can edit). If any page there is not fully controlled, F-01 is HIGH and the header fix is urgent.

## 6. What a passing suite does and does not prove

It proves that the rules written into the database policies, the function checks, the route guards, the approval gates and the redaction layer behave as
intended on synthetic data, that the properties named in section 2 are checked by tests that went red for the mutations listed in section 8, and that a
new table, function, route, provider, action type or model call site cannot be added without being looked at.

It does not prove: that the production database has the same migrations and settings as the local one (section 5); that the live providers behave as their
mocks do; that no vulnerability exists in code the suite does not enumerate (a new library, a browser-side flaw, a flaw in Supabase, Vercel or Inngest);
that people use the system safely (phishing, a stolen unlocked device); or that a real model will never be persuaded by hostile text (the suite proves what the
SERVER does when it is: nothing beyond two read tools, and no write without a human's approved exact content).

Limits of the new tests: the isolation tests seed rows with CHECK constraints, foreign keys and guard triggers relaxed inside a rolled-back transaction (policies, grants and RLS untouched), so they prove who may read what, not that every real row shape is valid. Static route checks see only that a guard CALL is present in the handler's code; they cannot see whether it is enforced (a call behind a condition that is never true, or a header that is read but not acted on, passes them). What catches that is the behaviour tests the inventory cites, which run the real handler code with the guards faked, and which are now part of `pnpm test:security`; the guards' own tests (`auth.test.ts`) show the guards refuse. The `335` oracle is pinned in the test (views per table, role-to-view literals, ownership rules), so it follows neither a changed policy nor a changed `core.role_views`.

## 7. How to run it

- Everything runs in the normal commands: `pnpm test` (vitest files and the node guard `scripts/security-suite.test.mjs`) and `pnpm test:db` (pgTAP).
- The vitest half on its own: `pnpm test:security`; with pgTAP (no reset): `pnpm test:security -- --db`, or `export PATH="$PATH:$(ls -d ~/.nvm/versions/node/v24*/bin | head -1)" && node scripts/test-db.mjs --no-reset`.
- The list is `scripts/security-suite.json`. A vitest file whose header carries the marker `T-170 (security suite)` or a pgTAP file named `*security*` that is not in the manifest fails `pnpm test`.
- Expected failures (`it.fails`) carry the finding id; when a finding is fixed its test fails loudly: remove `.fails`.
